# Kev-4B 推理提速：逐项测量与 kevfast 封装（2026-10-09）

负责人 2026-10-09 要求先把开源判官 Kev-4B 的推理速度提上去（准确率暂不管），并逐项统计每一步优化了什么。数字仅供参考，都是单次运行。

## 1. 环境与口径

| 项 | 内容 |
|---|---|
| 机器 | RTX 5060 Ti 16 GB（SM 12.0），torch 2.8.0+cu128，flash-linear-attention 0.5.2 |
| 模型 | 微调 v1（`/hy-tmp/train/runs/kev4b-v1`，只在算力服务器），bf16，LoRA 已合并，Kev 自带融合算子（`kev/fused_qwen35.py`） |
| 题目 | 评论场景的 3 题（辱骂、营销、注入防护）+ 各自打乱选项的复问，共 6 题，与 `eval-test.ts` 发出的相同 |
| 文本 | 测试集前 512 条（`text` 视图） |

## 2. 先测清楚的事实

**每条请求的组成（实测）**：Kev 原格式下，每条请求的中位数为 535 个 token；评论本身平均 26 个（中位数 18，p90 60），其余是规则原文和选项。Kev 的格式是"状态（评论）在前，每题一个分支在后"，分支之间互不可见，分支带着完整的规则原文。所以每条评论都要把所有规则重算一遍。Kev 的前缀缓存只在"状态完全相同"时命中。

**显卡上限（实测）**：bf16 矩阵乘法 51 TFLOPS（与推理同形状的 41–51），FP8 103 TFLOPS。

**一次推理的时间分布**（规则前置格式，一批 16 条，2,891 个 token，各模块前后同步计时；容器里没有 CUPTI 权限，用不了 torch.profiler）：

| 模块 | 占比 |
|---|---|
| MLP（32 层） | 50.5% |
| Gated DeltaNet 线性注意力（24 层） | 32.5% |
| 普通注意力（8 层） | 11.3% |
| 其他 | 5.7% |

**并发上不去的原因**（kev.serve，原格式，500 条，只有辱骂和营销两题 + 复问）：

| 并发 | 每秒条数 |
|---|---|
| 1 | 6.4 |
| 16 | 8.0 |
| 64 | 8.7–11.7 |

单条耗时从并发 1 时的 125 ms，涨到并发 64 时的 5.4–7.3 s。显卡此时已经满载。

服务端显存设置调过两次：开 `expandable_segments` 每秒 8.2 条；关前缀缓存那组没测完，提速转向逐项优化后就停了。默认设置下，v0 评测时 7 次 CUDA graphs 捕获全部因显存不足失败，后来几次服务启动是 0 次失败。

## 3. 逐项测量（`scripts/gpu/kev_speed_bench.py`）

速度测法：规则原文只算一次，作为缓存前缀（294 个 token）；每条评论一行，接在前缀后面，行内是"评论 + 题目分支"。各阶段都是 eager 模式（不开 CUDA graphs），每批 32 条，另测一条一条发时的单条耗时。

漂移测法：用训练过的原格式答 200 条（1,200 道题），和 S0 的 bf16 答案比较。

| 阶段 | 改了什么 | 每秒条数（批 32） | 相对上一阶段 | 单条 p50 | 每条 token（中位数） | 补齐浪费 | 答案漂移（vs bf16） |
|---|---|---|---|---|---|---|---|
| 参照 A | Kev 原格式，eager，一条一条 | 4.8 | — | 209 ms | 535 | — | — |
| 参照 B | Kev 原格式，kev.serve（CUDA graphs），4 题，并发 64 | 11.7 | — | 125 ms（并发 1） | — | — | — |
| S0 | 规则前置：规则只算一次缓存起来，评论只算一次；分支仍带"按上面的规则 X 判断这条内容"和三个选项 | 21.1 | — | 88–96 ms | 182 | 27.2% | 参照 |
| S1 | + FP8 矩阵乘法（权重按行、激活按 token 动态缩放，`torch._scaled_mm`） | 27.8 | +32% | 130–138 ms | 182 | 27.2% | 平均 \|dp\| 0.0024，最大 0.118，首选变化 2 / 1,200 |
| S2 | + 按长度分批（先排序再分批，少补齐） | 38.5 | +38% | 130 ms | 182 | 3.8% | 同 S1（只改分批） |
| S3 | + 分支只留一行：规则原文只在缓存前缀里，选项写成"是 / 否 / 不确定" | 66.7 | +73% | 131 ms | 100 | 6.5% | 需重新训练，未测 |
| S4 | + 去掉复问（6 题 → 3 题） | 92.5 | +39% | 130 ms | 67 | 9.1% | 需重新训练，未测 |

每秒处理的 token：S0 是 4,037，S2–S4 是 7,049–7,366。

以批量吞吐看，S4 是 S0 的 4.4 倍，是参照 B 的 7.9 倍。参照 B 只问两题 + 复问；线上实际是三题 + 复问，评测时测得每秒约 8 条，按这个算是 11.6 倍。

## 4. 没做或没做成的

1. **单条耗时被 FP8 拖慢**：88–96 ms → 130 ms。一条一条发时矩阵很小，激活量化的额外算子和 `_scaled_mm` 的固定开销超过了收益。没有按批大小切换 bf16 / FP8，也没有把激活量化融合进前一个算子。
2. **CUDA graphs**：各阶段都是 eager。参照 A 和参照 B 的单条差（209 → 125 ms）里有 CUDA graphs 的作用，但两者的服务路径和题数不同，不能单独归因。FP8 和新格式还没接进 kev.serve 的 graphs 路径。
3. **线性注意力换算子**：vLLM 用的 FlashInfer Blackwell GDN 预填充算子（flashinfer PR #3001）只支持 SM100/SM100A + CUDA 13。这张卡是 SM120，torch 用的是 cu128，所以没试。
4. **准确率**：S1 只测了相对 bf16 的漂移，没在测试集上重算 AUROC 和分流；S3、S4 改了输入格式，要按新格式重新训练后才能评测。另外，按新格式（规则前置）导出训练数据时，Kev 训练的状态上限是 384 token，规则 294 token 加上评论后，12,693 条里有 758 条超长会被丢掉（训练于 10-09 启动后按负责人要求停止）。
5. **S0–S4 的"一行"**：评论和所有题目分支在同一行里，后面的分支能看到前面的分支。Kev 原本的分支互不可见。速度上的计算量相同，但这不是能直接用的格式。正式实现需要分支之间的注意力隔离（块因果掩码），或者让 Kev 的缓存支持"规则前缀 + 评论续算"再分支。
6. **vLLM / SGLang**：没换。有报告称 vLLM 里 Qwen3.5-4B 的前缀缓存块是 528 token，短于此的前缀命中率为 0。我们的规则前缀是 294 token。另外 Kev 的指针头需要自行移植。

## 5. kevfast：可开关的推理引擎（`python/kevfast/`）

负责人 10-09 要求："先不管准确率……把优化到极致的情况先封装好，先修复你目前的问题，然后把每一个优化的功能封装成一个可以开关的选项"。第 3 节的原型有两个问题：各题在同一行里能互相看见；FP8 让单条变慢。kevfast 是重写的推理路径，用同一个 Kev checkpoint。

**怎么算**：每次计算把一批 token 段首尾拼接（不补齐），段分三层：

| 层 | 内容 |
|---|---|
| 前缀 | 规则块，可选，跨请求缓存 |
| 内容 | 每条请求一段 |
| 分支 | 每道题一段 |

- DeltaNet 层把父段的最终状态作为子段的初始状态，用的是 fla 的 varlen 算子，传入每段的初始状态。
- 注意力层每段只读祖先段和自己（因果）。所有段共有的前缀，在批量小时随段一起取出、走融合 SDPA；批量大时单独算一次，再按 log-sum-exp 精确合并。
- 分支之间互不可见，与 Kev 一致。

**开关**（`Options`，服务端用 `KF_*` 环境变量；`/v1/models` 会报告当前开关，评测可据此记录）：

| 开关 | 取值 | 作用 | 改变模型读到的输入？ |
|---|---|---|---|
| layout | native / rules_first | rules_first：状态以 `rules` 字段开头时，规则块作缓存前缀 | 是（需按该格式训练） |
| questions | full / short | short：分支只有规则名和短选项 | 是 |
| confirm | on / off | off：不算 `#confirm` 复问 | 少答一半题 |
| fp8 | off / on / auto | FP8 矩阵乘法；auto 只在一次计算 ≥ fp8_min_tokens 时用（同时保留 bf16 与 FP8 两份权重） | 只改舍入 |
| branch_mode | two_pass / rows / auto | rows：一次计算，每道题一行"评论 + 分支"；two_pass：先算评论，分支接着它的状态算；auto：≤ 4 条请求用 rows | 否 |
| cuda_graphs | on / off | rows 调用按 16 token 分档右补齐，每个（行数，档位）录制一次 CUDA graph 后重放；服务端遇到新题目组合时预录 | 否 |
| max_pass_tokens 等 | 数值 | 每次计算的 token 预算（16 GB 卡上约 14k 分支 token 时显存不足）、图的大小上限 | 否 |

**一致性检查**（`python -m kevfast.check_parity`，96 条文本，和 Kev 自己的 bf16 计算比）：

| 检查 | 题数 | 最大 \|dp\| | 平均 \|dp\| | 首选变化 |
|---|---|---|---|---|
| native，two_pass | 576 | 0.0166 | 0.00044 | 0 |
| rules_first，two_pass（和 Kev 对同一串 token 的计算比） | 576 | 0.0254 | 0.00059 | 0 |
| native，rows | 576 | 0.0116 | 0.00039 | 1 |
| rules_first，rows | 576 | 0.0161 | 0.00056 | 0 |
| rules_first，rows，单条 + CUDA graphs | 96 | 0.0109 | 0.00038 | 0 |
| native，fp8=on（对 bf16） | 576 | 0.0892 | 0.00213 | 2 |

**提速阶梯**（`python -m kevfast.bench`，512 条测试文本；吞吐为每批 32 条，单条为一次一条、64 条；单条在 E6 前先预录图）：

| 阶段 | 每秒条数 | 单条 p50 | 单条 p95 | 显存峰值 |
|---|---|---|---|---|
| E0 原格式、全题 + 复问、bf16（Kev 的计算，拼接不补齐） | 9.4 | 206 ms | 231 ms | 10.6 GB |
| E1 + rules_first | 17.7 | 215 ms | 240 ms | 12.3 GB |
| E2 + short 问题 | 27.1 | 205 ms | 212 ms | 13.0 GB |
| E3 + 去复问 | 42.3 | 203 ms | 222 ms | 11.4 GB |
| E4 + fp8 auto | 55.4 | 203 ms | 210 ms | 14.8 GB |
| E5 + branch_mode auto | 55.5 | 104 ms | 118 ms | 14.8 GB |
| E6 + CUDA graphs，fp8 改为 on | 55.3 | 37.8 ms | 51.8 ms | 11.5 GB |

E6 用 fp8=on 是因为：fp8=auto 时同时保留两份权重，再预录图会在 16 GB 卡上显存不足（实测一次 OOM）。

**单条耗时拆解**（rules_first + short + 去复问 + fp8 auto，单条，各段同步计时）：两次计算各约 100 ms，分别只算 33 个和 54 个 token。主要开销是每层的算子启动：每次计算约 600 次调用。rows 模式合成一次计算后约 105 ms，加 CUDA graphs 后约 38–48 ms。批量 32 条时，带同步计时的矩阵乘法约 290 ms（2,784 个 token）。

**服务端端到端**（`python -m kevfast.serve`，原格式 + 全题 + 复问 + fp8=on + 自动分支 + CUDA graphs，`eval-test.ts collect` 并发 32，完整测试集）：

| 判官 | 请求 | 用时 | 辱骂 AUROC | 营销 AUROC | 注入 AUROC |
|---|---|---|---|---|---|
| Kev 原服务（v1，第 5 节前的评测） | 3,002 / 0 失败 | 约 6 分钟 | 0.9644 | 0.9987 | 0.9961 |
| kevfast（同一 checkpoint） | 3,002 / 0 失败 | 282 s | 0.9643 | 0.9986 | 0.9957 |

第一次端到端运行时 3,002 条全部返回 422：`serve.py` 用了 `from __future__ import annotations`，FastAPI 认不出局部导入的请求类型。去掉后重跑。失败的那次输出移到 `/hy-tmp/train/void-kevfast-422`。

**还没做**：
1. rules_first / short / 去复问的准确率：要按新格式训练。规则前置时 Kev 训练的状态上限（384 token）会丢 758 条，见第 4 节第 4 条。
2. 批量路径（two_pass）没有 CUDA graphs，分支那次计算仍偏慢：一批 32 条时 303 ms，内容那次 171 ms。
3. 去掉复问后，快判的"复问一致"检查（`confirmsCallId`）就没有了，策略层怎么处理没改。
4. 单元测试：kevfast 只能在 GPU 上跑，没进 CI；一致性检查和 bench 是在算力服务器上手动跑的。

## 6. 批量路径的 CUDA graphs 与单卡上限（负责人 10-09："先给批量路径也加上 CUDA graphs，我们试出单卡的极限处理速度"）

**做法**：批量调用（two_pass）改成补齐到固定形状，这样才能录制 CUDA graph（`dense=True`）。补齐有两个难点：
1. **DeltaNet 状态**：补出来的位置把门控输入设为 -1e4，那一步衰减为 1、写入为 0，递推状态原样穿过。
2. **卷积状态**：按每行真实长度取最后 4 个输入。fla 的卷积状态就是最后 W 个原始输入，已实测。

批大小分档（8、16、24、32、48、64……），长度按 16 token 分档，每档录制一个图。原格式下和 Kev 比对：48 条、288 道题，最大 |dp| 0.010，首选变化 0。

**实测**（rules_first + short + 去复问 + fp8=on，最短的 400 条测试文本，每种跑 10 次）：

| 路径 | 一批 16 条 | 一批 32 条 | 预留显存（32 条） |
|---|---|---|---|
| 拼接不补齐（varlen），eager | 306 ms（52.3 条/秒） | 477 ms（67.1 条/秒） | 8.2 GB |
| 补齐（dense），eager | 397 ms（40.3） | 751 ms（42.6） | 10.1 GB |
| 补齐 + CUDA graphs | 361 ms（44.4） | 739 ms（43.3） | 9.8 GB |

一批 32 条时，CUDA graphs 只省了约 2%，补齐反而让每批多花 57%。所以 `dense` 默认关闭，批量调用仍走拼接不补齐的路径。单条 / 小批量调用（≤ 4 条）照旧走"单次计算 + CUDA graphs"。

显存方面，录制一个"一批 32 条"的图，私有显存池约 4.5 GB，主要是 32 条评论在 24 层的递推状态（每条每层 2 MB，fp32），外加分支那步临时复制的状态。录制前的预热占用的显存会被缓存住；录制前先 `empty_cache` 也没有降下来。长评论的批次在已有图的情况下再预热，会显存不足。

**单卡上限**（全部开关打开，varlen two_pass，512 条测试文本按原顺序，每次调用的条数 × 每次计算的 token 预算）：

| 每次计算的 token 预算 | 每次 32 条 | 64 条 | 128 条 | 256 条 |
|---|---|---|---|---|
| 4,096 | 55.6 条/秒（5,407 token/秒） | 55.8 | 51.2 | 54.1 |
| 8,192 | 55.5 | 54.5 | 55.4（显存峰值 13.8 GB） | 53.2 |
| 12,288 | 55.6 | 54.6 | 显存不足 | 显存不足 |

每条评论平均约 97 个 token（评论约 30 个 + 3 个分支）。加大批量或预算不再提高吞吐。按 3.5B 参数估算约 38 TFLOPS，是这张卡实测 FP8 矩阵乘法峰值（103）的约 37%。第 3 节原型的单行写法（各题互相可见）是 7,300 token/秒。

**其他改动**：fp8=on 的引擎会释放 bf16 权重，所以把 FP8 权重挂在模型上，同一进程里后续的 fp8=on 引擎直接复用；需要 bf16 时直接报错，不会悄悄出错。

## 7. 不改答案的算子优化（续）

**分段计时**：新增 `KF_PROFILE=1`，打开后按段同步计时，只在测量时用。测的是一批 32 条，全部开关打开，fp8=on，two_pass，512 条，单位是每批毫秒；同步会让总时间偏大。

| 段 | 内容 | 分支 |
|---|---|---|
| MLP | 99 | 114 |
| DeltaNet（卷积 + 递推 + 门控范数） | 68 | 77 |
| 注意力 | 38 | 55 |
| 输入投影 | 39 | 44 |
| 输出投影 | 22 | 23 |
| 范数 | 16 | 16 |
| 状态复制 | 6 | 18 |
| 掩码构建 | 3 | 8 |

另外，CPU 上的分词共 45 ms（算预算 23 + 分组 22）。

**改动与实测**（同一脚本，每次用新的请求对象，跑 3 遍）：

| 改动 | 每秒条数 |
|---|---|
| 之前 | 54.9 |
| 分词缓存：每条评论只分一次词，题目分支按题目缓存 | 59.2 / 59.4 / 59.6 |
| 对照：注意力改用 LSE 合并（`KF_SDPA_GATHER_MB=0`） | 55.4 / 55.7 / 55.7（更慢，不采用） |
| DeltaNet 用 fla 的逐 token 递推算子（`deltanet_kernel=recurrent`） | 58.6 / 58.9 / 58.8 |
| `deltanet_kernel=auto`（平均段长 < 32 时用递推） | 59.5 / 59.6 / 59.6 |

逐 token 递推算子的答案和 Kev 比对过：32 条，最大 |dp| 0.0146，首选变化 1。

没做：
- 激活量化与前一个算子融合。
- 内容与分支两次计算合并成一次以增大矩阵行数。
- 按题目分组调用 DeltaNet 以免复制状态（实测状态复制每批约 24 ms）。

## 8. 新的短问题格式、HTTP 服务压测与中等批次

**压测发现的问题与处理**：
1. 第一轮用每次最多 64 条、每次计算 8,192 token，并发 128 / 256 时 GPU 显存不足，返回 HTTP 500。处理：
   - 服务端遇到显存不足时，清缓存后把这一批拆成两半重算（`/v1/models` 报告 `oom_splits`）。
   - 默认改为每次最多 32 条、每次计算 4,096 token。第 6 节上限测试中，更大的批量没有更快。
   - 改完后并发 128 / 256 的 0 个 500、0 次显存不足。
2. 模型线程和 HTTP 事件循环争 GIL：照 kev.serve 的做法，把线程切换间隔设为 0.5 ms。
3. 单次计算模式的图原先按（行数，长度档）各录一个，行数种类多时会超过上限、反复重录。现在行数也分档（3、6、12、24、48），图的上限改为 64。

**中等批次的三种做法**（引擎层直接调用，rules_first + short + 去复问 + fp8=on，每次调用的条数 1–16，每次调用的 p50）：

| 每次条数 | 单次计算 + 图（rows） | 两次计算，拼接不补齐（varlen，eager） | 两次计算，补齐 + 图（dense） |
|---|---|---|---|
| 1 | 37 ms | 240 ms | 183 ms |
| 2 | 69 ms | 243 ms | 200 ms |
| 4 | 156 ms | 253 ms | 218 ms |
| 8 | 235 ms | 263 ms | 238 ms |
| 12 | 268 ms | 272 ms | 490 ms |
| 16 | 304 ms | 304 ms | 528 ms |

默认：≤ 8 条用单次计算 + 图，更多用拼接不补齐（`rows_max_requests=8`、`dense=False`）。

dense 有批大小下限 8：1 条也补到 8 行，所以 1 条和 8 条耗时接近。即使开着图也要 180 ms 以上，说明在这个规模上主要不是算子启动开销，而是按 token 计的计算本身。按补齐后的 token 数算，各路径都在每秒 4,000–5,000 token 左右。

**不足**：
- 单卡每秒约 50 条请求，按每天 86,400 秒折算约 430 万条。这是用测试集文本、单一题目组合、单台服务测得的。没测多卡、多题目组合混合，也没测长文本占多数的流量。
- 每 token 的计算成本为什么在小批量时也降不下来，没有用 Nsight 一类工具定位（容器里没有 CUPTI 权限）。

## 9. kevfast 作为 Kev 服务的直接替代：完整判官评测流程

做法：kevfast 用原格式、全题 + 复问、fp8=on、自动分支、CUDA graphs，服务 v1 checkpoint，然后把 `scripts/gpu/run-judge.sh` 原样跑一遍：
1. 在 1,884 条校准行上拟合它自己的温度（calib@7bc643deadeb）。
2. 测试集两个视图各 3,002 条，客户端并发 16。
3. 用线上阈值算分流，再算区分度。

整个流程 7,888 次请求，用时 848 秒，0 次显存拆分。

| 判官服务 | 辱骂 AUROC | 营销 AUROC | 注入 AUROC | 违规被自动放行 | 违规自动处置 | 正常自动放行 | 正常被误处置 |
|---|---|---|---|---|---|---|---|
| kev.serve（v1，第 5 节前） | 0.9644 | 0.9987 | 0.9961 | 2.0% | 44.4% | 68.2% | 0.3% |
| kevfast（同一 checkpoint） | 0.9641 | 0.9987 | 0.9962 | 1.8% | 43.6% | 67.6% | 0.3% |

text 视图成功请求的单次耗时：p50 1,663 ms，p95 1,856 ms（客户端并发 16，原格式每条 6 题）。

差异来自 FP8 的舍入，以及各自重新拟合的温度。

## 10. 新格式的训练与逐项准确率（v2s）

**做法**：
- **训练数据**：`train-v2s.jsonl` 和 v1 的条目、标签完全相同，格式改为规则前置 + 短问题。用 `scripts/gpu/train-eval-kevfast.sh` 训练，`--max_state 768`，丢了 5 条超长；batch 4 × accum 2，1 轮，lr 2e-5，约 0.77 秒 / 条，约 2.7 小时。
- **评测**：kevfast 服务训好的 checkpoint，按 rules_first、short、复问、fp8=on 配置，跑完整 run-judge 流程：拟合它自己的校准，测试集两个视图，阈值沿用线上的。
- **逐项对照**：在同一个 checkpoint 上每次只改一个开关，只评测不重训。注入检查这一题训练数据里没有，和 v1 一样。

**结果**（测试集 3,002 条，`text` 视图）：

| 配置 | 辱骂 AUROC | 营销 AUROC | 注入 AUROC | 违规被自动放行 | 违规自动处置 | 正常自动放行 | 正常被误处置 | 并发 16 时单次请求 p50 |
|---|---|---|---|---|---|---|---|---|
| v1（原格式，kevfast fp8，第 9 节） | 0.9641 | 0.9987 | 0.9962 | 1.8% | 43.6% | 67.6% | 0.3% | 1,663 ms |
| v2s（rules_first + short + 复问 + fp8） | 0.9622 | 0.9989 | 0.9721 | 1.5% | 49.9% | 66.8% | 0.5% | 783 ms |
| v2s，fp8 改 bf16 | 0.9620 | 0.9989 | 0.9797 | 1.6% | 49.4% | 67.2% | 0.5% | 698 ms |
| v2s，去复问 | 主问 0.9622 | 主问 0.9989 | 主问 0.9892 | 0 | 52.8% | 0 | 0.9% | 448 ms |

上表 AUROC 是主问与复问的平均；去复问那行只有主问。v2s 只看主问时：辱骂 0.9621、营销 0.9988、注入 0.9898。

**看到的现象**：
1. 辱骂、营销两题，新格式与原格式的区分度差在 0.002 以内。
2. 注入检查的复问在新格式下明显变差：平均 0.972，只看主问 0.990。这一题没有训练过；原格式下，题目分支里带着完整的规则文字和选项说明。
3. **去复问后，快判一条也不自动放行**：正常 0% 自动放行，99.1% 转 agent。原因是场景开关 `confirmPass` 默认开，放行要求同次复问确认；没有复问，就永远不满足放行条件。要去复问，策略层要同时把 `confirmPass` 关掉。这正是开发计划第 8 节"双确认默认开还是关"那一项，待负责人定。
4. bf16 和 FP8 的差别在噪声范围内：注入那一题差 0.008，其余差 0.001 以内。

**"双确认"开关的假设测算**（给负责人决定第 8 节用）：`WHATIF_CONFIRM_PASS=off` 让评测脚本只在内存里把场景的 `confirm_pass` 当作关闭。规则版本和校准都不变，所以这不是发布。用已有的 v2s 答案重新算分流：

| 配置 | 违规被自动放行 | 违规自动处置 | 违规转 agent | 正常自动放行 | 正常被误处置 | 正常转 agent |
|---|---|---|---|---|---|---|
| v2s，有复问，confirm_pass 开（现行） | 1.5% | 49.9% | 48.6% | 66.8% | 0.5% | 32.7% |
| v2s，有复问，confirm_pass 关 | 2.0% | 49.9% | 48.2% | 68.1% | 0.5% | 31.4% |
| v2s，去复问，confirm_pass 开 | 0 | 52.8% | 47.3% | 0 | 0.9% | 99.1% |
| v2s，去复问，confirm_pass 关 | 2.1% | 52.8% | 45.2% | 71.4% | 0.9% | 27.7% |

上表第一行"违规转 agent"和"正常转 agent"两格，是用其余列推算的（100% 减其余两项）。

**问题与处理**：
- 第一次跑去复问对照时，服务端去掉了复问，但评测客户端仍发复问题。pi-ai 的 TypeSafe 客户端发现回答缺题，把 3,002 条请求全部判为失败，尽管服务端都返回了 200。
- 处理：
  - 评测与校准脚本加了 `JEV_IN_CALL_CONFIRM=0`，不发复问。
  - kevfast 在 `KF_CONFIRM=off` 时收到带复问的请求，直接返回 400 并说明原因。
- 作废的输出移到算力服务器 `/hy-tmp/train/void-v2s-noconfirm/`（开发计划问题 15）。

**不足**：
- 只训练了一次，没有重复。
- 注入题没有加进训练。
- 去复问时没有同时关 `confirmPass` 再测分流。
- 训练标签与测试集同源（微调报告第 4 节）。

## 11. Kev 识图（零训练可行性，负责人 10-09："kev 识图要做……你先试试看能不能识图"）

**做法**（`python -m kevfast.vision_probe`）：
- **权重移植**：Kev 只保留了 Qwen3.5 的语言部分，它的底座 `Qwen/Qwen3.5-4B-Base` 是多模态的（`Qwen3_5ForConditionalGeneration`，自带视觉编码器）。把 v1 checkpoint 的 LoRA 用 PEFT 合并进语言权重，装回完整的多模态底座，视觉编码器保持底座原样。装载时检查：参数缺失 0、多余 0。
- **输入**：图片按 Qwen 的方式编码，`<|image_pad|>` 按合并后的 patch 数展开，`mm_token_type_ids` 标出图片 token 供 M-RoPE 使用。图片放在状态的 `content.image` 位置，后面接 Kev 的题目，原格式、一题一次。
- **测试图片**：测试集前 200 条文本，用文泉驿微米黑渲染成"评论截图"（白底卡片 + 头像占位 + 正文，每行 22 字）。图片只在算力服务器上生成，没有提交。

**结果**（仅供参考）：

| 检查 | 结果 |
|---|---|
| 移植是否正确：纯文本走多模态路径 vs Kev 自身（20 条 × 2 题） | 最大 \|dp\| 0.0143，平均 0.0008 |
| 辱骂（违规 30 / 允许 166）AUROC | 看文字 0.947，只看图片 0.931；两种输入首选一致 93.0% |
| 营销（违规 15 / 允许 183）AUROC | 看文字 0.999，只看图片 0.997；首选一致 97.5% |
| 速度（单张，eager，bf16，不融合，两题各一次前向，图片也编码两次） | p50 277 ms，p95 312 ms；每次前向约 240 token |

**过程中的问题**：
1. Kev 加载后语言部分仍是 PEFT 包装（`LoadOptions.merge` 对这个 bf16 训练的 checkpoint 没有合并），第一次移植时 426 个参数缺失、922 个多余，等于装的是原版底座。那一轮的数字作废。改为 `merge_and_unload()` 后严格检查为 0，并且在替换前先用 Kev 原路径算参考答案。
2. transformers 的图片预处理器要求 torchvision。算力服务器的 kev 环境用 `uv pip install torchvision==0.23.0 --no-deps` 从阿里云 PyTorch 镜像装上（匹配 torch 2.8.0+cu128）。用 `uv run` 启动 kev 时，可能会把这个不在锁文件里的包同步掉。

**不足**：
- 只测了文本渲染成的截图，没有测真实照片和纯画面内容。
- 200 条里营销违规只有 15 条。
- 没训练过图片。
- 速度没有优化。

**接进 kevfast**：`Engine.attach_vision` 挂上底座的视觉编码器（`common.load_vision`，从多模态底座里只取 `visual`）。请求的 `content.image` 可以是 PIL 图片或 base64 / data URL，HTTP 服务里也一样。
- **怎么算**：一次调用里的所有图片做一次视觉编码。视觉特征写进评论段对应位置的嵌入；图片 token 用 (t, h, w) 三维位置，后面的文字从图片最大位置 + 1 接着编。题目分支照常从评论段的状态接着算。带图的调用固定走 two_pass，拼接不补齐，不走录图。
- **对照**：`python -m kevfast.check_vision` 与上面多模态参考路径存下的答案比，同一批渲染图 200 张 × 2 题：最大 |dp| 0.082，平均 0.0021，首选变化 1 / 400。比纯文本的一致性检查大，原因可能是 kevfast 用了融合算子，参考路径没用，没有进一步定位。
- **速度**（原格式、两题、无复问）：

| 配置 | 单张 p50 | 单张 p95 | 每批 16 张的吞吐 |
|---|---|---|---|
| bf16 | 248 ms | 264 ms | 11.2 张/秒 |
| fp8=on | 322 ms | 342 ms | 13.6 张/秒 |
