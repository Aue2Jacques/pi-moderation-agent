## 3. agent 为什么几乎不处置

用 agent 最后一次复判的证据集重算当时的 support（`supportOf`，和提交检查同一套函数）：34 条里 A 组 29 条、C 组 31 条在交人工时 `allowed_now` 为空——判官带着上下文和历史复判后，违规概率大多仍在 0.10–0.90 之间（ABUSE-001 处置线 0.90、MARKETING-003 0.92，放行线都是 0.10），agent 按规则只能交人工；另有少数是主问和复问不一致。agent 没有处置权，只能在判官支持的范围内选择，这是现在的设计。

**离线敏感度**（不重跑，用 agent 最后一次复判记录的校准后概率取主问、复问平均，不要求复问确认；34 条 agent 审次；仅供参考，样本太少，不能用来定阈值）：

| agent 阶段处置线 / 放行线 | A：自动对 / 自动错 / 预期转人工却自动 / 交人工 | C：同左 |
|---|---|---|
| 0.90 / 0.10（现状） | 1 / 0 / 0 / 33 | 1 / 0 / 0 / 33 |
| 0.80 / 0.20 | 10 / 2 / 3 / 19 | 6 / 1 / 3 / 24 |
| 0.70 / 0.30 | 10 / 3 / 3 / 18 | 10 / 3 / 4 / 17 |
| 0.60 / 0.40 | 13 / 9 / 4 / 8 | 12 / 10 / 4 / 8 |

## 4. 发现的问题（已记入开发计划，待负责人决定）

1. **agent 阶段几乎全部交人工**：判官带证据复判后多数仍在中间带。可能的方向：agent 阶段单独的阈值（需要带上下文的标注数据来定，不能用案例池调）；或者改变 agent 的权限（例如判官概率在某个区间内由 agent 给出理由后处置），这会改变"判官定处置"的安全设计。
2. **快判看不到上下文**：回复、@ 他人的内容只看文本就被自动放行或处置，"上下文改变结论"的 10 对里有 4 条因此判错。可能的方向：带回复对象或 @ 的内容不在快判自动放行 / 处置，一律进 agent（会增加 agent 负载）。
3. **快判对"缺证"无感**：暗语、站外事件、指向不明的 @、父评论已删除的回复，快判按字面放行。父评论已删除这类信号是结构化的，可以在快判时识别。
4. **工具次数用完**：两组各有 2 条因 12 次工具上限交人工（agent 反复 judge / confirm / load_rule）。

## 5. 考虑不够全面的地方

- 每组只跑一次，agent 的随机性没有测；两组差别（工具调用、费用、时延）在一次运行里不能区分是否稳定。
- 案例池 80 条，其中只有 34 条进 agent，A/C 能比较的就是这 34 条。
- 预期处置由我（负责人委托）给出，公开样本的预期来自模型共识，不是人工金标准。
- 快判结果两组共用，所以快判层的问题对两组影响相同，也看不出 A/C 差异。
- 并发 8、同一中转站，时延受当时负载影响；C 在 A 之后跑。
- 截止时间重新起算的方式只适合这类离线试验。
