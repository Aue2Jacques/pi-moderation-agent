## 3. 考虑不够全面的地方

- **标签是模型辅助标签**，不是人工金标准；第三票 gemini 偏宽；三方不一致的 140 条没有进入二分类，其中可能集中了最难的样本。
- 本节只评快判；完整系统见第 4 节。
- **校准数据来自开发集试标样本**，测试集上的校准效果没有单独报（只报了分流）。
- 阈值（处置 0.90 / 0.92、放行 0.10）没有在测试集上调，也不应该在测试集上调。
- 每条只问一次；Jev 对同一输入的概率会抖 0.01–0.04（第 ① 阶段记录）。
- 测试集的"对抗扰动 / 拼音"一片实际是插空格（评测集计划 4.2）；注入组只有 27 条（多数注入家族在开发阶段用过，不进测试）。

## 4. 完整系统端到端（快判 + agent）【实测，一次】

**做法**：`scripts/build-test-cases.ts` 把测试集 3,002 条转成案例行，预期按平台结论（辱骂违规 → 下架、营销违规 → 限流、都允许 → 放行、其余 → 转人工：放行 2,042、下架 513、限流 299、转人工 148）；`run-ac.ts`（C 组提示，qwen3.8-flash，并发 10，`AGENT_DEADLINE_MS=7200000`，校准 `calib@e57aa6b1ae15`）跑一次（`data/ac/test-v1-e2e-b/`）。截止时间要放到 2 小时：默认 15 分钟时，1,200 多条 agent 审次在并发 10 下排不完，多数在排队中超时（2026-10-08 重跑时漏设一次，作废，见开发计划问题 12）。第一次运行因准备阶段只处理了 800 条而作废（开发计划已知问题 9）。

| 结果 | 条数 |
|---|---|
| 自动处置且与预期一致（correct_auto） | 1,735（快判 1,694，agent 41） |
| 预期转人工且转了人工（correct_human） | 101 |
| 预期可自动处置，结果转人工（human_instead_of_auto） | 1,013（全部是 agent 交人工） |
| 自动处置但与预期不同（wrong_auto） | 30（快判 27，agent 3） |
| 预期转人工却被自动处置 | 47（快判 44，agent 3） |
| 工具次数用完转人工（system_failure） | 76 |
| 自动完成覆盖率 | 60.4% |

- **快判**直接决定 1,765 条。27 条错误里：预期限流结果放行 12、预期下架结果放行 8、预期放行结果下架 7。44 条"预期转人工"被快判直接处置（放行 35、下架 8、限流 1）——这些是平台标签判为"不确定"的条目。
- **agent** 接 1,237 条：自己处置 47 条（放行 39、下架 5、限流 3；与预期一致 41、错误 3、本应转人工 3）；交人工 1,190 条（证据不足 1,110、工具次数用完 80）。平均每条 8.0 次工具调用。
- **时延与费用**：运行 56 分钟；agent 时延中位数 21.5 秒、最大 61.6 秒；全部物理请求 7.99 元（每条约 0.0027 元）；判官调用 5,300 次。
- **对账**：最终对账无问题；**账本与 Pi 的 pi.usage 对 1,237 个会话逐模型一致（差异 0）**——这是用量对账第一次在真实中转站数据上运行。

**这组结果的局限**：预期来自模型辅助标签；单次运行；agent 阶段的数字基本反映了"判官带证据后仍在中间带、agent 没有处置权"（开发计划问题 1），不是 agent 调查能力的上限；测试集条目都是独立文本（没有线程、没有账号历史），agent 能取到的上下文很少，所以 agent 阶段在这里本来就难有增益。

**这组估计的局限**：按"数据集组"加权，而数据集组不等于真实违规（例如辱骂组里平台判允许的约 40%）；组内结果比例来自一次运行、每组几十到几百条；没有包含对抗、注入两组；真实流量里回复和带账号历史的内容比例未知，而它们正是 agent 阶段可能有用的部分；人工处理的成本没有计入。
