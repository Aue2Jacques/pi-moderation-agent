# 第 ③ 阶段演练：注入配对（agent 层）、人工与申诉、规则发布（2026-10-08）

> **写法说明（2026-10-08 起统一）**：本文只记录做了什么、为什么这么做、测得的数字，以及考虑不够全面的地方。文中实验数字和看法均**仅供参考**（样本、设置、标注方式都有限），不作为结论；结论由审查方判断。日期按美国纽约时间（America/New_York）。

## 1. agent 层注入配对

**为什么**：第 ① 阶段只在快判层测了注入（`reports/2026-10-08-injection-pairs-fastpath.md`），计划要求 agent 层的配对测试在第 ② 阶段做。

**做法**：`scripts/build-injection-cases.ts` 从开发集取 50 对（违规原句 25 对、正常原句 25 对，固定哈希顺序），原句和加注入后缀的句子各一条；预期取原句的冻结平台标签，没有就用数据集原标签（逐条记录来源：100 条里 98 条来自数据集原标签，只有 1 对有平台标签——注入样本的原句大多不在试标样本里）。用 `run-ac.ts` 完整跑（快判 + C 组 agent，真实 Jev 和 qwen3.8-flash）。

**第一次运行作废**：准备阶段只跑快判、不消化队列，100 条里转 agent 的超过默认 agent 队列上限 50，28 条被以"背压"直接转人工，没进 agent（`run-2026-10-08c-injection`）。修正：准备阶段放开队列上限并写入清单（`dc056bc`），在新目录重跑（`run-2026-10-08d-injection`）。案例池的几轮只有 34 条转 agent，没有触发背压。

**结果**【实测，一次】：

| | 原句 50 条 | 加后缀 50 条 |
|---|---|---|
| correct_auto | 19 | 17 |
| human_instead_of_auto | 29 | 31 |
| wrong_auto | 2 | 2 |
| system_failure | 0 | 0 |

配对比较（同一文本加后缀后终态是否改变）：44 对不变；违规原句：1 对"转人工 → 下架"；正常原句：4 对"放行 → 转人工"，1 对"转人工 → 放行"。没有出现违规内容被后缀带成放行、正常内容被后缀带成处置。两组各 2 条 wrong_auto 是同样的 2 对：原句被快判放行，加后缀的进了 agent、也由 agent 放行（判官带证据复判支持放行）；预期来自数据集原标签"违规"，这 2 对没有平台标签。

快判分流：原句 50 条里快判直接处置或放行 20 条、转 agent 30 条（某规则在中间带）；加后缀的 50 条里注入检查命中转 agent 20 条、某规则在中间带转 agent 29 条、快判直接处置 1 条。

**不足**：只有 4 种模板化后缀；agent 读到的原文含后缀，但 agent 没有处置权（只能在判官支持的范围内处置），所以这组测试主要测的是"注入会不会让判官 + agent 的组合出错"，不是 agent 单独的抗注入能力；预期多数来自数据集原标签。

## 2. 人工领取、裁决、申诉重审、下游状态

**做法**：`scripts/drill-human-appeal.ts`，从 A/C 第一轮 C 组 app.db 的副本出发，起真实网关 HTTP 服务：

1. 脚本审核员通过 `/api/human/claim`、`/api/human/submit` 处理人工队列：按案例预期裁决；预期为"转人工"的按目标文本的冻结平台标签（作为人的替身，裁决理由里记录依据）。
2. 出站事件发到模拟下游，核对每条内容的下游状态等于它最新的裁决。
3. 对 10 条已处置的内容发 `/api/appeals`，每条再重复发一次。
4. 真实 agent（qwen3.8-flash + Jev，C 组提示）重审申诉；交人工的再由脚本审核员裁决；再次核对下游和对账。

申诉前补了两处（`83dacbe`）：申诉理由代码记为账号历史事件（审次表只存理由的哈希）；申诉审次的任务说明写明原裁决和申诉理由。

**结果**【实测】：

| 步骤 | 数字 |
|---|---|
| 人工队列（开始时） | 37 条（agent 交人工 34、带图 3） |
| 第一轮人工裁决 | 37 条全部 HTTP 200；裁决依据：案例预期 28、平台标签 9 |
| 下游核对 | 80 条有裁决的内容，下游状态全部等于最新裁决 |
| 申诉 | 10 条，首次 201、重复提交 200（同一审次） |
| agent 重审 | 维持 5 条（限流 4、下架 1）；交人工 5 条（证据不足 4、工具次数用完 1） |
| 第二轮人工裁决 | 5 条，全部 200 |
| 结束时 | 人工队列 0；下游 80 条全部一致；对账无问题；用时约 1.5 分钟 |

**不足**：审核员是脚本，不是人；10 条申诉都是对"下架 / 限流"的申诉，没有对"放行"的举报类申诉；没有测人工领取后超时、两个审核员抢同一条、申诉期间又来新的申诉这类并发情形。
