## 1. 做了什么

计划第 6 节：先找一个能稳定处理的负载 R，做稳定负载、短时超载、故障后恢复三项检查；接入、快判完成、完整审核完成分开报，排队时间和执行时间分开报。

| 项 | 值 |
|---|---|
| 系统 | 开发机上真实的 G、W 两个进程（`scripts/start.sh`），真实 Jev 和 qwen3.8-flash（中转站），校准 `calib@e57aa6b1ae15`，每个场景一个新库 |
| 配置 | W 准入上限 10，agent 队列上限 200（背压），快判批 16、并发 8；场景截止 60 秒（排队时间也算在内） |
| 输入 | 测试集 split-v1 的文本循环（三场景都没有用完一轮，没有重复文本）；泊松到达；账号轮换 2,000 个（不触发每账号每分钟 30 条的限流）；系统里没有判官结果缓存 |
| 脚本 | `scripts/loadtest.ts`：每 5 秒采样，到达停止后等排空（最多 15 分钟） |
| R 的选择 | 估算：快判约 16 条/秒，agent 约 0.5 条/秒，测试集约 40% 进 agent → 整体约 1 条/秒，取 R = 1 |

## 3. 观察

- **稳定负载**：接入和 agent 队列都不持续增长，0 超时。
- **短时超载**：快判不受影响（时延不变）；agent 队列峰值 62，没有到背压上限 200；超出能力的部分表现为排队超过 60 秒截止，被转人工（78 条，占进 agent 的 47%）。这是现在的降级方式——明确、不丢、不无限重试——但不是背压（背压没有触发）。到达恢复后 30 秒排空。
- **故障恢复**：W 被杀 31 秒期间队列积压到 18；重启后同时运行的 agent 不超过准入上限 10；被中断的审次恢复后完成，执行时间 95 分位升到 160 秒；19 条超时转人工；没有重复裁决，对账无问题。
- 三个场景里 agent 都几乎全部交人工（与 A/C 报告一致），所以"完整审核完成"的速度主要是"交人工"的速度。

## 4. 考虑不够全面的地方

- 每个场景只跑一次、5 分钟；R = 1 是估算后直接用的，没有逐级加压找上限。
- agent 队列上限设成 200，所以超载时没有测到背压（agent 队列满 → 快判直接转人工）这条路径；默认上限 50 下的超载行为没测。
- 截止 60 秒包含排队时间，超载时超时转人工的比例主要由它决定；没有测更长的截止。
- 只杀了 W，没有杀 G，也没有在 G、W 同时故障或中转站故障时测。
- 中转站和 Jev 的时延是当时的负载下的，可能随时间变化；开发机 4 核。
- 费用按价格表计，未与中转站账单逐条核对。
