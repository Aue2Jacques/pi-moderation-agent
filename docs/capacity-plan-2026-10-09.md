# 容量、高峰与空闲算力：方案（2026-10-09）

> 状态：**方案，后端都还没有实现**。GPU 调度部分（第 4.1 节加卡、第 6 节退卡）已被 [gpu-scheduling-plan-2026-10-09.md](gpu-scheduling-plan-2026-10-09.md) 取代：卡是公司自有的，不租不退，高峰时抢占离线任务的卡；切换耗时有实测。控制台"容量与调度"页（`packages/console/src/pages/Capacity.tsx`，模型在 `packages/console/src/capacity.ts`）是纯前端模拟，用来演示这套思路；页面上标了哪些数字是实测、哪些是假设。下面的数字凡未注明"实测"的都是估计或假设，仅供参考。

## 1. 要解决的问题

- 负责人的要求：用户发一条评论，几秒内审完，不能等十几二十秒；人工只处理很少一部分。
- 流量不平均：上下班、中午、晚上明显高于上班时段和深夜。
- 低峰时 GPU 空着，按小时计费。

## 2. 现在有什么（事实）

| 项 | 数字 | 来源 |
|---|---|---|
| 单卡快判吞吐（5060 Ti，kevfast 最快配置，关复问 + FP8） | 约 50 条/秒（HTTP），约 60 条/秒（引擎） | 实测，reports/2026-10-09-kev-inference-speed.md |
| 单条快判延迟 | 约 37–42 毫秒 | 实测，同上 |
| 复问开时单卡吞吐 | 约 32 条/秒 | 估计：由提速阶梯各步比例推算，没有单独测 |
| 回归评测 3,002 条（单卡） | 约 6 分钟 | 实测，v1 评测 manifest 的起止时间 |
| Kev 训练一版（单卡） | 约 2.7 小时 | 实测，v2s |
| 网关已有的背压 | agent 队列满 → 新的疑似直接转人工（S2'）；人工队列或未完成总量超限 → 暂停回放 | docs/dev-doc-v1.md §6.3 |
| 演示里转 agent 的比例（真实语料回放 Kev v1 分数） | 约 33–35% | 实测，开发机演示，docs/console-2026-10-09.md §6.5 |

## 3. 延迟：几秒内审完

做法分三层，越往后越慢、越少：

1. **快判**（Kev，约 40 毫秒；高负载时攒批，批 32 时一批约 0.5 秒）：大部分内容在这里结束。
2. **Kev 带证据复判（新增一层）**：快判落在中间带时，网关不先找大模型，而是直接并行取线程上下文和账号历史（现有的两个工具，确定性的），把证据放进 Kev 的状态里再判一次。能判定就带着证据 ID 处置；判不了才进 agent。
   - 预期：取证据加一次判官调用，估计 0.2–0.5 秒；agent 份额从约 15% 降到约 5%（两个数都是假设，需要实测）。
   - 前提：Kev 要学会读"评论 + 证据"格式。需要导出带证据的训练记录，训练一版，并在测试集上评测；证据格式要和 agent 看到的模型视图一致。
3. **LLM agent**：只处理剩下的难例。并发受模型服务限额约束。

体验上：作者发完立刻能看到自己的评论，别人要等审完才看到（现有的 `pendingVisibility` 机制）。

衡量：发布到审完的 p95，分快判、证据复判、agent 三段分别报；排队时间和执行时间分开报。

## 4. 高峰

### 4.1 能预测的高峰：提前加卡

- 按过去 7 天同一星期几、每 15 分钟一个点做流量曲线，目标卡数 = ⌈max(当前流量, 15 分钟后预测流量) × 1.2 / 单卡吞吐⌉。
- 新卡启动要加载模型、录 CUDA graphs，估计约 4 分钟；所以要提前，不能等排队了再加。
- 实现：一个控制进程读网关的 `/api/metrics`（接入速率、队列、p95），调云厂商的接口开关机器；新卡在 `/v1/models` 返回就绪后才加入路由。

### 4.2 不能预测的突发：临时加卡 + 降级

- 当前负载超过余量时临时加卡，但新卡有几分钟的空档，靠降级顶住。
- 降级梯子（每一档都用已有的开关，代价已有数据）：

| 档 | 做什么 | 效果 | 代价 | 现在要改什么 |
|---|---|---|---|---|
| 0 | 正常：复问开，先审后发 | — | — | — |
| 1 | 关复问 | 单卡吞吐约 1.5 倍 | 违规被自动放行 1.5% → 2.1%（v2s 测算，见速度报告第 10 节） | kevfast 现在用启动参数 `KF_CONFIRM` 控制，要改成按请求切换；策略的 `confirm_pass` 要跟着档位走 |
| 2 | agent 排不上的可疑内容先限流（仅作者可见），进补审队列 | agent 不再成为瓶颈 | 这些内容推迟可见 | 新的释放原因 `deferred`；补审队列表 |
| 3 | 信誉高的账号、低风险场景先发后审 | 进快判的量减少约三成（假设） | 少量违规短时可见 | 需要账号信誉分（见第 6 节） |

- 升档条件：快判利用率 > 90% 或开始排队 → 1；agent 进入速度超过并发上限 → 2；快判排队时间超过目标的六成 → 3。
- 降档：压力解除后持续 10 分钟逐档恢复，避免来回抖动。
- 这部分接在网关现有的背压控制循环上（`core.control.backpressure`）。

## 5. 负载均衡（多张判官卡）

- **判官池**：配置多个 kevfast 地址（如 `JEV_BASE_URLS`）。在 `packages/worker/src/judge-client.ts` 外面包一层路由。
- **选卡**：
  - 同一个规则版本的请求优先发到固定的卡上（按规则版本哈希）。原因：kevfast 的规则前缀缓存按卡存放，同一张卡上同前缀的请求才能攒成一批。
  - 那张卡排队比最空的卡多出一个阈值时，溢出到最空的卡。
  - 排队深度来自两处：kevfast `/v1/models` 的 `queued` 字段（定时拉取），以及客户端自己记的在途请求数。
- **健康检查**：连续 3 次失败或 `/v1/models` 超时就摘除；10 秒后放一个探测请求，成功了再加回来。
- **重试**：连接错误时换一张卡重试一次。判官调用有自己的 ID，重试不会重复记账。
- **规则灰度**：新规则版本先只路由到一张卡，比对后再放开（和现有的规则灰度配合）。

## 6. 低峰：空闲算力做什么

先保证在线流量有 15% 余量，剩下的卡按下面的顺序用；都没活了就退卡。

**同一张卡上分两个优先级**（kevfast 要改）：
- 请求带优先级。模型线程先取在线队列，在线队列空了才取离线请求。
- 离线批限制大小，在线请求最多等一个离线批（约 0.5 秒）。
- 要实测的是：离线任务跑满时，在线 p95 变了多少。

**任务清单**：

| 任务 | 用什么算力 | 产出 | 估计耗时 |
|---|---|---|---|
| 补审高峰时暂缓的内容 | Kev（+ agent） | 第 2、3 档留下的内容补上结论 | 看高峰积压多少 |
| 回归评测 | Kev | 每晚在测试集上重跑，分数漂移就报警 | 约 6 分钟/版（实测） |
| 规则回扫 | Kev | 规则改了以后，最近 N 天的内容按新规则重判 | 看量 |
| 影子评测 | Kev | 新模型 / 新规则在真实流量的副本上跑，和线上结论对比 | 看量 |
| Kev 增量训练（数据飞轮） | GPU 训练 | 用当天 agent 和人工的结论微调，第二天 Kev 能直接判的更多、转 agent 的更少 | 约 2.7 小时/版（实测，全量） |
| 校准重拟合 | CPU 即可 | 新一天的校准温度 | 分钟级 |

**除了 Kev 和大模型以外，还能拿来做的**：

| 任务 | 用什么 | 产出 |
|---|---|---|
| 向量聚类、团伙识别 | 句向量模型（如 bge 类）批量算全天评论的向量，聚类 | 同一套话术由多个账号发出的团伙（水军、引流），做成第二天快判前的拦截模板 |
| 账号信誉分 | 图特征（谁回复谁、注册时间、历史处置）+ 小模型 | 高峰时决定谁优先审、谁可以先发后审（第 3 档） |
| 图片里的文字识别 | OCR 模型 | 图片评论、头像、昵称里藏的联系方式 |
| 语音和视频 | 语音转文字、视频抽关键帧 | 语音评论、点播视频的审核；不急的放低峰做 |
| 近重复索引 | simhash / 向量索引重建 | 快判前的去重和缓存命中 |
| 对抗样本 | 规则生成（拼音、谐音、插符号、emoji） | 训练集增强，补对抗类的弱项 |
| 预热 | kevfast | 新规则版本的前缀缓存、CUDA graphs 提前录好 |
| 退卡 | — | 云上按小时计费，没有活就退掉本身就省钱；模拟里卡时比全天开满少约三到四成（模拟值） |

## 7. 演示页做了什么

- 一天压缩成约 3 分钟（每 125 毫秒一个模拟分钟，可 2×、4×）。早高峰、午间、晚高峰的流量曲线是假设的形状，峰值设为 300 条/秒。
- **GPU 池**：12 张卡，每张卡显示状态（在线 / 启动中 / 故障摘除 / 未租用）、利用率和批大小；空出来的卡显示为"离线任务"。
- **按钮**："突发热点"让流量在 3 分钟内涨到 2.2 倍并持续 25 分钟；"拔掉一张卡"后流量转给其他卡，8 分钟后那张卡下线检修。
- **开关**：按预测提前加卡、自动降级、Kev 带证据复判。关掉任何一个，都能看到延迟和降级时长的变化。
- **其他面板**：降级梯子显示当前档位；延迟图和今天的超目标分钟数；离线任务进度；调度日志；数字依据（实测 / 假设）。
- 模拟里 agent 并发上限设为 30 次/秒，所以不开"Kev 带证据复判"时，晚高峰 agent 进入速度会超过上限，触发第 2 档。

## 8. 不足

- 以上后端都没有实现，页面上的曲线都是模型算出来的，不是测出来的。
- 复问开时的单卡吞吐（32 条/秒）、新卡启动时间（4 分钟）、agent 份额（15% / 5%）、第 3 档的分流比例（30%）都是假设。
- "Kev 带证据复判"能不能判得准，要训练和评测后才知道；如果判不准，agent 份额降不下来。
- 只有一张卡，多卡路由和故障转移暂时只能用模拟或同卡多进程验证。
- 第 1 档关复问的漏放代价来自 v2s 的测算（关双确认 + 无复问），不是线上数据。
