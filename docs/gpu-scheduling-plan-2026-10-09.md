# 自有 GPU 卡池的统一调度：开发方案（2026-10-09）

> 状态：**方案，还没有实现**。第 2 节的切换耗时是在算力服务器（1 张 RTX 5060 Ti 16GB）上实测的（`python/kevfast/switch_bench.py`，单次实测，仅供参考）；其余数字是估计。控制台"容量与调度"页（`packages/console/src/capacity.ts`）按这份方案做了前端模拟。上一版方案 [capacity-plan-2026-10-09.md](capacity-plan-2026-10-09.md) 按"租卡、空闲就退"写，这一版改成负责人说的前提：**卡是公司自己的，一直在干活**；高峰时把正在跑离线任务的卡抢过来做判官，过了高峰再还回去。

## 1. 前提和目标

- 卡池：公司自有的 N 张卡（模拟里设 12 张），不按小时计费，不退卡。
- 每张卡任何时候都有一个角色：
  - **判官**：跑 kevfast，接在线审核。
  - **离线**：跑离线任务，如训练、向量聚类、OCR、规则回扫，或其他团队的批处理。
  - **切换中**、**故障**。
- 目标：
  1. 在线审核"发布到审完" p95 ≤ 3 秒（[capacity-plan](capacity-plan-2026-10-09.md) 第 3 节）。
  2. 高峰靠抢占离线卡顶住，尽量不降级。
  3. 卡池整体利用率尽量高。
  4. 被抢占的离线任务不丢进度。

## 2. 切换要多久（实测）

测法：`python -m kevfast.switch_bench <v2s 目录> <题目> <文本> 3`，每轮新开进程，卡上没有别的任务。判官为最快配置（规则前置、短问题、关复问、FP8、CUDA graphs）。

| 步骤 | 耗时 | 说明 |
|---|---|---|
| 新进程 `import torch` + 建 CUDA 上下文 | 1.7 s + 0.5 s | 实测，含在下一行里 |
| 启动判官进程 → `/v1/models` 就绪（加载模型、转 FP8） | 16.3–17.0 s（6 轮：16.75 / 16.25 / 17.04 / 16.56 / 16.67 / 16.64） | 实测 |
| 首个请求（为这组题录 CUDA graphs） | 11.5–12.7 s | 实测 6 轮 |
| 就绪后单条延迟 | p50 42 ms | 实测 |
| 判官显存 | 就绪 5.4 GB，服务中 6.3 GB | 实测（nvidia-smi） |
| SIGTERM → 进程退出 → 显存释放 | 0.6–0.7 s | 实测 |
| LoRA 断点：v2s 大小（6,500 万参数：bf16 权重 + 两份 fp32 Adam 矩）共 620 MB，写盘并 fsync | 1.6 s | 实测（代理：同大小的随机张量，没有真跑训练） |
| 读回断点到显存 | 0.56 s | 实测（同上） |
| 训练一个优化步 | 约 6 s（batch 4 × accum 2） | 实测，v2s 的 `training_metrics.json` |
| 训练峰值显存 | 12.3 GB | 实测，同上 |
| 推理类离线任务的一批 | 约 0.5 s | 实测（批 32 时每秒约 60 条） |
| 冷启动多出的读盘时间 | 约 3 s（底座 8.8 GB ÷ 3.0 GB/s） | 估计：直读（O_DIRECT）测得 3.0 GB/s；容器里不能清页缓存，"冷""热"两组实测其实都是热的 |

**由此算出的一次切换**：

| 切换 | 步骤 | 合计 |
|---|---|---|
| 推理类离线任务 → 判官 | 停在批边界 0.5 + 释放 0.7 + 启动 16.6 + 录图 12.0 | 约 30 s |
| 训练 → 判官 | 停在步边界 ≤ 6 + 存断点 1.6 + 释放 0.7 + 启动 16.6 + 录图 12.0 | 约 37 s |
| 判官 → 离线 | 停止接新请求、清空在途 ≈ 0.5（估计）+ 释放 0.7 + 任务启动约 20（估计） | 约 21 s |

**能看出的几点**：
- 一次切换在半分钟上下，所以只要提前几分钟决定，抢占离线卡来得及。
- 录 CUDA graphs 占了约四成。graphs 只降低单条延迟，批量时的吞吐不变（速度报告：批量路径的 graphs 只快约 2%）。所以可以先不录图就开始服务，空闲时再补录，这样约 17 秒就能上岗（见 M3）。
- 判官 6.3 GB 加训练 12.3 GB 超过 16 GB，这张卡上两者不能同时放下。24 GB 以上的卡可以让判官常驻、和训练共存，切换就只剩"暂停训练"（见第 6 节）。

## 3. 架构

```
           ┌──────────── 调度器（scheduler，新进程）────────────┐
 网关指标 ─▶│ 每 10 s：当前流量、排队、p95、预测曲线 → 目标判官卡数 │
           │ 选卡（抢占顺序）→ 下发角色                          │
           └───────────────┬───────────────────────────────────┘
                           │ HTTP
        ┌──────────────────┼──────────────────┐
   节点代理（每台机器一个）  ...                 节点代理
   每张卡：启动 / 停止判官，启动 / 暂停 / 恢复离线任务，上报状态
        │
   kevfast（判官）  ◀── 判官池路由（judge-client 外包一层）：规则版本亲和 + 最少排队 + 健康检查
   离线任务（遵守"可抢占"约定）
```

### 3.1 节点代理（node agent，Python，每台机器一个）

- 管本机每张卡上的进程，用 `CUDA_VISIBLE_DEVICES` 绑定。
- 对外接口：
  - `GET /cards`：每张卡的角色、进程、显存、心跳。
  - `POST /cards/{i}/role`：设为 `{judge | offline: <任务ID>}`，按第 2 节的步骤执行。每一步都有超时；超时就杀进程，上报故障。
- 判官就绪的判断：`/v1/models` 返回，并且跑通一条探测请求。
- 状态写在本地，重启后能接上正在跑的进程。

### 3.2 离线任务的"可抢占"约定

- 收到 SIGUSR1 后，在下一个安全点停下：
  - 推理类任务：当前这一批算完。
  - 训练：当前这个优化步算完，再存断点。
- 停下后写一个"已暂停"标记，然后退出。必须在 30 秒内完成，超时节点代理就直接杀掉。
- 用同样的参数重启时，从断点接着跑。推理类任务的断点就是"处理到第几条"。
- 定期上报进度，给调度器选卡用。
- **要补的**：`kev.train` 现在只有全量微调支持断点续训（`--resume`、`--save_every_steps`），LoRA 不支持。要加上：保存适配器、优化器状态、步数和数据游标，恢复后 loss 曲线要能接上。

### 3.3 调度器（scheduler）

- **输入**（每 10 秒一次）：
  - 网关 `/api/metrics` 的接入速率、队列、快判 p95。
  - 预测曲线：过去 7 天同一星期几、每 15 分钟一个点。
  - 各卡状态。
- **目标判官卡数** = ⌈max(当前流量 × 1.15, 10 分钟后预测流量 × 1.1) ÷ 单卡吞吐⌉ + 1 张热备。
  - 提前量取 10 分钟，远大于一次切换的约 37 秒，留出余量。
- **加判官时**按抢占顺序选卡，先停代价最小的：其他团队的批处理 → OCR / 回扫 → 聚类 → 信誉分 → 评测 → 训练。训练排最后，因为它要存断点，而且被打断的那个步要重算。
- **还卡时**：判官数比目标多 1 张以上，并且这张卡当判官已满 15 分钟（防止来回抖动），每 5 分钟最多还一张。还出去的卡领取最高优先级的待办任务。
- **故障**：节点代理报告故障，或判官健康检查失败，就从路由摘除，同时立刻按抢占顺序补一张。
- **记录**：每次切换的原因、各步耗时、被打断的任务，写进 app.db 新表 `gpu_switch`，控制台直接读。

### 3.4 判官池路由

和 [capacity-plan](capacity-plan-2026-10-09.md) 第 5 节相同，补充两点：
- 规则版本亲和。
- 只有就绪的卡才进路由；切换中的卡先停止接新请求，等在途请求清空。

### 3.5 判官卡上"混跑"离线推理（kevfast 改动）

- 请求加优先级字段。模型线程先取在线队列，在线队列空了才取离线请求；离线批限制大小，在线请求最多等一个离线批（约 0.5 秒）。
- 用途：判官卡有余量时，在同一个进程里跑补审、回扫、评测，不需要切换。

## 4. 高峰时怎么用

- **能预测的高峰**：提前 10 分钟按抢占顺序借卡，每张约 30–37 秒到岗。
- **突发**：按当前负载临时借卡，下一分钟就到岗。空档期由降级梯子第 1 档（关复问）顶住；卡池全部借完还不够，才升到第 2、3 档。
- **低峰**：判官卡逐张还给离线任务。零点平台自己的任务入队（评测、训练、聚类、信誉分、回扫、OCR），排在其他团队的批处理前面。

## 5. 开发路线（每一步都在真卡上验收）

| 里程碑 | 内容 | 验收（真测） |
|---|---|---|
| M1 kevfast 两级优先级 | 请求优先级、离线批大小上限、`/v1/models` 报两个队列 | 离线批处理跑满时，在线单条 p95 比空闲时多不超过一个离线批（约 0.5 s）；离线吞吐 ≥ 空闲吞吐的 80% |
| M2 LoRA 断点续训 | `kev.train` 支持 LoRA 的 `--resume`、`--save_every_steps`；响应 SIGUSR1 | 在随机一步发 SIGUSR1 → 退出时间 ≤ 一步 + 存断点；恢复后 loss 和不中断的同一次训练逐步对齐（同种子） |
| M3 判官快速上岗 | 先不录图就开始服务，空闲时按档补录 graphs；可选：FP8 权重预先转好存盘 | 启动到能接批量请求 ≤ 18 s（实测基线 16.6 s 就绪 + 12 s 录图）；补录期间在线 p95 不超过目标 |
| M4 节点代理 | 第 3.1 节；进程绑卡、角色切换、超时与故障上报 | 单卡上"训练 → 判官 → 训练"往返 20 次：每次各步耗时都记录；训练从断点恢复；没有残留进程和显存 |
| M5 调度器 + 判官池路由 | 第 3.3、3.4 节；`gpu_switch` 表；控制台读真实数据 | 回放一天的流量曲线（压缩时间），在单卡加一个模拟卡池上跑通；故障注入（杀判官进程）后补卡时间 ≤ 1 分钟 |
| M6 降级档位接入 | 第 1 档关复问改为按请求切换，策略 `confirm_pass` 跟着档位走；第 2 档 `deferred` 释放原因 | 档位切换时，在途请求不报错；补审队列在低峰清空 |

**依赖和顺序**：M1、M2、M3 互不依赖，可以先做；M4 依赖 M2、M3；M5 依赖 M4；M6 依赖 M5。

## 6. 不同卡型的做法

| 卡 | 判官 + 训练能否同卡 | 切换方式 |
|---|---|---|
| 16 GB（如 5060 Ti） | 不能（6.3 + 12.3 GB > 16 GB，实测） | 整卡切换，约 30–37 s |
| 24 GB（如 4090） | 估计可以（训练峰值随批大小变，需要实测） | 判官常驻，高峰时暂停训练（≤ 一步，约 6 s），判官直接接流量 |
| 80 GB（如 A100） | 可以 | 判官常驻 + MPS 或优先级流，训练只让出算力，不用停 |

## 7. 不足

- 切换耗时是在单张卡、单个进程、卡上没有别的任务时测的。多卡同时启动时，磁盘和 CPU 会互相抢，可能更慢。
- 页缓存不能清，所以没有真正冷启动的实测，只按读盘速度估了约 3 秒。
- 断点保存是用同样大小的随机张量测的，没有真跑训练再打断。
- "判官 → 离线"里任务启动的 20 秒是估计。
- 预测曲线和抢占顺序都还没有用真实流量验证。
- 卡池大小、平台峰值、各任务的工作量都是模拟用的假设。
