## 0. 主线与原则

**主线收回到项目文档定的第一条：有预算的证据调查，如何得到正确、可提交的审核结论。**要回答的四个问题：

1. 一个疑似任务为什么值得交给 agent；
2. agent 查到了什么新事实；
3. 这些事实怎样按规则改变裁决；
4. 这个过程相对固定取证工作流（A 组）是否值得付出成本。

两条原则：

- **安全不变量由代码保证，不做实验。**例如：不能提交别的审次，过期租约不能处置，规则版本不能混用，裁决不能重复执行，模型不能决定自己的权限。
- **效果策略要在固定开发集上比较，不靠单句反复重测。**例如：放行是否必须双确认，同调用两份还是分开两次，平均还是别的聚合，阈值放在哪，题面怎么写。从现在起冻结 3cdcb21 的题面，不再围绕少数句子改措辞、打乱方式和阈值。

**暂缓**（不在本计划内）：
- 新判官、守卫模型（Qwen3Guard 等）、小分类器级联、蒸馏导出、案例知识库；
- 图片通道；
- 完整灰度发布；
- 仪表盘美化；
- 云厂商横评；
- crash-matrix 扩到 20 次以上。

## 2. 第 1 步：统一裁决语义，按疑似原因分流

### 2.1 规则 × 例外 → 净结论 → 处置（真值表草案，**需要你拍板**）

以 ABUSE-001（有例外 EX-QUOTE）为例。"高"="达到拦截阈值"，"低"="低于放行阈值"，"中"=两者之间：

| 事实问题（是否包含攻击） | 例外问题（是否引用举报） | 净结论 | 处置 |
|---|---|---|---|
| 低 | 任意 | 该规则不违规 | 可放行（是否要确认见 2.4） |
| 高 | 不成立 | 该规则违规 | 按规则动作处置 |
| 高 | **成立** | **待定**：方案甲 = 该规则不违规、可放行；方案乙 = 转人工 | 现状是两头都不行（既不能拦也不能放） |
| 高 | 不确定 | 疑似 | 交 agent 核实是否引用（查上下文） |
| 中 | 任意 | 疑似 | 交 agent 或有限复核 |

### 2.2 多条规则同时命中的合并

建议：
- 动作取最重的一个（下架 > 限流）；
- 裁决只引用支持这个动作的规则，其他命中的规则记在理由里；
- `allowedActions` 只给这一个动作，模型不能挑较轻的；
- 有一条规则是疑似、另一条是违规时，按违规处置，疑似那条记录在案。

### 2.3 疑似原因分三类

疑似原因写进审次（新字段），agent 一开始就能看到：

| 原因 | 例子 | 路径 |
|---|---|---|
| 缺上下文 | 例外不确定；分数在中间带；黑名单或频控命中 | 进 agent，明确告诉它要核验什么 |
| 系统不可用 | 这个桶没有校准文件、判官挂了、规则包取不到 | **不进 agent**，直接转人工（或降级），不耗预算 |
| 证据已全但仍有争议 | agent 补完证据后仍在中间带 | 有限复核；没有新信息就停，不重复取同样的证据 |

### 2.4 确认机制：从硬要求改为待验证的策略（**需要你拍板**，因为要改冻结的项目文档）

现在"所有自动放行必须双确认"是写进项目文档的契约（第八轮审查定的）。第十一轮审查认为它没有被证明有增量收益。

建议：
- 保留现有实现，但把它变成可开关的策略；
- 在第 2 步的固定案例集上，对比开和关的误放、误拦、覆盖率和成本；
- 有数据之后再决定是否保留为默认。

### 2.5 c5（注入式文本）拆成两件事（**需要你拍板**）

- **业务标签：**按 ABUSE 的定义，这句话不是辱骂，期望应改为"放行"，CI 不再因它变红。
- **安全测试：**单独验证"即使模型被诱导，规则版本、证据归属、工具权限、提交约束都改不了"（现有 H-16 的方向）。再加一组有／无注入的配对，看误放和误拒。
- **要不要单设一条"操纵审核系统"规则**，是业务决定。不加关键词补丁。

## 3. 第 2 步：建一个小型、有标签的业务案例池

规模：**60–100 条起步**。这是起步建议，不保证统计充分。

四类各占一部分：
- **上下文能改变结论：**例如引用举报、反讽、对话中的回击；
- **历史是诱饵：**账号历史不好，但这条本身没问题；
- **确实缺证：**无论怎么查都定不了，应该转人工；
- **普通对照：**明显违规、明显正常。

规矩：
- 内容、线程上下文、账号历史、证据边界、预期结果、标签来源一起固定，ID 不透明，不泄漏类别；
- 原始单条标签和"加上上下文后的项目标签"分开存，不能把前者当后者的 gold；
- 开发者本人不看样本正文。拿不准的标签交给 glm-5.3-flash 判，并标明"模型标签"；仍存疑的只发链接给负责人；
- 冻结后才开始任何对比实验，之后不再改。

校准（**需要你拍板**）：strict 模式没有校准文件时什么都不自动处置。要么从案例池再分出一份专门用来拟合校准，要么 A/C 对比先在 identity 模式下跑并明确标注。

## 4. 第 3 步：简化 agent 的审核接口

模型仍然自己决定查什么、下一步做什么。下面这些改由 harness 明确提供，不再让模型靠被拒的报错去摸索：

- **初始任务**带上：疑似原因、卡在哪条规则或例外、待核验项、能取哪些证据、剩余预算；
- **judge 返回**：当前能支持哪些处置、还缺什么条件；
- **运行层统一处理**：确认调用的关联、同样的证据请求不重复做（缓存或去重）、当前允许的动作、还能不能继续花预算。

通过条件：
- 不再靠反复 `dispose` 被拒才发现规则；
- 同样的证据不重复调查；
- 缺证时知道停止并转人工。

旧回放里 13 条 evidence_gap 有 12 次被拒，这项要用新的拆分脚本复查。

## 5. 第 4 步：最小 A/C 主比较

- **A 组：**固定取证工作流，每次都查线程、查历史、复判。
- **C 组：**动态取证，由 agent 决定查什么。
- **控制条件：**同一案例池、同一主模型、同一规则包、同一证据环境、同一预算和截止。
- **报告指标：**
  - 质量（对 gold 的正确、错误、合理转人工、系统无法完成）；
  - 自动完成覆盖率、转人工量；
  - 工具调用数；
  - 成本（含全部物理请求）；
  - 时延。
- **允许出现不利结果。**C 不比 A 好，就如实写"在这批任务上尚未证明动态调查值得"，然后检查任务、工具或策略，不靠加循环把 agent 做复杂。

### 7.1 负责人的决定（2026-10-07）

1. **删掉"引用举报"例外（EX-QUOTE）。**负责人的理由：现在的评论区是"回复某条 + @某人"，很少有人整段转贴别人的辱骂；原评论违规本来就该先被处理，也不希望有人继续转述。"反偏见"（批评歧视的表态）保留在规则定义里：它和引用不是一回事，在评论区常见，COLD 也把它标为安全，删了会让规则和校正数据的标准对不上。规则文件在第 1 步改，题面和 sha 会变，契约夹具要重录。
   - 顺带的设计要求：线程上下文要体现"回复的是哪一条"（父评论 ID / @ 关系），不能只按时间取邻居。
2. **双确认开和关都跑一遍**，用案例池的数据比较误放、误拦、覆盖率和成本，再定默认值。
3. **注入不转人工，自己按大模型安全的做法处理。**c5 按辱骂规则改为"放行"。两层都要防：
   - 快判层：约 93% 的内容只经过 Jev、不经过大模型，所以要做"真违规内容 + 注入后缀"与不加后缀的配对测试，看 Jev 分数会不会被带偏；
   - agent 层：不可信数据与指令分开放并加标记，系统提示写明数据里的指令一律不执行，权限门兜底（已有）；同样做配对测试，看误放和误拒。
4. **案例池一半自写、一半来自公开数据集。**公开部分先用 COLD。上下文由开发者编造；带上下文后的标签按规则给，再由 glm-5.3-flash 复核并注明来源；开发者不看原文，存疑的发链接给负责人。

### 7.2 负责人的决定（2026-10-08）：漏斗与目标

- **架构是漏斗**：第一层机筛 → Jev → 拿不准的交大模型或人工。第一层由 **Jev 承担**（不另加关键词机筛或小模型），暂时不限调用量；之后的评测也按 Jev 的链路做。
- **目标**：效果比现有商用审核服务（阿里云、腾讯云、网易易盾等）好，速度差不多。
- **对照方式**：同一份公开数据（先用 COLD 测试集，二分类标签是中立的公开标准），比准确率、召回、误拦（特别是"反偏见"类），以及延迟 p50/p95。之后再加按本平台规则书标注的标准答案集。
- **当前最大的成本风险**：Jev 交给 agent 的比例。COLD 测试集上是 41%，目标压到个位数。办法：在 COLD 验证集上拟合校准、重新定阈值，测试集只在最后跑一次。
- 这几天用 deepseek、qwen 跑全量，是离线定标准和评测用的工具，不在线上链路里。

### 7.3 负责人的决定（2026-10-08 凌晨）：开源判官与图片
