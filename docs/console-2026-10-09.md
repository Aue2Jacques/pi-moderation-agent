# Web 控制台与演示模式（2026-10-09）

> 写法同 README：只写做了什么、为什么、怎么用和不足。演示模式下的概率、费用、耗时都是脚本产生的，**仅供演示**，不是评测数字。

## 1. 做了什么

一套用来现场演示、也能接真实判官使用的前后端：

- **后端**：在 G（gateway）现有 HTTP 服务上加了控制台 API（`packages/gateway/src/http.ts`、`console-api.ts`、`console-types.ts`）。审核逻辑一行没有另写：提交内容走原来的 `intakeInsert` → 快判 → 策略引擎 → `fastDispose` / `createSuspiciousReview`；agent 走 W 和 Pi durable 会话；人工裁决走 `core.submitRuling`（同一套提交检查）；申诉走 `createFollowupReview`。
- **前端**：`packages/console`，Vite + React + TypeScript，构建产物 `packages/console/dist` 由 G 直接托管在 `/`。
- **演示模式**：`packages/worker/src/demo.ts`，只替换两个模型接缝（判官、agent 模型），其余链路和真实模式相同。
- **启动器**：`scripts/console.ts`，一条命令构建前端、起 G 和 W、Ctrl-C 一起停。
- **演示流量（2026-10-09 第二轮）**：演示模式下 G 里有一个流量生成器（`packages/gateway/src/demo-traffic.ts`），持续产生自编的温和内容、一个限速的模拟审核员和偶发申诉，控制台像在运行的系统一样一直有数据变化。真实模式不创建它。
- **全局实时流（同上）**：`GET /api/events`（SSE），概览、审次列表、人工队列、申诉都靠它更新，不再定时轮询。
- **界面重做（同上）**：新布局与视觉、动画、窄屏适配、长文本处理；见第 3 节。

## 2. 怎么用

| 模式 | 命令 | 说明 |
|---|---|---|
| 演示 | `pnpm run demo` | 不读 `.env`，不需要任何 key 和 GPU。数据库在 `data/demo/`，每次启动清空（`--keep` 保留）。 |
| 真实 | `pnpm run console` | G、W 照常读 `.env`：`JEV_BASE_URL` / `JEV_API_KEY`（可以指向 Jev，也可以指向开源判官 kevfast），`RELAY_BASE_URL` / `RELAY_API_KEY`（agent 模型）；校准默认 strict。 |

打开 `http://127.0.0.1:8080/`。其他参数：`--port 9000`（W 用端口 +1）、`--build`（强制重新构建前端）、`--data dir`（演示数据库目录）、`--traffic N`（演示流量每分钟条数）、`--no-traffic`（不产生演示流量）。`--traffic` / `--no-traffic` 只能和 `--demo` 一起用，否则启动器直接退出。

演示流量的环境变量（只在 `DEMO=1` 时读取）：

| 变量 | 默认 | 含义 |
|---|---|---|
| `DEMO_TRAFFIC_PER_MIN` | 20 | 每分钟生成的内容条数，0 = 不生成（顶栏仍可再打开），上限 600 |
| `DEMO_SIM_REVIEWS_PER_MIN` | 6 | 模拟审核员每分钟最多处理几条任务，0 = 不启用 |
| `DEMO_SIM_MIN_AGE_MS` | 30000 | 模拟任务在队列里至少停留这么久才会被模拟审核员领取（留时间给人手动演示） |
| `DEMO_SIM_THINK_MS` | 4000 | 模拟审核员领取到裁决之间的间隔（这段时间里页面上能看到"已领取"） |
| `DEMO_HUMAN_CAP` | 8 | 未处理的模拟任务超过这个数时，模拟审核员不再等 `DEMO_SIM_MIN_AGE_MS` |
| `DEMO_APPEAL_PCT` | 3 | 每生成一条内容时，以这个百分比的概率对最近一条模拟的限流 / 下架发起申诉 |
| `DEMO_TRAFFIC_SEED` | 启动时间 | 随机种子（测试用，固定后序列可复现） |
| `LIVE_POLL_MS` | 500 | 全局实时流读计数器的间隔（真实模式也用） |

运行中也可以在顶栏的"模拟流量"控件里改速率（6 / 12 / 20 / 40 / 60 / 120 条每分钟）或暂停，对应 `POST /api/demo/traffic`。只开发前端时可以 `pnpm --filter @mod/console dev`（G 需在 8080 上运行，`/api` 会被代理）。

演示时的建议顺序：

0. 打开后先看**概览**：演示流量在跑，接入量、各路占比、最新审次、每分钟柱状图会持续变化；节奏太快或太慢用顶栏调。
1. **提交与追踪**：点"演示示例"。六条示例分别走出：自动放行、自动处置（限流）、agent 查上下文后放行、agent 查账号历史后下架、证据不足交人工、注入检查转 agent 后仍限流。右侧实时显示快判打分条、分流、agent 每一步工具调用、最终裁决。
2. **人工复核**：交人工那条出现在队列里；领取 → 看证据（原文默认隐藏，点开写审计）→ 裁决。提交检查拒绝的组合（例如下架但不引用规则）会显示错误码。
3. **申诉**：选一条已处置的内容发起申诉 → 新审次由 agent 重审，原裁决在新裁决形成前继续有效。
4. **概览**、**审次**、**规则与版本**按需展示。

## 5. 时间线怎么来的

只读 app.db（业务事实源），不读 W 的 `session.sqlite`：

- 快判打分：`judge_call`（`attempt IS NULL`）+ `judge_answer` 的原始与校准后概率；同次请求的打乱选项复问是确认主问的那条记录。比较线取审次绑定的规则版本（agent 阶段有 `agent_thresholds` 的用它）。
- 分流：审次的 `trigger`、`suspect_reason`、`release_reason`、快判裁决的理由码。
- agent 步骤：`tool_slot`（每次工具调用一行）按时间排；`load_rule` / 上下文 / 账号历史对应同类型、时间不早于它的 `evidence`；`judge` / `confirm` 经 `tool_request` 对到 `judge_call`；`dispose` 对到裁决或 `submit_rejected` 审计；`release` 对到 `release_reason`。
- 人工与申诉：`human_queue`、`feedback`、`synth_event`（申诉理由）。

为什么这样做：W 崩溃重启、换实例接管后，账本仍完整；G 不需要访问 W 的会话库；默认视图天然不含原文。

## 6. 演示模式怎么做的

- **判官**（`demoJudge`）：对 model view 文本和传入的证据做关键词打分。营销词 ≥2 个 0.995、1 个 0.55；明显辱骂词 0.995、轻度用词 0.55；带上下文复判时，父评论是自嘲 → 0.02，账号近 7 天被处置 ≥2 次 → 0.985；注入句式 0.95。每次主问同时返回打乱选项的复问（与 Jev 的同次复问相同形状），复问在主问附近有固定小偏移。
- **agent**（`demoAgentFactory`）：pi-ai 的 faux provider，每一步只看对话里的工具返回：读任务说明里卡在中间带的规则 → 取上下文 → 取账号历史 → 带两份证据复判 → 按判官返回的 `support.allowed_now` 处置；只缺复问就 confirm 一次；否则 release(evidence_gap)。处置被提交检查拒绝时转人工。步骤之间默认间隔 700 ms（`DEMO_AGENT_MS`），判官 350 ms（`DEMO_JUDGE_MS`），方便现场看。
- **校准**：用仓库里已拟合的温度文件（`calib/jev-latest/*.json`），按题目取 T；仓库只有评论场景的拟合，演示时弹幕、昵称也沿用这组 T。
- **费用**：价格表在真实表上加两项，脚本判官按 Jev 单价、脚本 agent 按 qwen3.8-flash 单价；token 数是 faux provider 按字符估算的。
- **账号历史**：启动时为 `u_repeat` 写入两条历史下架和一条警告（agent 查历史的示例用）。

### 6.1 演示流量

- **内容**：按比例混合 7 类自编的温和文本：正常 58%、营销 15%、辱骂 6%、轻度辱骂 8%、需看上下文（父评论自嘲）5%、需看账号历史 5%、注入 3%。按脚本判官的关键词，各类分别走：快判放行、快判限流、快判下架、agent 查证据后证据不足交人工、agent 带上下文复判后放行、agent 查历史后下架、注入检查转 agent 后限流。正常内容里有少量弹幕、昵称、帖子场景。账号按类别分配：轻度辱骂每条用新账号（没有历史可依），需看历史的类别用启动时写入两条历史下架的 `u_sim_repeat_1..4`。内容 ID 以 `sim-` 开头。间隔是均值 `60000 / DEMO_TRAFFIC_PER_MIN` 毫秒的指数分布，截在均值的 0.2–3 倍之间。
- **同一条写入路径**：生成器调用的入库、领取、人工裁决、申诉函数（`packages/gateway/src/console-actions.ts`）就是 HTTP 接口用的那几个，所以模拟内容和人手提交的内容走同样的快判、策略、agent、提交检查。
- **模拟审核员**：ID `sim-reviewer`，只在演示模式加进审核员名单。每秒看一次队列，只处理 `sim-` 开头的、没人领取的任务：任务排队满 `DEMO_SIM_MIN_AGE_MS` 后（或者未处理的模拟任务超过 `DEMO_HUMAN_CAP` 时不等）领取，过 `DEMO_SIM_THINK_MS` 后裁决，两次领取至少间隔 `60000 / DEMO_SIM_REVIEWS_PER_MIN` 毫秒。裁决：取这条审次判官给出违规概率最高的规则，概率 ≥ 0.5 时按审次 ID 的哈希约一半给该规则的默认处置，其余放行；裁决经过和人工相同的提交检查，被拒绝时放弃这条并放回队列。人手提交的内容、被真人领取的任务它都不碰。
- **申诉**：每生成一条内容，以 `DEMO_APPEAL_PCT`% 的概率对最近 15 分钟内一条模拟的、最新审次是限流或下架的内容发起申诉（理由代码随机），每条内容最多一次。
- **只在演示模式**：G 只在 `DEMO=1` 时创建生成器；生成器的构造函数遇到非演示模式直接抛错；`/api/demo/traffic` 在真实模式不存在。真实模式设置了 `DEMO_TRAFFIC_PER_MIN` 也不会生成内容（有测试）。
- **背压**：G 暂停接入时生成器跳过这一条，计入 `intake_skipped`。

## 8. 不足

1. **时间线是账本重建，不是会话原文**：工具参数是推出来的（复判的 rule_ids 从答案反推，证据按时间对应），agent 的自由文本输出和工具返回给模型的原文都没有展示；同一毫秒写入的多条同类证据按写入顺序匹配。
2. **SSE 是轮询**：每个连接每 250 ms 查一次 app.db、有变化才推；多客户端时查询量线性增长，没有做压测。
3. **演示模式不是模型**：判官是关键词规则，agent 是固定流程；能演示的只是"系统怎么流转、怎么拦"，不能说明真实模型的效果。弹幕、昵称借用评论场景的温度；费用是估算 token 乘真实单价。
4. **真实模式没有在本次跑过**：按约束没有调用付费或远程模型，真实模式只做了类型检查；它的判官、agent provider 和 `.env` 读取代码没有改动，只是挪进了 `DEMO` 分支之外。
5. **鉴权仍是单令牌 + 审核员名单**（`config/reviewers.json` 目前只有 `rev1`），没有角色分级；演示模式通过 `/api/config` 把令牌交给前端，真实模式由审核员手输、只存在本标签页的 sessionStorage。G 只监听 127.0.0.1，没有做 CSRF 防护。
6. **规则页只读**：影子检查、灰度、回退仍用命令行 `scripts/rules-release.ts`。
7. **口径**：概览的"自动完成率" = （快判处置 + agent 处置）/ 已结束审次，申诉审次也算在内，与 `/api/metrics` 的窗口指标口径不同。
8. **前端没有组件级单元测试**；交互靠浏览器冒烟覆盖主路径。浏览器冒烟没进 CI（需要 Chromium 和系统库；本机缺库，是用本地解压的库跑通的）。
9. **行为变化**：`/` 在有构建产物时变成新控制台（旧仪表盘在 `/legacy`）；`/api/human/submit` 对别人已领取的任务返回 409。
10. **演示流量是脚本**：文本只有几十条，按固定比例重复；模拟审核员的裁决规则是固定的（概率最高的规则 + 哈希），不代表真人的判断分布；申诉理由随机。人工队列"有界"靠模拟审核员的速率高于交人工的流入，速率设得比流入低时，模拟任务会一直堆到 `DEMO_HUMAN_CAP` 以上。
11. **长时间运行**：演示流量开着时 app.db 一直增长（默认每小时约 1200 条内容），没有清理；G 内存里的近重复索引也随之增长。每次 `pnpm run demo` 启动会清空库（`--keep` 除外）。
12. **全局实时流仍是轮询 app.db**：只是由多个连接共用一个轮询器；W 写库后要等下一次轮询（默认 500 ms，帧间隔至少 800 ms）才推出去。agent 运行中租约续期也会更新审次的 `updated_at`，所以运行中的审次会反复出现在增量里。
13. **列表重读**：审次列表、人工队列、申诉在计数变化时整页重读当前查询（最多每秒一次），不是按增量合并；切换筛选或页签时，新数据到之前仍显示旧列表。
14. **截图检查的覆盖面**：溢出检查只看 DOM 几何（裁切、溢出、超出视口），看不出重叠以外的排版问题，例如对齐和视觉层次，这部分是人工看截图；只在本机的 Chromium 和文泉驿微米黑字体下检查过，其他字体和浏览器没有看。
15. **浏览器测试仍不在 CI**（同第 8 条）。
