# Web 控制台与演示模式（2026-10-09）

> 写法同 README：只写做了什么、为什么、怎么用和不足。演示模式下的概率、费用、耗时都是脚本产生的，**仅供演示**，不是评测数字。

## 1. 做了什么

一套用来现场演示、也能接真实判官使用的前后端：

- **后端**：在 G（gateway）现有 HTTP 服务上加了控制台 API（`packages/gateway/src/http.ts`、`console-api.ts`、`console-types.ts`）。审核逻辑一行没有另写：提交内容走原来的 `intakeInsert` → 快判 → 策略引擎 → `fastDispose` / `createSuspiciousReview`；agent 走 W 和 Pi durable 会话；人工裁决走 `core.submitRuling`（同一套提交检查）；申诉走 `createFollowupReview`。
- **前端**：`packages/console`，Vite + React + TypeScript，构建产物 `packages/console/dist` 由 G 直接托管在 `/`。
- **演示模式**：`packages/worker/src/demo.ts`，只替换两个模型接缝（判官、agent 模型），其余链路和真实模式相同。
- **启动器**：`scripts/console.ts`，一条命令构建前端、起 G 和 W、Ctrl-C 一起停。
- **演示流量（2026-10-09 第二轮）**：演示模式下 G 里有一个流量生成器（`packages/gateway/src/demo-traffic.ts`），持续产生自编的温和内容、一个限速的模拟审核员和偶发申诉，控制台像在运行的系统一样一直有数据变化。真实模式不创建它。
- **全局实时流（同上）**：`GET /api/events`（SSE），概览、审次列表、人工队列、申诉都靠它更新，不再定时轮询。
- **界面重做（同上）**：新布局与视觉、动画、窄屏适配、长文本处理；见第 3 节。
- **第三轮（2026-10-09）**：演示流量改成每秒条数，档位 1 / 5 / 10 / 20 / 50，默认 10；实测上限见 6.3 节。概览加实时处理管线（点按真实分流比例流动）和近 5 分钟吞吐曲线。演示模式定期清理旧的模拟内容，累计数字从汇总表补回（6.4 节）。提交页可以传图片或点预置截图，演示模式下图片由脚本判官模拟，时间线显示缩略图和"视觉编码"步骤（6.2 节）。

## 2. 怎么用

| 模式 | 命令 | 说明 |
|---|---|---|
| 演示 | `pnpm run demo` | 不读 `.env`，不需要任何 key 和 GPU。数据库在 `data/demo/`，每次启动清空（`--keep` 保留）。 |
| 真实 | `pnpm run console` | G、W 照常读 `.env`：`JEV_BASE_URL` / `JEV_API_KEY`（可以指向 Jev，也可以指向开源判官 kevfast），`RELAY_BASE_URL` / `RELAY_API_KEY`（agent 模型）；校准默认 strict。 |

打开 `http://127.0.0.1:8080/`。其他参数：`--port 9000`（W 用端口 +1）、`--build`（强制重新构建前端）、`--data dir`（演示数据库目录）、`--rate N`（演示流量每秒条数）、`--traffic N`（同上，每分钟条数，旧写法）、`--no-traffic`（不产生演示流量）。这几个流量参数只能和 `--demo` 一起用，否则启动器直接退出。

演示模式的环境变量（只在 `DEMO=1` 时读取）：

| 变量 | 默认 | 含义 |
|---|---|---|
| `DEMO_TRAFFIC_PER_SEC` | 10 | 每秒生成的内容条数，0 = 不生成（顶栏仍可再打开）；`DEMO_TRAFFIC_PER_MIN` 是旧的每分钟写法，两者都设时以每秒为准 |
| `DEMO_MAX_PER_SEC` | 50 | 控制接口接受的最高速率；只在测容量时调高（`scripts/demo-capacity.ts` 用 1000） |
| `DEMO_SIM_REVIEWS_PER_MIN` | 6 | 模拟审核员每分钟至少能处理几条；实际产能随流入上调（6.1 节），0 = 不启用 |
| `DEMO_SIM_MIN_AGE_MS` | 30000 | 模拟任务在队列里至少停留这么久才会被领取（留时间给人手动演示） |
| `DEMO_SIM_THINK_MS` | 4000 | 每条模拟任务从领取到裁决的间隔（这段时间里页面上能看到"已领取"），多条可以同时在处理 |
| `DEMO_HUMAN_CAP` | 12 | 没人领取的模拟任务超过这个数时，模拟审核员不再等 `DEMO_SIM_MIN_AGE_MS` |
| `DEMO_APPEAL_PCT` | 0.5 | 每生成一条内容时，以这个百分比的概率对最近一条模拟的限流 / 下架发起申诉 |
| `DEMO_KEEP_CONTENTS` | 4000 | 库里保留最近多少条模拟内容，更早且已结束的定期删除（6.4 节）；0 = 不清理 |
| `DEMO_PRUNE_MS` | 5000 | 清理的间隔（G 和 W 各自按这个间隔跑） |
| `DEMO_PRUNE_QUIET_MS` | 60000 | 最近这么久内有变化的内容不删 |
| `DEMO_VISION_MS` | 300 | 脚本图片检查每次的耗时（代表视觉编码 + 图片题） |
| `DEMO_IMAGES_DIR` | `demo/images` | 预置截图所在目录 |
| `DEMO_TRAFFIC_SEED` | 启动时间 | 随机种子（测试用，固定后序列可复现） |
| `LIVE_POLL_MS` | 500 | 全局实时流读计数器的间隔（真实模式也用） |

演示模式还改了几项 G / W 的默认值（真实模式不变，环境变量仍可覆盖）：`INTAKE_BATCH` 96（真实 16）、`INTAKE_CONCURRENCY` 48（8）、`INTAKE_MS` 200（500）、`QUEUE_AGENT_MAX` 200（50）、`ADMIT_MAX` 128（10）、`ADMIT_MS` 500（1000）、`SIMHASH_MAX` 2000（50000，近重复索引每条内容线性扫一遍，演示文本重复度高，索引大了每条都要比几万次）。

运行中在顶栏的"模拟流量"控件里切换档位（1 / 5 / 10 / 20 / 50 条每秒）或暂停，对应 `POST /api/demo/traffic`；窄屏时档位是下拉框。只开发前端时可以 `pnpm --filter @mod/console dev`（G 需在 8080 上运行，`/api` 会被代理）。

演示时的建议顺序：

0. 打开后先看**概览**：顶部是"每秒处理"和处理管线，点按真实分流比例从接入流向自动放行、自动处置、agent、人工；下面是吞吐曲线、累计数字、每分钟柱状图、最新审次。节奏用顶栏档位调，想看高并发切到 50。
1. **提交与追踪**：点"演示示例"。六条示例分别走出：自动放行、自动处置（限流）、agent 查上下文后放行、agent 查账号历史后下架、证据不足交人工、注入检查转 agent 后仍限流。右侧实时显示快判打分条、分流、agent 每一步工具调用、最终裁决。再点"图片示例"里的三张评论截图，或拖入任意一张图片（6.2 节）。
2. **人工复核**：交人工那条出现在队列里；领取 → 看证据（原文默认隐藏，点开写审计）→ 裁决。提交检查拒绝的组合（例如下架但不引用规则）会显示错误码。
3. **申诉**：选一条已处置的内容发起申诉 → 新审次由 agent 重审，原裁决在新裁决形成前继续有效。
4. **概览**、**审次**、**规则与版本**按需展示。

第三轮的界面改动：

- **实时处理管线**（`packages/console/src/Flow.tsx`）：节点是接入 → 判官快判 → 自动放行 / 自动处置 / agent 查证据 → agent 处置 / 人工，另有申诉进 agent 的虚线。每个节点显示累计数、每秒速率（近几帧算出）、占比或处理中数量，数字滚动到新值。点的来源是相邻两帧之间累计计数器的增量（快判完成数、各路数、agent 处置 / 交人工、申诉数），在到下一帧之前均匀放出；快判之后的点比进快判的点晚一段路程出发，看起来是接着走。超过每秒约 90 个点时一个点代表多条，左下角写"每个点约 N 条"。连线画在一张只在尺寸或主题变化时重画的画布上，点画在另一张画布上，一个 requestAnimationFrame 循环、每条通道一次填充。宽度不足 600 px 时改成从上到下的布局。减少动态效果时只画连线，不放点，数字直接跳。
- **吞吐曲线**：SVG，近 300 秒每秒快判完成条数，数据来自 G 内存（`gateway.flow()`，不受清理影响），悬停看某一秒。
- **版式**：标题、卡片圆角与阴影、数字字号层级调整，数字一律等宽并带千分位；深色模式的底色和边框重新调过。
- **高频下的渲染**：滚动数字的每一帧直接改文本节点，不经 React 重渲；概览的最新审次最多每 1.5 秒换一次；审次列表的行组件做了记忆化，最多每 2 秒重读一次，有"跟随最新 / 已暂停刷新"开关（翻到第二页起自动停住）；一次新出现超过 8 行时不逐行高亮；人工队列、申诉列表最多渲染 100 行；每分钟柱状图去掉了高度过渡（当前这一分钟每帧都在长）。

界面（第二轮重做）：

- **布局**：左侧导航（分组；底部显示规则 / 校准 / 模型版本，长值换行不截断），顶栏是面包屑、实时流连接状态、模式、演示流量控件、审核员、主题切换；每页有标题和一句说明。宽度 ≤ 900px 时侧栏收成抽屉（左上角菜单按钮），≤ 640px 时审次、人工队列、申诉、版本等表格改成每行一张带列名的卡片，打分行重排。
- **视觉**：平面面板 + 细边框，一个强调色，状态色只用在有含义的地方；不用渐变、发光；图标只留在导航和少数按钮上；数字等宽。
- **长文本**：ID 中间省略，悬停看全文、点一下展开；长文本按行截断时同样有悬停全文和点击展开；版本号、原因、工具名和返回值、规则说明一律换行而不是截断。
- **模拟数据标记**：演示流量的内容 ID 以 `sim-` 开头，出现的地方都带"模拟"标；模拟审核员 `sim-reviewer` 的领取和裁决也带这个标。
- **实时**：概览数字（滚动到新值）、最新审次（新行滑入并短暂高亮）、审次列表 / 人工队列 / 申诉（有变化才重读，新行高亮）、状态与结论徽标（值变化时过渡）。
- **动画**：页面切换淡入；打开时间线时 agent 步骤依次出现，实时新增的步骤到达即出现；快判打分条从 0 增长后标记落位；柱状图、占比条增长。都是 CSS 过渡和少量 requestAnimationFrame（数字滚动），没有引入动画库。系统设置了"减少动态效果"时动画和过渡关闭，数字直接跳到新值。原有 `/human` 页保留，旧仪表盘移到 `/legacy`（没有构建产物时 `/` 仍是旧仪表盘）。

### 3.1 导航与原文显示（2026-10-09 晚）

- **原文直接显示**：负责人担心"查看原文与证据（受限）"按钮让人不敢点。演示模式下审次详情和人工复核页直接显示原文与上下文证据，不再有按钮。实现是自动读取受限视图（`useOpenView`），每次时间线变化重读一次；G 照常把每次读取写进审计。真实模式不变：仍要审核员身份、确认，并写审计。
- **找得到功能**：负责人担心访客不知道左侧有菜单、随便点两下就走。
  - 概览页顶部曾加过"首次访问建议按以下顺序浏览"的四张卡片，负责人要求删除，已去掉。
  - 每页末尾加"下一站"，顺序为：概览 → 提交与追踪 → Agent 与 Harness → 容量与调度 → 人工复核 → 规则与版本。
  - 手机（≤ 900 px）底部加标签栏：概览、提交、Agent、调度、全部（打开菜单）。

### 3.2 去掉费解的小模块（2026-10-09 晚）

负责人认为动画和整体结构可以，问题在于很多让人费解的小模块。按"每个模块只回答一个一眼能看懂的问题"整理：

- **概览**：
  - 顶部数字只留每秒处理、单条用时、自动完成率。
  - 指标卡改为 4 个，每个配一句说明。
  - 删除与流水线重复的"各路占比""当前处置结果"。
  - 用时、转人工原因、申诉合并为一块；用时表头改为"中位数 / 较慢的 5%"。
- **系统状态（新页 `#/system`）**：网关实时指标、模拟流量明细、当前版本，从概览移到这里。侧栏底部的版本哈希默认折叠。
- **打分条**：
  - 默认一根条、一个点、一句结论，如"无法确定，交给 agent"。
  - 主问、复问、原始分点"主问、复问与原始分"再展开。
- **Agent 页**：9 项约束默认只显示名称和防范的问题，点开后才显示实现与验证。
- **容量页**：实时部分在前；切换耗时、实施路线、数字依据放到页底。
- **术语**：
  - `labels.ts` 的 `GLOSSARY` 是唯一来源，新增术语表页 `#/glossary`。
  - 各页说明里的关键词加虚线下划线，点击即弹出解释；手机上改为底部弹出。
- **导航分组**：了解系统（概览、提交与追踪、Agent 与 Harness、容量与调度）、审核后台（人工复核、申诉、审次、规则与版本）、其他（系统状态、术语表）。
- 顶栏流量档位保留不动（负责人要求）。

### 3.3 Agent 页改用真实运行记录（2026-10-09 晚）

- **为什么**：负责人看到回放里只有一两条、而且是演示程序自带的示例句，像是没做 harness；要求至少 300 条真实数据、各类别均衡。
- **记录集**：
  - `scripts/build-harness-set.py` 从测试集取 300 条真实文本，6 类各 50 条：正常、易误判、辱骂、变形辱骂、营销引流、注入。
  - 每类优先选冻结测试运行里判官拿不准的条目，也就是会转给 agent 的那些。
  - 用 `scripts/run-ac.ts prepare / run C` 跑一遍：真实快判 Jev，真实 agent qwen3.8-flash，正式 harness。
  - 结果存成单独的 app.db，文本只放在开发机上。
- **接口**：
  - 设置 `HARNESS_RECORD_DB` 后，`GET /api/harness/record` 返回汇总：按类别分流、工具调用与拦截原因、提交校验错误码、外部请求与重试、模型调用与 token、预算用量、重新接手与追问收尾、agent 用时，以及会话列表。
  - `GET /api/harness/record/contents/:id` 返回单个会话的完整时间线。实现在 `packages/gateway/src/harness-record.ts`，只读。
- **页面**：
  - 回放改为固定高度的信息流，新步骤从底部出现、旧的往上滚，下方内容不再跟着跳动。
  - 可按类别筛选，统计数字跟随所选类别。
  - 新增"Harness 在这次运行中做了什么"面板。每项约束卡片上直接显示"本次运行"的实际数字。
  - 没有记录库时退回回放演示环境的实时会话。
- **演示 agent 的习惯**：只作用于演示流量。约 15% 的会话会在取证前先提交下架，被提交校验拒绝；约 10% 会重复获取上下文，拿回已有证据。这样演示回放里也能看到 harness 的拦截。

### 3.4 Agent 页统计改读主库，演示语料带上下文（2026-10-10）

- **为什么**：负责人担心单独的运行记录会和概览等页面的数字冲突，要求数据多、像真的、彼此一致。
- **一个数据源**：
  - 演示模式且有语料时，`/api/harness/record` 不再读单独的记录库，而是读控制台自己的 app.db（`HarnessRecordStore` 的 live 模式，只读连接，10 秒重算一次，只看 `sim-` 内容）。
  - 类别按评论文本在语料里查到的切片定。
  - 概览、审次、人工复核和 Agent 页读的是同一批行。
- **演示语料带上下文**：
  - `scripts/synth-context.ts corpus` 给语料每条生成父帖、0–3 条同线程较早回复和账号历史（比例与 3.3 节相同；3,001 条中 2,999 条成功）。
  - 演示流量发出这条评论时，用 `contextInsert` 写入父帖和回复，用 `synthEventInsert` 写入该账号的既往处置。带历史的条目用独立账号。
  - agent 的 `get_thread_context` / `get_account_history` 因此能取到真实的行。清理时这些行随内容一起删除。
- **页面说明**：演示语料带上下文时，Agent 页注明以下几点，口径与概览一致：
  - 评论取自测试集；父帖、回复与账号历史按合成方案生成。
  - 分数为 Kev-4B 实测回放。
  - agent 决策为脚本。
- **不足**：
  - 合成的上下文不影响演示判官的打分（演示判官回放的是只看评论的实测分数），也不影响脚本 agent 的结论。所以上下文只让回放里的取证步骤有内容，不代表 agent 用上下文改变了判断。
  - 真实模型的三轮运行结果只记在 `data/harness/`（开发机）和本节以外的说明里，不上网页。

## 5. 时间线怎么来的

只读 app.db（业务事实源），不读 W 的 `session.sqlite`：

- 快判打分：`judge_call`（`attempt IS NULL`）+ `judge_answer` 的原始与校准后概率；同次请求的打乱选项复问是确认主问的那条记录。比较线取审次绑定的规则版本（agent 阶段有 `agent_thresholds` 的用它）。
- 分流：审次的 `trigger`、`suspect_reason`、`release_reason`、快判裁决的理由码。
- agent 步骤：`tool_slot`（每次工具调用一行）按时间排；`load_rule` / 上下文 / 账号历史对应同类型、时间不早于它的 `evidence`；`judge` / `confirm` 经 `tool_request` 对到 `judge_call`；`dispose` 对到裁决或 `submit_rejected` 审计；`release` 对到 `release_reason`。
- 人工与申诉：`human_queue`、`feedback`、`synth_event`（申诉理由）。

为什么这样做：W 崩溃重启、换实例接管后，账本仍完整；G 不需要访问 W 的会话库；默认视图天然不含原文。

## 6. 演示模式怎么做的

- **判官**（`demoJudge`）：对 model view 文本和传入的证据做关键词打分。营销词 ≥2 个 0.995、1 个 0.55；明显辱骂词 0.995、轻度用词 0.55；带上下文复判时，父评论是自嘲 → 0.02，账号近 7 天被处置 ≥2 次 → 0.985；注入句式 0.95。每次主问同时返回打乱选项的复问（与 Jev 的同次复问相同形状），复问在主问附近有固定小偏移。
- **agent**（`demoAgentFactory`）：pi-ai 的 faux provider，每一步只看对话里的工具返回：读任务说明里卡在中间带的规则 → 取上下文 → 取账号历史 → 带两份证据复判 → 按判官返回的 `support.allowed_now` 处置；只缺复问就 confirm 一次；否则 release(evidence_gap)。处置被提交检查拒绝时转人工。步骤之间默认间隔 400 ms（`DEMO_AGENT_MS`，2026-10-09 晚从 700 调小，一次 agent 审核约 2.5 秒），判官 350 ms（`DEMO_JUDGE_MS`），方便现场看。
- **校准**：用仓库里已拟合的温度文件（`calib/jev-latest/*.json`），按题目取 T；仓库只有评论场景的拟合，演示时弹幕、昵称也沿用这组 T。
- **费用**：价格表在真实表上加两项，脚本判官按 Jev 单价、脚本 agent 按 qwen3.8-flash 单价；token 数是 faux provider 按字符估算的。
- **账号历史**：启动时为 `u_repeat` 写入两条历史下架和一条警告（agent 查历史的示例用）。

### 6.1 演示流量

- **内容**：按比例混合 7 类自编的温和文本：正常 66%、营销 12%、辱骂 5%、轻度辱骂 4%、需看上下文（父评论自嘲）5%、需看账号历史 5%、注入 3%（第三轮把交人工的轻度辱骂从 8% 降到 4%，高速率下人工队列不至于被灌满）。按脚本判官的关键词，各类分别走：快判放行、快判限流、快判下架、agent 查证据后证据不足交人工、agent 带上下文复判后放行、agent 查历史后下架、注入检查转 agent 后限流。正常内容里有少量弹幕、昵称、帖子场景。账号按类别分配：正常内容从 5000 个账号里抽（G 对单个账号限每分钟 30 条，账号池小了，高速率下正常内容会因频控变成疑似），轻度辱骂每条用新账号（没有历史可依），需看历史的类别用启动时写入两条历史下架的 `u_sim_repeat_1..4`。内容 ID 以 `sim-` 开头。到达是每秒 `DEMO_TRAFFIC_PER_SEC` 条的泊松过程：每 100 ms 醒一次，把到达时间已到的内容都放进接入队列；一次最多 400 条，落后太多（例如进程卡顿）时跳过而不是补发。
- **同一条写入路径**：生成器调用的入库、领取、人工裁决、申诉函数（`packages/gateway/src/console-actions.ts`）就是 HTTP 接口用的那几个，所以模拟内容和人手提交的内容走同样的快判、策略、agent、提交检查。
- **模拟审核员**：ID `sim-reviewer`（一个 ID 代表一组人），只在演示模式加进审核员名单。每秒看一次队列，只处理 `sim-` 开头的、没人领取的任务：任务排队满 `DEMO_SIM_MIN_AGE_MS` 后（或者没人领取的模拟任务超过 `DEMO_HUMAN_CAP` 时不等）领取，过 `DEMO_SIM_THINK_MS` 后裁决，多条可以同时在处理。产能（每分钟可领取条数）= max(`DEMO_SIM_REVIEWS_PER_MIN`, 1.3 × 近 1 分钟进入人工队列的模拟任务数 + 2 × 超出上限的条数)，按令牌桶发放，所以速率高低都让人工队列停在上限附近：有东西看，但不会越积越多。裁决：取这条审次判官给出违规概率最高的规则，概率 ≥ 0.5 时按审次 ID 的哈希约一半给该规则的默认处置，其余放行；裁决经过和人工相同的提交检查，被拒绝时放弃这条并放回队列。人手提交的内容、被真人领取的任务它都不碰。
- **申诉**：每生成一条内容，以 `DEMO_APPEAL_PCT`% 的概率对最近 15 分钟内一条模拟的、最新审次是限流或下架的内容发起申诉（理由代码随机），每条内容最多一次。
- **只在演示模式**：G 只在 `DEMO=1` 时创建生成器；生成器的构造函数遇到非演示模式直接抛错；`/api/demo/traffic` 在真实模式不存在。真实模式设置了 `DEMO_TRAFFIC_PER_MIN` 也不会生成内容（有测试）。
- **背压**：G 暂停接入时生成器跳过这一条，计入 `intake_skipped`。

### 6.2 图片（演示模式下"假装有"，标明是模拟）

- **怎么用**：提交页的"图片"一栏拖入或选择一张图片（可同时填文字），或点"图片示例"里的三张评论截图。示例图是 `scripts/demo-images.ts` 用本机 Chromium 把自编的温和评论渲染成 480 px 宽的"评论截图"，放在 `demo/images/`（字体用的是本机找到的文泉驿微米黑，仓库里只有渲染出的图片，没有字体文件）。页面上的说明："真实识图：开源判官 Kev-4B 零训练读截图，测试集 200 张渲染截图上辱骂 AUROC 约 0.93、营销约 0.997，单卡约 28–31 张/秒（实测，见 reports/2026-10-09-kev-inference-speed.md 第 11 节）"。
- **走的是已有的图片通道**：图片按内容哈希存进图片存储（演示模式在演示数据目录下的 `images/`），内容的 `image_refs` 指向它；快判照常在问完文字题后经 `image.ts` 的 `ImageStore` + `ImageChecker` 问场景的 `image_check` 题（主问 + 复问），答案记在内容的判官调用上，再进同一个策略引擎。演示模式换上的只有两样：
  - 图片检查用脚本（`demo-images.ts` 的 `demoImageChecker`，模型名 `vision-scripted`）：预置截图按哈希认出，给固定概率（正常 0.02、营销 0.97〔图里有联系方式〕、辱骂 0.03〔不涉及武器、血腥、二维码〕）；其他任何图片给 0.5，落在中间带。演示的校准对 `image_check` 用 T=1（真实模式没有这项拟合时仍是未校准，不会自动决定）。
  - 脚本判官读预置截图的已知内容：判官请求带着内容 ID，演示判官查到这条内容挂的是哪张预置截图，就把截图上的那句话和附带文字一起打分，所以三张截图的辱骂、营销分数各不相同（代表 Kev 直接读截图答规则题）。随手上传的图片没有已知内容，规则分只看附带文字。
- **结果**：正常截图 → 自动放行；营销截图 → 自动限流；辱骂截图（账号 `u_repeat`，近期两次被下架）→ 辱骂在中间带，转 agent，agent 取账号历史后复判，下架；随手上传的图片 → 图片检查 0.5，转 agent，agent 没有图片通道、不能放行图片内容，取完上下文和历史后交人工（证据不足）。
- **一处只在演示模式打开的分流**：真实模式下带图片、落在中间带的内容直接交人工（`image_review`，agent 看不到图）。演示模式给快判传 `imageToAgent`，让它先进 agent 再交人工，能看到 agent 那一段；真实模式不传，判定逻辑没有改。
- **时间线**：接入阶段写"N 张图"；多一个"视觉编码"阶段和一段"视觉编码"卡片，显示缩略图、`image_check` 的主问 / 复问打分条（按场景的图片放行线 0.1 / 处置线 0.9）；事件流里有"视觉编码 + 图片打分"一条。演示模式下时间线上写明"演示模式：图片由脚本判官模拟（预置截图按已知内容打分，其他图片给中间带概率）"。
- **图片属受限内容**：时间线的默认视图只有图片的 ref 和是否预置。预置截图从公开的示例地址显示；本标签页自己上传的图片用浏览器里的本地副本显示；其他图片要点"查看图片"，经受限接口取（审核员令牌 + 确认，写审计）。受限视图里自动取。
- **真实模式**：设了 `IMAGE_DIR` 才接收图片（存到这个目录）；同时设了 `IMAGE_MODEL` 时走已有的 relay 图片检查，没设时按原逻辑交人工（`image_unsupported`）。没设 `IMAGE_DIR` 时提交图片返回 400 `E_IMAGE_DISABLED`。这条路径有 harness 测试，但真实的图片模型没有跑过（不调用付费或远程模型）。

- **上限**：快判一侧在每秒约 61 条到顶（70 档时接入队列 2 分钟涨到 1200 条）；agent 一侧每秒约 10 条审次（W 同时最多 128 个会话，每条脚本 agent 审次约 5–7 秒），约 17.5% 的内容进 agent，对应每秒约 60 条流量。60 档 2 分钟内还跟得上，但 agent 队列峰值到 108，再高就会顶到 G 的 agent 队列上限（200）开始背压。控制台的最高档定为 **50**，留约 17% 余量；默认档 **10**（每秒 10 条，人工队列保持在 10–20 条）。
- **早先的问题**：本轮最初 W 同时最多 64 个会话，50 档的长时间运行里 agent 队列一直涨，涨到 G 的上限后，新的疑似内容（包括手动提交的示例）因背压直接交人工；把演示模式的 `ADMIT_MAX` 调到 128 后上表 50 档稳定。
- **数据库大小**：开了清理（保留 4000 条模拟内容）后 app.db 稳定在约 50 MB、session.sqlite 约 23 MB，不再随时间增长（审计表除外，见 6.4 节）。另跑了一次 50 档 10 分钟（先等 30 秒）：生成 49.9、快判 49.92、agent 8.77、人工 2.06 条/秒，接入队列 39 → 21（峰 130），agent 队列 42 → 40（峰 116），人工队列 37 → 25，app.db 57.3 MB、session.sqlite 23.7 MB，跟得上；G 内存 165 MB，W 内存 269 MB（比 2 分钟时的 242 MB 还在缓慢上涨，原因没有查，见第 8 节）。
- **怎么复现**：`node --experimental-strip-types --no-warnings scripts/demo-capacity.ts --tiers 10,20,30,40,50 --secs 120 --warm 30`；测 50 以上的档位时脚本自动把 `DEMO_MAX_PER_SEC` 调到 1000。

### 6.4 清理与保留（演示模式）

- **为什么**：第二轮实测，每条内容在 app.db 里约 19 KB（审次、判官调用和答案、证据、投递记录、审计等），每个 agent 会话在 Pi 的 session.sqlite 里约 22 KB；每秒 10 条时一小时就是几百 MB，而且每帧统计要扫的行越来越多。
- **G 这一半**（`packages/gateway/src/demo-retention.ts`）：每 `DEMO_PRUNE_MS`（5 秒）检查一次，模拟内容超过 `DEMO_KEEP_CONTENTS`（4000）条时，删掉最早的、已经结束的一批（每次最多 600 条）：所有审次都已处置，没有未投递的出站事件，最近 `DEMO_PRUNE_QUIET_MS`（60 秒）内没有变化。删除连带它们的审次、裁决、判官调用和答案、证据、工具记录、人工任务、标注、出站与下游记录、申诉事件、父评论。人手提交的内容不删。
- **统计连续**：删除前，在同一个事务里用和统计相同的查询（`statCounts`，限定在这批内容上）算出它们贡献的计数——内容数、已快判、审次数、各路、当前有效处置、转人工原因、agent 处置 / 交人工、人工已完成、申诉与改判、费用、近 30 分钟每分钟各路——加进 `console_rollup` 表；`/api/stats` 和实时流 = 库里现有的 + 汇总表。删除和加汇总在同一事务里，数字不会少算也不会重复。耗时分位数和"近 2000 条"类的统计只看库里剩下的。汇总表只在演示模式创建，真实模式没有这张表（有测试）。
- **W 这一半**（`packages/worker/src/demo.ts` 的 `DemoSessionRetention`）：同样间隔，删掉 Pi 会话库里已经没有审次指向的会话（G 删了对应审次）、本进程不再持有、所有任务都已结束、没有子会话的那些。Pi 没有删除接口，是按会话 ID 从它的表里删（entries、submissions、tasks、documents 及其版本、record_ids）。
- **不清理的**：审计表按设计只追加（有触发器拒绝删除，且行与行串成哈希链），每条裁决一行，所以它仍然随时间增长（见第 8 节）。上传的图片文件也不清理（只有人手提交的才有图片）。
- **列表**：审次、人工、申诉列表只看得到保留下来的内容；审次列表标题写着"演示模式只保留最近的模拟内容"。

### 6.5 真实语料回放（`DEMO_CORPUS`，2026-10-09 晚）

- **为什么**：负责人看到演示里的句子都是编的，太简单，要用真实句子。
- **语料**（`scripts/make-demo-corpus.py`，在算力服务器上跑）：测试集 3,002 条，配上 Kev-4B v1 在这个测试集上的实测原始答案（`data/eval/test-v1-kev4b-v1/answers-text.jsonl`：每题主问一个分布、打乱选项的复问一个分布）。文本取模型视图（链接、邮箱、@、手机 / QQ / 微信号换成占位符），剩下的连续 6 位以上数字也换成"[联系方式]"。按切片分成正常、营销、辱骂（含对抗扰动）、注入四类；去掉 1 条过长或无答案的，实际 3,001 条：正常 1,792、辱骂 809、营销 373、注入 27。文件里是数据集原文，**只放在算力服务器和开发机上，不提交**。
- **流量**（`demo-traffic.ts` 的 `CORPUS_MIX`）：设了语料，模拟流量只发语料里的句子，按 正常 72% / 营销 12% / 辱骂 13% / 注入 3% 抽（测试集本身约三分之一是违规，平台上没有这么高）；辱骂内容三分之一挂在有处置历史的账号上，给 agent 查历史用。没设语料时还是原来编的句子。
- **快判**（`packages/worker/src/demo-corpus.ts`，`demoJudge` 的 `corpus`）：请求的文本（按模型视图）在语料里，就按题目键（ABUSE-001、MARKETING-003、injection_guard）回放记录的主问和复问分布；其他文本（手动提交、图片）仍用脚本打分。agent 带证据复判时也回放同一份答案（那次评测没有给证据）。判官名报为 `kev4b-v1-replay`。
- **agent 复判**（`corpusAgentAnswer`，2026-10-09 晚加）：第一次部署时 agent 结束的审核九成多交给了人工，因为带证据复判回放的仍是同一个中间带分数。负责人要求演示里人工少一些、agent 处理掉大部分。现在 agent 带证据复判时，规则题按数据集自身的标签（文本来自哪个切片）给出明确答案；按 ID 固定约 `DEMO_CORPUS_HUMAN_PCT`（默认 10）% 的条目仍回放原分数，因而仍交人工。注入检查题和例外题保持回放。**这是演示脚本，用数据集标签代替 agent 查证据的结论，不代表任何 agent 的实测效果。**
- **校准**：用 Kev-4B v1 拟合的温度（`calib/kev4b-v1/`，从 `data/calib/fitted-kev4b-v1` 拷来，只有数字），G 和 W 都换成这一份；所以快判这一段（校准、策略、分流）跑的是真实模型输出。
- **页面**：`/api/config` 多了 `demo_corpus`（回放的判官、条数）；顶栏"演示模式"的提示和概览的说明改成"内容取自测试集真实文本（联系方式已打码），快判回放实测打分；agent 是脚本"。
- **启动**：`DEMO_CORPUS=data/corpus/demo-corpus.jsonl [DEMO_CORPUS_JUDGE=kev4b-v1] pnpm run demo -- --build`。语料不能放在 `data/demo/` 下：演示启动时会清空这个目录（不带 `--keep` 时），第一次部署就这样被删过。
- **部署后实测（开发机，每秒 10 条，约 1 分钟，仅供参考）**：快判 538 个审次里，自动放行 281、自动处置 77、转 agent 179（约 33%，脚本判官时约 15%）；agent 结束的 167 个里 12 个自己处置，155 个以"证据不足"交人工。原因：agent 复判回放的是同一份中间带分数，脚本 agent 拿不到能改变判断的新信息。
- **不足**：
  - 回放的是离线分数，不是现场推理；延迟仍是演示设定的 350 毫秒。
  - agent 还是脚本，它对真实句子的判断不代表真实 agent。
  - 打码只覆盖上面几种格式，变形写法（如汉字数字、拆开写的号码）可能漏掉；原文仍是公开数据集里的原话，含真实辱骂。
  - 测试集是评测用的，演示里会反复出现同一批句子。
  - 转 agent 的大多交给人工（见上），人工队列比脚本判官时长；每秒 50 条时转 agent 约 16 条 / 秒，超过脚本 agent 实测约 10 条 / 秒的上限，会触发背压直接转人工。这一档没有重新实测。

## 8. 不足

1. **时间线是账本重建，不是会话原文**：工具参数是推出来的（复判的 rule_ids 从答案反推，证据按时间对应），agent 的自由文本输出和工具返回给模型的原文都没有展示；同一毫秒写入的多条同类证据按写入顺序匹配。
2. **SSE 是轮询**：每个连接每 250 ms 查一次 app.db、有变化才推；多客户端时查询量线性增长，没有做压测。
3. **演示模式不是模型**：判官是关键词规则，agent 是固定流程；能演示的只是"系统怎么流转、怎么拦"，不能说明真实模型的效果。弹幕、昵称借用评论场景的温度；费用是估算 token 乘真实单价。
4. **真实模式没有在本次跑过**：按约束没有调用付费或远程模型，真实模式只做了类型检查；它的判官、agent provider 和 `.env` 读取代码没有改动，只是挪进了 `DEMO` 分支之外。
5. **鉴权仍是单令牌 + 审核员名单**（`config/reviewers.json` 目前只有 `rev1`），没有角色分级；演示模式通过 `/api/config` 把令牌交给前端，真实模式由审核员手输、只存在本标签页的 sessionStorage。G 只监听 127.0.0.1，没有做 CSRF 防护。
6. **规则页只读**：影子检查、灰度、回退仍用命令行 `scripts/rules-release.ts`。
7. **口径**：概览的"自动完成率" = （快判处置 + agent 处置）/ 已结束审次，申诉审次也算在内，与 `/api/metrics` 的窗口指标口径不同。
8. **前端没有组件级单元测试**；交互靠浏览器冒烟覆盖主路径。浏览器冒烟没进 CI（需要 Chromium 和系统库；本机缺库，是用本地解压的库跑通的）。
9. **行为变化**：`/` 在有构建产物时变成新控制台（旧仪表盘在 `/legacy`）；`/api/human/submit` 对别人已领取的任务返回 409。
10. **演示流量是脚本**：文本只有几十条，按固定比例重复；模拟审核员的裁决规则是固定的（概率最高的规则 + 哈希），不代表真人的判断分布；申诉理由随机。人工队列"有界"靠模拟审核员的产能跟着流入走（6.1 节）。
11. **长时间运行**：清理之后 app.db 和 session.sqlite 稳定在保留条数对应的大小（6.3 节），但审计表不清理，每条裁决一行，按设计只追加；G 内存里每个账号的频控记录随新账号增长（轻度辱骂每条一个新账号）。每次 `pnpm run demo` 启动会清空库（`--keep` 除外）。
12. **全局实时流仍是轮询 app.db**：只是由多个连接共用一个轮询器；W 写库后要等下一次轮询（默认 500 ms，帧间隔至少 800 ms）才推出去。agent 运行中租约续期也会更新审次的 `updated_at`，所以运行中的审次会反复出现在增量里。
13. **列表重读**：审次列表、人工队列、申诉在计数变化时整页重读当前查询（最多每秒一次），不是按增量合并；切换筛选或页签时，新数据到之前仍显示旧列表。
14. **截图检查的覆盖面**：溢出检查只看 DOM 几何（裁切、溢出、超出视口），看不出重叠以外的排版问题，例如对齐和视觉层次，这部分是人工看截图；只在本机的 Chromium 和文泉驿微米黑字体下检查过，其他字体和浏览器没有看。
15. **浏览器测试仍不在 CI**（同第 8 条）。
16. **上限是这台机器上的数**：6.3 节的上限是 2 核、2 GB 的开发机上 G、W 同机测得的，换机器要用 `scripts/demo-capacity.ts` 重测；脚本判官和脚本 agent 只是按定时器等待，真实模型的上限取决于判官和 agent 模型的服务能力，与这里无关。瓶颈在 agent 一侧（每条 agent 审次约 5–7 秒，W 单进程），快判一侧在每秒 60 条左右也到顶（G 单线程，和 W 共用一个 SQLite 写锁）。
17. **清理的副作用**：审次、人工、申诉列表只剩最近的模拟内容；`/api/metrics` 的 5 分钟窗口指标从 app.db 算，速率高到 5 分钟内的内容超过保留条数时，窗口指标只覆盖库里剩下的那部分（概览头部的吞吐和耗时来自 G 内存，不受影响）。W 的会话清理直接按 ID 删 Pi 会话库的行（Pi 没有删除接口），依赖 Pi 1.0.4 的表结构，升级 Pi 时要重新核对。
18. **图片是演示**：演示模式不识图。预置截图的"读图"是脚本按已知内容打分，其他图片一律给 0.5；`image_check` 用 T=1 当作已校准只在演示模式。页面和时间线上都写了这一点。真实模式的图片通道（relay 模型）没有在本轮跑过。
19. **帧率是无头软件渲染下的数**：没有 GPU 的无头 Chromium 和 G、W 挤在 2 核上；有 GPU 的普通浏览器没有测过。概览在每秒 50 条下仍是持续重绘（点一直在动），减少动态效果时没有这部分开销。
20. **管线的点是计数差值，不是一条条内容**：点按相邻两帧计数器的增量均匀放出，进 agent 的点和 agent 出来的点不是同一条内容；速率高时一个点代表多条。
21. **W 内存在高速率下缓慢上涨**：50 档 10 分钟 W 从约 150 MB 涨到 269 MB；会话库清理之后仍在涨，可能是 Pi 在进程里缓存了已结束的会话对象，没有定位。长时间开在最高档时要留意，重启演示会恢复。
