## 3. 按设计改变的行为（审查时请留意）

1. **判官看到的文本**：线上快判和 agent 的判官请求改用模型视图（链接、邮箱、@、联系方式换成占位符）；库里原文不变，agent 读原文的工具不变。
2. **校准**：`calib/jev-latest/` 有了拟合文件，strict 模式下按它分流；规则改了以后这些文件不再匹配，相应题目会按"缺校准"转人工。
3. **agent 首轮输入**：多了按审次生成的任务说明；worker 入口的指令改为按 judge 返回的 support 处置（原来在提示里写死 0.10 / 0.90）。
4. **judge / confirm 的返回**：多了 `support`（当前允许的处置、各规则状态、缺什么）和 `dispose_with`。
5. **重复请求**：同一审次再次取线程上下文 / 账号历史返回已有证据；同证据同问题的 judge 返回上次结果，不新开工具请求。
6. **申诉**：`POST /api/appeals` 额外写一条 `synth_event`（kind=appeal，含理由代码）。
7. **网关**：可挂候选规则包（默认不挂，行为不变）；场景开关 `context_route`（默认不设，行为不变）。
8. **评测集**：每条多了 `raw`、`text_strip`、`family_id`；`text` 改为模型视图；4 条注入样本的临时切分随去重代表改变。
10. **图片**：配置 IMAGE_DIR + IMAGE_MODEL 时带图内容送看图判官（新转人工原因 `image_review`）；图片送达时 `image_check` 成为必答题；提交检查只把 `api=image` 的成功调用当作"图片已送达"。
9. **强模型默认值**：`STRONG_MODEL` glm-5.3 → deepseek-v4.1-flash（升级默认关闭）。

## 4. 已知不足（详见开发计划 3.1 节问题 1–9 与各报告）

- agent 阶段几乎全部交人工（判官带证据后多在中间带，agent 没有处置权）；快判看不到上下文、对"缺证"无感。
- 标签是模型辅助的；辱骂组两模型一致率约 80%；第三票偏宽；委托裁定的 22 条不是负责人本人的判断。
- 所有实验只跑一次；案例池小；第三票、校准、阈值都没有在独立的人工标注上检查。
- 评测集 v0.1 的拼音扰动实为插空格；校准版本是整个目录的哈希。
- 负载下偶发测试失败两类，原因未查明；开发机靠复制文件同步。
- 图片审核只有临时最小通道（无校准、题面不含图中文字的辱骂 / 营销、单次 5–8 秒）；开源判官暂缓。

## 5. 希望审查重点看的问题

1. `support` 的计算（`packages/worker/src/support.ts`）是否与提交检查完全一致；有没有它说"允许"而 dispose 被拒的情况。
2. 重复请求不重做（`extension.ts` 的 `fetched` 与 judge 去重）在崩溃重放、换代次时是否仍正确。
3. 灰度发布：闸门配置（含校准版本）与网关实际使用的配置是否会不一致；比例改动的权限。
4. 校准沿用和"校准版本 = 目录哈希"的组合对在途审次的影响。
5. 模型视图正则（两份实现）有没有会误伤正常内容或漏掉联系方式的写法。
6. 正式切分把"用过的家族"挡在测试集外的判定是否覆盖了所有用过的来源。
7. 各报告的口径（预期从哪来、哪些条目不进分母）是否会让数字偏好看。
8. 图片通道："图片已送达"按 `api=image` 判定是否足够防伪；图片内容未进入输入指纹的影响。
