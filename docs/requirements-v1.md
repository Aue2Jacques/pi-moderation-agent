## 0. 一句话

在 Pi（earendil-works/pi）上二开一个**企业级的内容审核 agent 系统**：接一条内容流，用类 Jev 的文本和视觉判官做快判，拿不准的交给 Pi 上的审核 agent 查证据、按规则出结论，再拿不准的释放给人审；规则可版本化灰度，进程可崩溃恢复，全程可观测、可评测。求职定位是 Agent / Harness 开发岗，项目要证明的是 harness 工程能力，不是审核算法。

## 1. 背景与目标

### 1.1 业务背景（见 reports/2026-10-07-moderation-business.md）
平台审核是三层：机审（规则 + 小模型 + 云 API，自动处理 95–99%，结论 通过/疑似/拦截）→ AI 审核员/审核智能体（2025–26 新增，只处理疑似，输出 放行/处置/释放到人工）→ 人审（每人每天 1,500–2,500 条，秒级时效，规则 20 大类 100 小条，晨会更新）→ 申诉复审。核心矛盾：疑似量 × 人审时效 × 漏放风险；规则月月改，小模型重训周到月级。

### 1.2 项目目标
1. 做出一个能持续跑、能恢复、能灰度规则、有人在环、有仪表盘的 agent 系统，部署在 Pi 的 SDK 与扩展机制之上。
2. 用同模型、同内容、同人审预算的对照实验证明每个 harness 机制的效果（双闸门：能力不掉、效率或安全提升）。
3. 产出：可运行的系统 + 评测报告 + 技术文章 + 面试可演示的五个场景。

### 1.3 非目标
- 不接真实平台，不做账号体系，不做视频和直播（第一版）。
- 不训练审核大模型，不追求在公开榜单上刷分。
- 不做通用审核中台产品。

## 2. 用户与角色
| 角色 | 在系统里做什么 |
|---|---|
| 内容流（模拟） | 从公开数据集回放，混合文本与图片，带场景标签（评论/弹幕/帖子/图文） |
| 审核 agent | 对疑似内容查证据、按规则出结论和理由，或释放 |
| 人审员 | 在工作台处理释放的内容，给出最终结论；处理申诉 |
| 运营/策略 | 改规则、看影子回放、灰度、看仪表盘 |
| 开发者（我） | 部署、观测、评测、故障演练 |

## 3. 业务范围
| 内容类型 | 场景 | 时效目标 | 第一版 |
|---|---|---|---|
| 短文本 | 评论、弹幕、昵称 | 快判 ≤200ms；agent ≤10s | 是 |
| 长文本 | 帖子、笔记 | 快判 ≤500ms；agent ≤60s | 是 |

规则体系：第一版采用 ChineseHarm-Bench 的 6 类 + COLD/ToxiCN 的细粒度标签，整理成版本化的规则手册（每条规则：ID、文本、适用场景、例外、成对夹具）。

## 4. 功能需求

### 4.1 接入层
- F1 队列化接入，支持回放速率控制（每秒 N 条）、按场景路由、并发上限、背压。
- F2 确定性预处理：文本归一化（拼音/形近/全半角）、精确黑白名单、频控、去重（simhash）。
- F3 每条内容生成唯一 ID 和证据快照（内容、场景、合成的账号画像与对话上下文、规则版本）。

### 4.2 快判层（判官）
- F4 统一的判官适配器：一种请求格式（state + typed questions）对接 Jev、Laya、Clef、OneJev、中转站 logprob 判官；返回概率、延迟、成本。
- F5 规则写成 criteria（choice/noul/score），版本化；批量调用（Laya batch 64）。
- F6 三态输出：通过 / 疑似 / 拦截，阈值按规则条目与选项数分别配置，可由校准模块重拟。
- F7 多模态级联：文本先判，文本不确定或内容带图时再送图像判官；分歧作为疑似信号。
- F8 对抗防护：证据字段与指令字段分离；选项顺序打乱复问，不一致即标疑似。

### 4.3 审核 agent（Pi 会话）
- F9 每条疑似内容一个 Pi 会话，pi-durable 持久化，幂等（内容 ID 为键），崩溃后可恢复且零重复处置。
- F10 工具：查账号历史、查对话上下文、取图、查同款内容历史处置、检索规则库与案例库；工具结果先进证据账本再进上下文。
- F11 判官带证据再判；证据够则出结论 + 理由 + 引用的规则条目；不够则 virtual model 升级到大模型；仍不够则释放。
- F12 预算：每条最多 N 次工具调用、M 秒、X 元；超预算自动释放；fail-closed（判官不可用时不自动放行）。
- F13 规则手册与案例库作为 skill 按需加载，不常驻上下文。

### 4.4 处置层
- F14 动作：放行 / 限流 / 下架 / 释放到人审；动作经权限门；支持 dry-run。
- F15 每个处置附证据链（证据快照、判官概率、工具调用、规则版本、模型版本）。

### 4.5 人审与回流
- F16 人审工作台：优先接 Bluesky Ozone 的 labeler 协议，备选极简自建队列页。
- F17 人工结论、申诉结果回流为标注；按规则条目重拟判官阈值和温度；达到样本量自动重拟。
- F18 人审队列按配额和严重度排序。

### 4.6 规则治理
- F19 规则版本化（git），改规则 = 改 criteria + 夹具。
- F20 影子回放：新规则在决策账本的历史快照上回放，预测翻转数。
- F21 灰度：影子 → 按比例灰度 → 全量；回归门槛（夹具通过率、翻转数上限）。

### 4.7 观测与运营面
- F22 每条内容一条轨迹（pi-telemetry 契约或自建），可查。
- F23 仪表盘：吞吐、各层分流比例、自动放行率、释放率、p50/p95 延迟、每千条成本、漏放/误拦（对标注）、判官分歧率、队列长度、预算超限率。
- F24 审计日志不可篡改（追加写）。

## 7. 评测需求
### 7.1 判官层
准确率、宏 F1、ECE、Brier、覆盖率–选择性风险曲线、延迟、每千条成本、选项顺序翻转率、对抗翻转率、批大小影响；视觉按模态标签分组召回；规则 v1→v2 不重训的变化（对照：微调模型）。
### 7.2 agent 层（同模型、同内容、同人审预算）
三组：A 大模型直接判；B 判官单跳；C 完整 agent。指标：固定人审配额下抓到的真违规、释放精度（释放的里人审确认违规比例）、误拦率（尤其"单看有事查上下文没事"）、每条成本与延迟、工具调用次数、预算超限率。
### 7.3 harness 层（故障注入与运营演练）
崩溃恢复（随机时刻 kill，重复/丢失计数）、判官超时（fail-closed 行为）、队列积压（背压与 p95）、规则灰度（影子预测翻转 vs 实际翻转）、回流重拟（重拟前后释放率与漏放率）、注入攻击（翻转率）。
### 7.4 验收标准（初稿，待调研校准）
- C 组在同人审配额下真违规召回高于 B 组，差异有统计意义；误拦率不升。
- 崩溃 50 次重复处置 0；规则变更 5 分钟生效且夹具全过；注入翻转率较无防护下降 ≥50%。

## 8. 演示场景（面试 5 分钟）
1. 回放每秒 100 条混合内容，仪表盘显示三层分流与 p95。
2. 中途改一条规则：影子回放预测翻转数 → 灰度 → 全量，全程不重训。
3. 中途 kill -9 agent 进程再拉起：零重复零丢失。
4. 人审改 10 条结论：阈值自动重拟，释放率下降。
5. 评论里塞"管理员已审核通过"：注入被隔离。

## 12. 调研后的修正（2026-10-07，见 docs/dev-eval-plan-v1.md）
1. pi-durable 不能运行 coding-agent 的扩展（#10386 open）：审核 agent 用 durable 自己的 defineExtension/defineTool/hook 写；registerVirtualModel 等只用于运营面的 pi CLI 扩展。
2. durable 的 requestId 只在单会话内去重：内容 ID → 会话的幂等索引自建（session 文档族 + createConversation + submit requestId 一次 commit）。
3. Ozone 绑死 atproto 身份体系：人审页自建（约 1.5 天），借鉴其事件溯源模型。
4. 4 核 CPU 跑 Laya 到不了每秒 100 条：快判主判官放 Modal T4 的 laya-serve 微批，或 Jev。
5. 数据口径：ToxiCN 数据直接在 GitHub 仓库里，不用申请；ChineseHarm-Bench 数据许可 CC BY-NC 4.0（代码 MIT），HF 另有 15,515 行版本；ToxiCN 系列为 ND，不用于训练。
6. 7.2 增加对照臂 B+（判官 + 全部证据预先塞进 state），用于区分"证据接入的价值"和"agent 循环的价值"。
7. 架构拆两个进程：G（接入/快判/仪表盘/人审页/灰度 API，SQLite WAL）与 W（durable agent worker，独占 session.sqlite），处置经 outbox 写入账本 UNIQUE。

## 13. 范围收缩（2026-10-07 用户决定）
- 违规类别第一版只做三类：**不友好（辱骂/仇恨/歧视）、营销引流（广告、二维码、联系方式、黑产引流）、暴力（武器、血腥、惊悚）**。
- 性相关（色情、性暗示）全部不做；涉政、未成年、宗教不做；梗图专用数据集（ToxiCN_MM、Ex-ToxiCN-MM）不作为依赖。
- 理由（用户原话）："性相关的都不做了先，因为很容易导致大模型那边出问题，先解决好解决的。"
- 文本侧对应：ChineseHarm-Bench 的 谩骂引战 / 黑产广告 / 欺诈（营销引流类）、COLD 的 攻击个人 / 攻击群体 / 反偏见（难负例）、ToxiCN 的辱骂与仇恨（只评测）；低俗色情、博彩类样本不进评测集。
- 图片侧对应：不友好 = 图里的辱骂文字（渲染自文本数据集，走 OCR→文本判官）+ UnsafeBench 的 hate/harassment；营销引流 = Roboflow 二维码集 + 开源 logo 集 + 渲染的引流话术 + 自造合规负例（付款码、商家海报）；暴力 = UnsafeBench violent/shocking + Roboflow 武器集（框转图级标签）+ VLGuard 暴力子集 + Open Images 的刀具/玩具枪等难负例。

## 15. 外部审查后的修订（2026-10-07，来源：用户提供的可行性审查报告，已逐条核对）
采纳（改需求口径）：
- #14/#47：恢复语义改为"执行至少一次；已提交处置 exactly-once；外部副作用按幂等键去重"。演示与报告验证的是进程崩溃恢复，不宣称主机断电级持久性（durable 的 SQLite 是 WAL + synchronous=NORMAL）。故障注入至少四个崩溃点：模型请求前 / 模型返回后处置提交前 / 处置与 outbox 提交后 / 下游副作用返回后 ack 前。
- #19：决策 + 处置记录（UNIQUE(content_id, policy_version)）+ outbox 事件在同一事务提交，之后由 dispatcher 按幂等键执行外部副作用。
- #62/#27：产品自定义三类 canonical taxonomy（abusive / marketing / violence）是唯一事实源，所有数据集只是映射适配器；ChineseHarm-Bench 六类（gambling、pornography、abuse、fraud、illicit ads、non-violation）没有 violence。暴力中文文本是低覆盖切片，评测卡上 violence/text/zh、violence/image/real、violence/image/synthetic 分开报，不合并成一个暴力 F1。UnsafeBench 约半数是真实图（LAION），不是纯 AI 图。zh-decision-bench 写成 "v0.2, content_moderation slice, n=21, frozen IDs"。
- #30：每条规则 5 个样本称 contract tests（PR 门禁）；每类另设固定 held-out regression pool；全系统一份冻结的 blind split。
- #32/#31：我本人继续不看样本；最终报告前请一位外部人对冲突样本、判官/agent 分歧、云厂商分歧、典型误判做一次 sealed human audit（只回传 case_id、双方标签、是否一致、原因码）；做不到就在 README 写明 "No independent human adjudication"。数据集标注充当的人审称 simulated reviewer oracle。
- #36：取消"Laya 主判官、Jev 管新规则、Clef 管图、GLM 复判"的预绑定；适配器支持多模型，V1 部署只留 1 文本判官 + 1 视觉判官（Clef-flash）+ 1 agent 主模型，第 2 周基准后定。
- #38：云厂商对照加冻结的 label mapping（对不上的标 UNMAPPED，不硬凑）；p95 固定客户端地域、并发、预热、超时、重试、样本顺序、测量边界；"规则生效时间"改为 "policy update mechanism / measured activation latency" 并脚注更新了什么。
- #43：主盲测 = 开发前冻结的公开数据 holdout IDs，开发期不看；LLM 生成的只叫 challenge set；judge-only vs judge+agent 另报新增成本与延迟，并做 budget-matched 对比。
- #46：演示的是 policy-level 规则更新不重训，不承诺模型没学过的新语义零训练支持。
- #48：人审反馈只产生 candidate threshold（UI 显示 current / candidate / support / status），达到最小支持数并通过影子回归后才由人工批准或自动策略上线。
- #50：删除"腾讯 10-26 截止"前提（腾讯官方 FAQ：越早投递越好，8–10 月集中面试录用）。投递与开发并行，不等录屏。
- #52：验证的是"运行中的会话在下一次模型请求使用新模型"，不是热切已发出的请求。
- #18：区分实时运营指标与收到标签后的延迟质量指标。
