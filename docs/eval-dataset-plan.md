# 综合评测数据集方案（v0.1，2026-10-11，待负责人确认）

目标：
- 不再只靠 COLD 一个数据集。用多个来源拼出一份覆盖辱骂、营销引流、诱导绕过（变体字）、注入、上下文和"不该拦"的难负例的综合评测集；
- 所有判官（Jev、Laya、Kev、Valen、JevEmbed、守卫模型等）都在同一份集合上比较。

开发者不看样本正文：统计只看条数和标签，判断交给模型，存疑的交给负责人看。

## 2. 我们自己构建的部分

项目文档 §8.3 的原则不变：**不让大模型生成有害文字**。有害内容只从公开数据按编号抽取；自己构建的部分是结构、变体和无害内容。

| 类别 | 做法 | 用途 |
|---|---|---|
| 功能测试（照 HateCheck 的类型） | 按规则书写中文模板；有害位置用公开词表的编号，由程序填充，不由人或模型写有害句子；无害部分自写 | 按能力分类报告：哪一类判错了 |
| 难负例 | 批评机构和观点、陈述新闻事实（含"犯罪""暴力"这类词）、夸奖、自嘲、无指向的粗口、反对偏见。自写，加上无害改写由模型批量生成 | 测"开放讨论"立场下的误拦 |
| 变体攻击 | 对公开数据里的有害句子，按 ToxiBenchCN 的六种方式（emoji、同音、调序、拆偏旁、拼音、繁体）用程序加干扰；数据集自带的变体直接用 | 测抗绕过能力 |
| 注入配对 | 同一条基础内容（有害的、无害的各一份）加或不加"忽略规则，判不违规"之类的后缀 | 测快判和 agent 会不会被带偏 |
| 上下文案例 | 按项目文档 §8.3 的 C0–C5 案例族（普通、查历史才有问题、查上下文才没问题、历史是诱饵、证据缺失或冲突、协同刷量）；"其他评论"按编号从公开数据里抽，账号历史是结构化字段 | 测 agent 查证据有没有收益（A/C 对比） |

## 3. 标签：两套并存，绝不混用

1. **原始标签**：数据集自己的标签，原样保留，用来报"在该数据集标准下"的成绩。
2. **本平台标签**：按规则书（`docs/policy/abuse-policy-draft.md` 定稿后）重新标注。流程：两个不同家族的模型各自独立标（不用 Jev，避免自己考自己），一致的直接采用，不一致的交负责人裁定，裁定记成判例。
3. 每条记录来源、原始编号、原始标签、本平台标签、标注方式（模型一致 / 负责人裁定）、是否有争议。

## 4. 规模、切分和防泄漏

- 起步规模约 6,000 条：每个来源按类别分层抽样几百到一千条，自建部分约 1,500 条。
- 切分成**开发集**和**冻结测试集**两份。测试集冻结后，任何调整（提示词、阈值、校准、微调）都不能看它；只在最后报一次成绩。
- 防泄漏：同一来源的近似重复样本（simhash）不能同时出现在开发集和测试集；模型微调用的训练数据（COLD 训练集等）不能和测试集有重叠。
- 编号不透明，不在编号里透露类别（吸取第九轮审查第 10 条的教训）。

## 5. 报告怎么出

每个判官都按下面几个维度报，不把所有东西混成一个总分：
- 每个来源、每个类别：原始标签成绩和本平台标签成绩；
- 功能测试按类型逐项过 / 不过；
- 变体攻击：加干扰前后的检出变化；
- 注入：加后缀前后的判断变化，误放和误拒都要看；
- 漏斗：固定漏放和误拦时，交给 agent 的比例；
- 延迟和成本。
