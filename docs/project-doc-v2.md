## 0. 一页摘要

**做什么**：在 Pi（earendil-works/pi）之上二开一个企业级的内容审核 agent 系统。内容像流水一样进来，判官（类 Jev 的决策模型）毫秒级快判，拿不准的交给跑在 Pi durable 运行时上的审核 agent 查证据、按规则出结论，再拿不准的释放给人审。规则版本化可灰度，进程崩溃可恢复，全程可观测、可评测。

**为什么做**：目标岗位是国内 2026 秋招的 Agent / Harness 开发工程师。这个项目证明的是 harness 工程能力：路由、恢复、幂等、背压、规则治理、人在环、观测、评测，而不是"又一个审核模型"。

**技术中心一句话**：**让模型决定需要查什么，但不让模型决定自己拥有什么权限、采用哪套规则、哪些结果可以提交。** Pi 提供检查点、会话恢复和工具重跑；我们的贡献在上面这句话，面试时分清底座能力和自己的工作。

**三条技术主线**（不再新增多 agent、通用记忆或更多基础设施，把这三条做深）：
1. 有预算的证据调查：为什么查线程而不查历史、什么时候证据已够、什么时候再查也没用；证据 = 与固定取证流程相比的质量、工具调用量、成本、延迟变化。
2. 不可靠执行下的可靠处置：模型超时、进程崩溃、旧结果迟到、申诉改判同时发生时谁有权提交；证据 = 故障测试后的数据库终态，不是日志里的"恢复成功"。
3. 规则和证据约束下的决策：模型能否换规则、伪造证据、借用别的审次的低风险分；规则更新后旧校准还能不能用；证据 = 权限拒绝记录、版本绑定检查、规则发布门槛与失败案例。

调研到的开源审核 agent 项目目前没有公开评测数字（见 reports/2026-10-07-moderation-open-source.md），这是本项目补的空，不是对整个行业的判断。

**第一版边界**：文本（评论、弹幕、昵称、帖子）和图片；三类违规（不友好、营销引流、暴力）；不做色情、涉政、未成年、宗教、博彩；不做视频、直播、音频；不接真实平台，流量用公开数据集回放。

**怎么证明**：对外一张表和阿里云、腾讯云比；内部主比较是完整 agent（C）对固定取证工作流（A），判官单跳（B）与判官加全部证据（B+）只解释收益来源；故障注入、规则灰度、注入隔离直接演示。

**时间**：8 周，10-08 起；10-22 冻结最小可演示版，10-24 录屏。投递与开发并行。

## 1. 目标与定位

### 1.1 目标
1. 一个持续运行的 agent 系统，部署在 Pi 的 SDK 和扩展机制之上，具备第 4 节定义的六项企业级属性。
2. 效果类机制（证据调查、判官选择）有同条件对照数据；正确性类机制（恢复、幂等、超时、权限门、版本隔离）用明确的不变量和故障验收证明，不为每项另搭一套对照系统。
3. 产出：可运行代码、评测报告与评测卡、技术文章、5 分钟演示视频、面试叙事。

### 1.2 非目标
- 不接真实平台，不做账号体系，不做视频、直播、音频。
- 不训练审核大模型，不刷公开榜。
- 不做通用审核中台产品，不做漂亮后台。
- 不复现论文，不做评测基础设施为主线。

### 1.3 求职定位
面试官是同行 agent 开发者。他们会问的词：状态持久化、断点恢复、异常处理与超时重试降级、并发控制、人在环、规则热更新、可量化评测、安全防护、成本与延迟。本项目每个演示场景对应其中几项（第 10 节）。

## 2. 业务背景

### 2.1 平台审核的真实流程（2026 年国内主流厂商说法一致）

```
全部内容
 → 第一层 机审：关键词/黑白名单/频控/去重 + 小模型分类器 + 云厂商 API
     结论三态：通过 / 疑似 / 拦截（腾讯云 Pass/Review/Block；阿里云 RiskLevel high/medium/low/none + Label + Confidence 0–100）【原文】
     自动处理 95%–99%【二手】；机审:人审 ≈ 9:1【二手】；传统 AI 过滤后约 3% 存疑【二手，数美宣传】
 → 第二层 "AI 审核员 / 审核智能体"（2025–2026 新增，只处理疑似）
     知乎：从人审平台绑定了 AI 的队列领任务，输出 放行 / 释放（转人工）/ 豁免（高风险兜底）【二手，知乎专栏摘要】
     网易易盾 CMA：机审守速度，智能体做语义理解、规则执行、流程分发【原文，易盾文章】
     数美审核 Agent：3% 存疑压到 0.3%–1.5% 进人工；案例送审量 15 万/日→3 万/日，准确率 95%【二手，宣传】
     快手：多模态大模型 + 智能体框架（规划/记忆/工具/行动），规则库与历史违规库检索，小模型预检大模型精查，大模型辅助审核员做 ASR 总结和关键信息标注【原文，InfoQ 与掘金分享】
 → 第三层 人审：工作台（倍速、批量）、队列按权重分发、晨会更新违禁词库
     一人一天 1,500–2,500 条视频【二手，澎湃】；时效细则 涉政 ≤15 秒/条、低俗 ≤5 秒【二手】；规则 21 大类 100 条【原文，网信办细则】
 → 申诉 → 复审；处置：限流 / 仅自己可见 / 下架 / 扣分 / 封号
```

### 2.2 机审的构成与弱点

| 环节 | 做法 | 弱点 |
|---|---|---|
| 预处理 | 文本归一化（拼音、谐音、形近、拆字、emoji）；OCR、二维码、水印；抽帧；ASR | 变体追不完 |
| 精确规则 | 违禁词、审核词、替换词；AC 自动机；黑白名单；频控；simhash 去重 | 无语义，谐音漏、引用误杀 |
| 小模型分类器 | 每个标签一组模型，输出 0–100 分，按分段映射三态 | 标签固定在训练里，新规则重训周到月级；分数不校准；只看单条，无上下文；几十个模型各自维护 |
| 策略层 | 标签开关、阈值、自定义词库、按场景切换 | 改不了规则的含义 |
| 送审策略 | 标签 × 分数落在疑似区间进人审 | 区间宽则人审爆，窄则漏放 |

### 2.3 我们在流程里的位置
- **判官层替代机审里的"小模型分类器 + 策略层"**：规则写成 criteria 当输入、概率可校准、一个模型管多类和多模态。不替代预处理、精确匹配、频控、去重（确定性代码，便宜又准）。
- **Pi 上的 agent 是第二层"AI 审核员"**：对疑似内容查证据、按规则条目出结论和理由，拿不准释放给人。
- 判官还打不过小模型的地方：速度和成本（int8 编码器 CPU 4 毫秒【二手】 vs Laya 14–200 毫秒【原文】）。所以第一版形态是：精确规则先过 → 小模型/判官过老标签 → 判官过新规则和难标签。

## 4. 企业级属性（系统必须满足）

| 属性 | 定义 | 验收 |
|---|---|---|
| 接流量 | 队列、按场景路由、并发上限、背压、对下游模型限流 | 回放 100 条/秒不丢不崩；积压时分档降级 |
| 可恢复、幂等 | **执行至少一次；同一审次（review_id）的处置 exactly-once；外部副作用按幂等键去重；申诉与重审是新的审次，允许追加新裁决** | 四个崩溃点各 kill 若干次，同一审次重复处置 0、作业丢失 0；"初审下架 → 申诉放行 → 重放旧事件仍保持放行"通过 |
| 规则治理 | 版本化、热更新、影子回放、灰度、回归门槛 | 改一条策略级规则 ≤5 分钟生效且 contract tests 全过 |
| 三层分流 | 判官 → agent → 人，每层有延迟与成本约束 | 仪表盘可见分流比例与 p95 |
| 人在环 | 人审队列、人工结论回流、申诉重审、阈值按反馈产生候选值 | 回流后候选阈值出现并经门槛才上线 |
| 可观测 | 每条内容一条轨迹；仪表盘；追加写审计 | 轨迹覆盖 100% |

恢复语义的精确说明：Pi durable 的 SQLite 是 WAL + synchronous=NORMAL，保证进程崩溃后已提交数据不丢，不保证主机断电【原文，durable README】。我们验证和宣称的是进程崩溃恢复。

## 5. 系统架构

### 5.1 框图

```
[回放器 Python] → app.db(SQLite WAL) 队列: intake(content_id PK, scene, prio, status, lease)
                 │
┌─ 进程 G：gateway（TypeScript）────────────────────────────────┐
│ 令牌桶限速 → 预处理(归一化/黑白名单/simhash/频控)             │
│ → 快判：pi-ai ModelRuntime.classify()，判官适配器             │
│    文本判官 ─不确定或带图→ 视觉判官 → 策略引擎三态            │
│ → 通过/拦截：同事务写 决策 + 处置记录 + outbox                 │
│ → 疑似：进 agent 队列（有界，背压）                           │
│ HTTP：仪表盘 / 人审页 / 灰度 API / 指标                       │
└──────────────────────────────────────────────────────────────┘
                 │ 疑似（准入信号量 ≤20）
┌─ 进程 W：agent worker（TypeScript，独占 session.sqlite）───────┐
│ pi-durable Harness：每个审次（review_id）一个会话               │
│ 扩展 moderation：工具（查证据/复判/升级/处置/释放）            │
│              + hooks（预算、截止、权限门、证据投影）           │
│ 处置：app.db 事务（审次唯一 + outbox）→ 成功后 durable memo    │
└──────────────────────────────────────────────────────────────┘
outbox dispatcher（幂等键）→ 外部动作（第一版为模拟端点）
旁路：Python（评测、校准拟合、合成数据）；Modal（判官服务、基准）
运营：pi CLI + ops 扩展（/shadow、/rollout、/status 调 G 的 API）
```

拆两个进程的理由：演示 kill -9 时杀的是 W，G 仍在，仪表盘能看到队列堆积、背压和恢复后的消化。

### 5.2 一条内容的生命周期（状态机）

```
内容：received → preprocessed → judged(pass|block|suspicious)
  pass/block → 审次 r1 直接形成有效裁决 → dispatched → acked
  suspicious → 审次 r1：queued → investigating → 裁决(pass|limit|takedown) 或 流转(release → human_queue)
  人审 → 在同一审次上形成有效裁决（人工裁决也是裁决）
  申诉 → 新审次 r2（新会话）→ 同上
  任何阶段失败/超时/超预算 → retry(≤N，同审次、新执行代次) → 仍失败则 release
```

两类结果分开：**裁决**（pass / limit / takedown）改变内容的有效处置；**流转**（release 到人审）只改变审次状态，不改变内容的有效处置。内容的有效处置 = 序号最大的**已提交裁决**；一个新审次只要还没形成裁决，旧裁决继续有效。待审期间的可见性由场景策略单独决定（§5.4）。

### 5.3 审次、恢复与幂等（最会被追问的部分）
**审次（review）模型**：一次审核 = 一个 review_id（content_id + 触发原因 + 序号）。重试复用同一 review_id 但换**执行代次（attempt / 租约代次）**；申诉、重审、规则变更触发的复核新建 review_id，并且**一个审次一个 durable 会话**（旧裁决通过受控工具查询，不继承旧会话的上下文、预算、截止）。裁决以 review_id 唯一；release 也是对审次状态的一次写入，同样幂等。同一内容可以有多条按序的裁决，**当前有效裁决 = 序号最大的已提交裁决**，迟到的旧事件（序号更小或代次更旧）不能覆盖。提交裁决时重新检查：审次身份、执行权限、规则/校准/证据版本与审次记录一致、证据归属本审次，以及**该动作所需的证据条件**（按动作区分，见 §6.4）。

**人工接管契约**：机器审核的截止时间只终止自动审核权限，不终止人工裁决资格。转人工后，旧机器执行代次永久失效；人工通过独立的授权路径，在"待人审"状态下提交裁决，不继承机器租约，也不受机器截止时间约束；人工裁决不需要服从被纠正的机器判断。已提交的裁决需要纠正时新建审次，不覆盖旧记录。验收用例：机器超时 → 转人工 → 人工放行成功 → 旧机器结果迟到 → 旧结果被拒绝，人工裁决保留。

**事实源**：app.db 是唯一业务处置事实源：处置记录（UNIQUE(review_id)）、内容终态、outbox 事件在 app.db 的同一事务提交。durable 的 session.sqlite 只保存执行进度（对话、工具调用、intent）；重试时先查 app.db 是否已有该 review_id 的处置，有则直接复用。

**写法**：
- review_id → conversation_id：一次 durable commit 里查 ReviewIndex[review_id]、无则 createConversation 并登记，再 submit({requestId: review_id})。两步幂等。content_id 只用于关联同一内容的多个审次，不对应会话。
- 工具：执行前先提交 intent；只有声明 replay:"safe" 的工具在恢复时重跑，否则得到 interrupted【原文，durable README】。dispose 工具声明 replay:"safe"，其执行体是对 app.db 的一次事务：INSERT 处置（review_id 唯一，已存在则读回原值）+ INSERT outbox；完成后再在 durable 里 memo。崩溃在两者之间时，重跑 dispose 读回同一结果，不产生第二条处置。
- outbox dispatcher：at-least-once 投递，消费端按幂等键去重并按 review 序号保序；启动时对账。
- 并发：durable 调度器无并发上限【原文】，自建准入信号量（≤20）。
- 崩溃点矩阵：A 模型请求前；B 模型返回后、处置提交前；C 处置与 outbox 提交后、memo 前；D 下游返回后、ack 前。
- 首个验收用例（开工第一件事）：初审下架 → 申诉新审次放行 → 重放初审的旧 outbox 事件 → 当前有效裁决仍是放行；再在 B、C 两个提交边界插入 kill 重复该用例。

### 5.4 容量、背压与超时
- 容量按分流比例和平均耗时推算（Little 定律，假设计算非实测）：100 条/秒 × 3% 进 agent × 平均 10 秒 = 30 个在途，超过 20 并发。所以吞吐分三项分别报：接入速度、快判完成速度、完整审核完成速度；回放器写入成功不等于系统完成。
- 背压按**总未完成量**和各队列容量决定：agent 队列超过容量 → 新疑似改为直送人审并打标；人审队列也超过容量或总未完成量超过上限 → 暂停回放器。不只盯 agent 队列。
- 可见性策略按场景写死：先审后发场景（帖子）疑似内容在裁决前"仅自己可见"；先发后审场景（评论、弹幕）疑似内容保持可见但打标，超过时限未裁决则按策略限流。
- 主动超时（谁触发、W 死了谁管）：截止时间持久化在 app.db 的审次记录里；由 G 的运行控制层定时扫描到期审次。顺序固定：**先在 app.db 的一个事务里原子完成"撤销当前执行代次的租约 + 审次状态改为待人审"**，然后尽力通知 W 发出 root.abort(context) 停止该会话（durable 的语义是取消 wait 不取消工作，必须走 abort【原文，durable README 第 76、415 行】）。转人工不依赖 abort 成功返回；W 已死或不响应不能阻止人工接管。W 拉起后重新申请租约并重新受准入与预算约束。迟到的结果带着已失效的执行代次，提交层拒绝写入。"最后会 release" 由这条控制链路保证，不由模型自觉。
- 可见性与 fail-closed 的口径：先审后发场景（帖子）待审不公开，是严格 fail-closed；先发后审场景（评论、弹幕）疑似内容限时可见并打标，这是"限时暴露策略"，不称为严格 fail-closed。MVP 阶段待审一律不公开。
- 人审队列按 严重度 × 时效 排序。

## 6. 模块设计

### 6.1 接入与预处理
- 队列：app.db 表 + 租约，不引入 Redis。
- 预处理：文本归一化、精确黑白名单（AC 自动机）、频控、simhash 去重。全部确定性。
- 证据快照：内容、场景、合成的账号画像与对话上下文引用、规则版本、时间。
- 存储边界分两层：**受限原始存储**（content 表、证据文档全文、durable 的 session.sqlite，这三处不可避免含正文，访问受控、不进 git、不进演示）和**脱敏观测输出**（app.db 其他表、轨迹、日志、仪表盘、人审页默认视图，只存 content_id、sha256、长度、类别、概率）。模型写的证据摘要可能复述正文，归入受限存储，不假定摘要天然脱敏。

### 6.2 判官层
**适配器接口**（兼容 /v1/systemone，state/questions 原样透传，bool↔noul 互转）：

```json
请求 {"request_id","content_id","rule_version":"rules@<sha>",
      "state":{"content":{"text_ref":"sha256:…","text":"…","scene":"comment"},
               "context":{…},"images":[{"ref":"blob:sha256:…"}]},
      "questions":{"cat":{"type":"choice","instructions":"…","criteria":{…},"rule_ids":["ABUSE-003"]}},
      "options":{"shuffle_seed":17,"timeout_ms":400,"calib":"calib/<judge>/<rule>@<ver>.json"}}
响应 {"judge":{"provider","model","api"},"status":"ok|timeout|error|abstain",
      "answers":{"cat":{"type":"choice","choice","probabilities":{…},"confidence",
                 "calibrated":{"probabilities":{…},"T"}}},
      "latency_ms","usage":{"input","output","cost_usd"}}
```

- 注册方式：pi-ai 的 createProvider({classifiers}) 或扩展的 classifier 模型条目（Pi 0.99.0 起支持，待在验证 1 中核实代码路径）。
- 三个自建 API：laya-batch（10ms 窗口或 64 条微批）、openai-logprob（照 Pi 的 llama-cpp-classify.ts 改成 top_logprobs；只问 choice 不问 bool，因为中文基准上 LLM logit 探针在二元题上崩到 0.53【原文，zh-decision-bench】）、clef-mm（图片；先试 onPayload 透传 images，不行就独立 provider）。
- 候选判官（第 2 周基准后择一部署）：文本 Laya multilingual（零样本 / 微调）、Jev、Clef-flash 纯文本、Kev-4B、NeoHorse-4B、qwen3.8-flash / glm-5.3 logprob；视觉 Clef-flash（主）、Clef 27B、OneJev、Valen；排除 imajev（仅英文）、Vev（非商用）；Chinese-Jev 权重未发布，观望。
- 对抗防护：证据字段与指令字段在协议层分开；同一问题打乱选项顺序复问，argmax 不一致标疑似。
- 视觉级联（路由规则，不是阈值）：**含图内容要被自动放行，必须先完成一次图片检查**（Clef-flash 一次调用或去重库命中）；文本已确定拦截的可提前结束；图片检查不确定或与文本判官分歧时才进更贵的复核。否则"正常长文 + 违规图"会被文本判官直接放过。

**策略引擎**（判官输出 → 三态）：

```
risk.abuse = 0.83, risk.marketing = 0.17, risk.violence = 0.01
policy v17:
  if scene == "nickname" and abuse > 0.92: block
  elif abuse > 0.65: suspicious
  else: pass
```

校准与阈值的键 = 判官模型版本 × 规则/问题结构版本 × 场景 × 选项数；规则或问题含义一改，旧校准自动失效，必须重拟或显式沿用并记录。温度缩放由我们的适配器在拿到原始概率后执行（System One 协议没有 temperature 参数，Pi 里只有 llama-cpp-classify 支持它【原文，pi-ai 源码】），不假定 provider 替我们校准。默认温度缩放；isotonic 只在该桶样本约千条以上才启用（scikit-learn 文档提示 isotonic 小样本易过拟合【原文】），否则只报可靠性图不切换方法。写成 calib/*.json 由 G 热加载。改阈值、加例外 = 策略级更新，不重训；新增模型没学过的语义不承诺零训练。

### 6.3 规则与策略层
**规则文件**（git 版本化，`rules/<ID>.yaml`）：

```yaml
rule_id: MARKETING-003
version: 3
category: MARKETING
scenes: [comment, post, nickname]
severity: 2
default_action: takedown
text: "…规则正文…"
exceptions: [{id: EX-QUOTE, text: "反诈科普、引用举报"}]
question: {id: lead, type: choice, options: {lead: "…", benign_mention: "…", none: "…", unknown: "…"}}
thresholds: {block: 0.92, pass: 0.10, keyed_by_option_count: true}
contract_tests:   # 5 个手写样本，PR 门禁
  - {id: c1, kind: obvious_positive,  ref: fx/m3-1, expect: violate}
  - {id: c2, kind: boundary_positive, ref: fx/m3-2, expect: violate}
  - {id: c3, kind: obvious_negative,  ref: fx/m3-3, expect: pass}
  - {id: c4, kind: hard_negative,     ref: fx/m3-4, expect: pass}
  - {id: c5, kind: injection_like,    ref: fx/m3-5, expect: release}
```

- 三级测试：每规则 5 条 contract tests；每类一个固定 held-out regression pool；全系统一份开发前冻结的 blind split。
- 影子回放：新规则在决策账本的证据快照上回放（只用快照不重查），预测翻转数。新规则需要旧快照里没有的证据时，该样本的影子结果标"证据不足"，不计入可上线结论；证据版本从一开始就进入结果缓存键。
- 灰度：影子 → 按 hash(content_id)%100 分桶 10% → 全量。发布门槛四项同时满足：contract tests 100%；**该改变的样本确实改变了**（规则的目标样本翻转率达到预期，防止"没生效所以翻转为零"）；不该改变的样本无退化（回归池）；成本与转人审量不超限。
- V1 不支持运行中热换工具代码；工具代码变更走发布并换版本号，新审次才使用新代码。
- 版本隔离契约：**每个审次固定规则版本、校准版本、证据快照版本**，写入审次记录；灰度只决定新审次用哪个版本，同一审次前后不混用。规则更新是数据版本切换（G 热加载规则 YAML 与 calib，W 端按审次记录的版本读取），不靠重装扩展实现。重装扩展只用于代码变更：durable 的语义是正在跑的工具调用用旧代码完成，下一阶段或下一次调用用新代码【原文，durable README 第 273 行】，所以同一审次内可能前后换代码，这正是要靠版本固定在数据层解决的原因。每次模型调用记录实际使用的模型 ID。

### 6.4 审核 agent（durable 扩展）
- 一个审次一个会话（review_id → conversation_id）；系统提示只放规则目录；规则手册与案例库按需加载（load_skill(name@ver) 工具；案例库 SQLite FTS5）。
- 工具（defineTool + TypeBox）：

| 工具 | 做什么 | replay | 备注 |
|---|---|---|---|
| get_account_history | 近 7 天处置与发帖摘要 | safe（只读） | 合成数据 |
| get_thread_context | 前后 N 条评论（按 ID 引用真实样本） | safe | |
| get_image | 取图并送视觉判官 | safe | |
| find_similar_dispositions | 同款内容历史处置 | safe | simhash |
| load_rule | 按规则 ID 取正文与例外 | safe | |
| judge | 带证据的判官复判 | safe | |
| escalate_model | 在 commit 里 configure() 换更强模型，下一请求生效 | safe | 只在"有证据但理解有歧义"时用；证据缺失时强模型补不出事实，直接 release |
| dispose | 提交裁决：对 app.db 的事务（审次唯一 + outbox），成功后 memo | safe（幂等） | 有副作用；只接受证据 ID 与行动建议 |
| release | 流转到人审，附证据链；也是对审次状态的幂等写入 | safe（幂等） | |

- 证据账本：工具结果全文进证据文档（存哈希与引用），模型看到的是投影 {evidence_id, 摘要, untrusted:true}。内容是 typed data 走证据通道；规则与权限走可信通道。**这不是防注入边界**：字段标签和结构化提示不能代替工具执行端的权限控制（OWASP 提示注入指南的立场【原文】）。安全上分别证明两件事：模型是否被诱导改变判断；即使被诱导，代码是否阻止了越权动作。
- 权限门绑定"本次审次的完整审核依据"：agent 只能提交证据 ID 和行动建议；原始内容、适用规则、问题选项、校准配置由服务器按审次绑定；裁决层只接受属于当前审次、版本一致、证据归属本审次的判官结果。放行和下架都过门，但**证据完整性要求按动作区分**（G 的快判与 W 的慢审用同一张表，不形成两套隐含标准）：

| 动作 | 所需依据 |
|---|---|
| 自动放行 | 完成所有适用的必查类别与模态（含图必检），没有未解决的必要证据缺口 |
| 自动下架 / 限流 | 满足支持该动作的规则证据，并完成相关例外核验；不能跳过仍可能改变该裁决的必要证据；文本已明确命中拦截规则时可提前结束，无需补齐其他类别 |
| 转人工 | 无法满足相应动作的条件，或达到预算、截止等边界 |

所有动作共同检查审次身份、执行权限、版本一致性和证据归属。不允许模型凭空引用一条规则就下架，也不允许凭"最近一次低分"就放行。
- 预算与截止（hooks + 控制层）：每审次最多 N 次工具、M 秒、X 元；超限或到期由控制层撤销租约并 release（§5.4）；判官不可用不自动放行。
- 升级路径分两种情况：证据缺失且无法补齐 → release（强模型补不出事实）；证据在但理解有歧义 → escalate_model → 仍不定 → release。
- agent 与固定工作流的边界：agent 根据中间证据选择下一个工具并在边界内停止，这是有意义的 agent 行为；如果所有内容都固定查同样三个工具再问一次模型，那就是固定工作流（评测里的 A 组），不包装成动态调查。

### 6.5 处置层
动作：放行 / 限流 / 下架 / 释放。权限门：动作白名单 + 场景；dry-run 模式。每个处置附证据链（证据快照、判官概率、工具调用、规则版本、模型版本）。

### 6.6 人审与回流
- 页面自建（一张页 + 三个 API，约 1.5 天【估计】），借鉴 Ozone 的事件溯源模型（takedown/label/escalate/acknowledge 事件流 + subject 状态）。不接 Ozone（绑死 atproto 身份体系）。
- 默认脱敏：默认视图只显示结构化元数据（内容哈希、场景、类别、概率、命中的规则 ID、证据类型与来源、审次状态）；自由文本的证据摘要和原文都属于受限查看，点开需二次确认并写审计。
- 人审结论与申诉 = simulated reviewer oracle（来自数据集标注），文档里不写"真实人审"。
- 回流：按规则条目积累标注 → 校准器计算 candidate threshold → UI 显示 current / candidate / support / status → 达到最小支持数且影子回归通过 → 人工批准或自动策略上线。最小支持数（正式 30，演示 10 并明示）是"允许生成候选"的流程门槛，不是安全上线的统计保证；上线前的依据是影子回归在 held-out 池上的结果与区间。

### 6.7 观测与审计
- 轨迹：pi-telemetry 契约 + 自写 SQLite 适配器（约 150 行，跑官方一致性测试）+ durable 的 subscribeCommits 补墙钟时间。
- 指标：吞吐、各层分流比例、自动放行率、释放率、p50/p95、每千条成本、判官分歧率、队列长度、预算超限率（实时运营指标）；漏放/误拦（收到标签后的延迟质量指标，分开报）。
- 审计：durable JSONL 追加写；app.db 的 audit 表禁止 UPDATE/DELETE + prev_hash 哈希链。
- 仪表盘：G 提供 /api/metrics + 静态页（uPlot，SSE 每秒刷新），约 1 天【估计】。

### 6.8 运营面
pi CLI 扩展：/shadow <rule@ver>、/rollout <pct>、/status、/calib，调 G 的 API。

### 8.3 合成数据（Python 包 synth/，生成规则公开）
- 原则：不让大模型生成有害文字；上下文里的"其他评论"从数据集按 ID 抽真实样本；账号画像、历史处置、申诉、时序全为结构化字段。
- 案例族与占比：C0 普通 60%；C1 查历史才有事 10%；C2 查上下文才没事 10%；C3 诱饵（历史差但本条无害）10%；C4 证据缺失/冲突 5%；C5 协同刷量 5%。gold 推导规则写进规则手册。
- 三种数据的结论边界分开：原始公开数据及其人工标签 → 只支持"该数据集标签体系下的识别效果"；加入上下文的构造场景及项目规则标签 → 只支持"在明确构造的审核场景中的表现"；注入、缺证、崩溃等挑战用例 → 只支持"对已定义故障和攻击场景的处理能力"。不把少量外部抽审说成整套合成场景获得了真实平台验证。
- C1、C5 里凡是 gold 只由"历史次数超过阈值"决定的部分，由代码判定，不拿来证明 agent 的理解能力；agent 评测只保留需要结合证据解释的歧义案例。
- 流量：泊松到达 + 突发；场景配比固定；按比例插入重复测 simhash。
- 防"合成偏向 agent"：主盲测 = 开发前冻结的公开数据 holdout IDs，开发期不看；LLM 生成的另叫 challenge set；捷径审计（只用上下文元特征训逻辑回归，准确率过高即合成太顺手）；结果按案例族分层报，不报合并总召回。
- 泄漏检查（冻结切分后单独跑）：同线程、同账号、近重复（simhash）样本不得跨开发集与盲测集；agent 可查的"账号历史"里不得出现该样本之后产生的人审结论或盲测标签（历史只含审次时间之前的事件）。

### 8.4 敏感内容处理铁律
- 开发者本人不阅读任何样本正文；需要判定内容时调 glm-5.3-flash；存疑样本只给负责人链接或行号。
- 最终报告前由一位外部人做 sealed human audit：对 taxonomy 映射冲突、判官/agent 分歧、云厂商分歧、典型误判各抽几十条，只回传 case_id、project_gold、auditor_gold、agree、reason_code。找不到人则 README 写明 "No independent human adjudication was performed."
- 日志、轨迹、仪表盘、仓库不出现正文；调试统一用 inspect CLI，正文打印为 [TEXT len=42 sha=ab12]。

### 9.2 三条赛道

| 赛道 | 问题 | 数据 | 对照 | 统计 | 零结果说明什么 |
|---|---|---|---|---|---|
| 判官 | 谁最准、最校准、最便宜；规则当输入 vs 进权重 | COLD / ChineseHarm 按 ID 分层 50/50，温度只在开发集拟合；zh-decision-bench；UnsafeBench 切片 | 候选判官 + 云厂商 + Qwen3Guard / Llama Guard 4；论文公开数字只作背景参考 | 每判官 ≥2,000 条；宏 F1 bootstrap CI；ECE 15 桶；Wilson 区间；覆盖率–风险曲线；"不掉能力"预先定义可接受差距（非劣性边界，例如宏 F1 −2pp），看区间不看点值 | 零样本在当前规则与测试分布下未观察到超过边界的差距：支持"规则当输入"在这些规则上可替代重训，不外推到新语义 |
| agent | 动态调查比固定取证多什么 | 疑似集：开发 400 + 验证池 + 盲测 900 | **B 判官单跳**（内容 + 场景 → 判官）；**B+ 判官 + 完整证据**（固定取证 → 全部证据给判官）；**A 固定取证工作流**（固定取证 → 与 C 相同的主模型一次判断 → 相同的最终判官与权限门）；**C 完整 agent**（按需取证、决定继续或停止 → 相同的最终判官与权限门）。**主比较是 C 对 A**，B、B+ 解释收益来源。A 与 C 同主模型、同规则、同可用工具、同证据环境、同处置检查；固定取证取得全部证据的调用量和成本计入 A。固定人审配额 K/千条，超配额未处理的样本计为待处理，不消失在分母里；人工 oracle 介入前后分开报 | 配对 McNemar：不一致率 10% 时检出 5pp 需约 312 条，3pp 需约 870 条【计算】；主指标：自动误放、自动误拦、自动完成覆盖率、转人审量、完整耗时、成本；宏 F1 与 ECE 只作解释指标；同时检查轨迹与最终数据库终态（模型说"已下架"不等于处置提交成功） | C 与 A 质量接近但取证更少或成本更低：仍支持按需调查的价值；质量、成本、延迟都无优势：这批任务上没有证明动态调查值得，如实写 |
| harness（模拟模型） | 状态转换、超时、恢复、租约失效、权限拒绝、outbox 终态 | 录制的判官响应 + faux provider（脚本化响应，用量是模拟值【原文，pi-ai README】），不花 token | 不变量 + 故障验收；Plan B（AgentSession + sink 幂等）只作退路，不是必做对照 | 统计单位是"一次崩溃"而不是在途任务（同一次崩溃里的任务共享故障条件）：50 次崩溃、重复 0 时按 50 个独立单位报 Wilson 上界（约 7%），在途任务数只作描述 | 不变量不成立即为失败，没有"零结果"一说 |
| 安全（真实模型） | 语义注入、拒答、证据利用、实际成本 | 真实判官与主模型；两条不可信输入路径：用户内容、工具返回 | 有无通道隔离与权限门各一组 | 每组 300 条配对；同时报告正常内容被误拒或误转人审的比例，不靠"全部转人工"得到好看的阻断率；分别报"模型是否被诱导"和"代码是否阻止越权" | 无防护时也不翻：说明判官本身抗这一类，换攻击类型 |

agent 赛道执行细节（开发文档落实）：
- 疑似集的选取：先冻结同一个入口判官与路由规则，得到共同的疑似样本 ID 集，A/B/B+/C 都处理这同一批；不允许各组按自己的结果各选一批再横比。
- 系统级报告除疑似集外，还包含快判直接放行与直接拦截路径的结果；这些路径上的错误不会被后面的 agent 纠正。
- 主比较 C 对 A 时**关闭 escalate_model**，固定主模型和总预算上限，各组报告实际消耗；模型升级作为单独说明的实验，不混进主结论。A 与 C 不要求消耗相同 token，节省调用本身是要测的收益。
- 各组从相同且互不污染的环境起跑：A 组写入的裁决、历史记录和缓存不得成为 C 组随后可查的证据；用独立数据库副本或只读证据快照实现。

故障注入矩阵：kill 随机时刻 + 四个定点（CRASH_AT=A/B/C/D）；判官 100% 超时与 30% 抖动（放行数必须 0）；回放 2× 容量看背压与 p95；注入话术追加在 state 末尾对比有无隔离。

规则灰度实验：影子预测翻转 vs 实际翻转的一致率；证据版本从一开始在缓存键里。
回流实验：日常回归和候选阈值门槛只用验证池；盲测集只在最终方案冻结后跑一次，作为最后的报告实验，不用于反复批准候选阈值。

### 9.3 云厂商对照方法
- 对象：阿里云内容安全增强版、腾讯云天御 TMS/IMS。同一批公开样本：文本 1,000、图片 500。
- 费用：腾讯云个人实名即可开通，新用户文本 3,000 条 / 图片 3,000 张免费 15 天，之后 25 元/万【原文】；阿里云增强版个人实名可开通但无免费额度，1.0 需企业认证【原文】。开工第一天验证"能开通、能建 key、能调 1 条"。
- 冻结的 label mapping（rules/mapping.yaml）：对不上的标 UNMAPPED 不计，不硬凑；**报告 UNMAPPED 的排除比例**；横向比较只在三方（阿里、腾讯、我们）都有可比标签的共同样本子集上算分，不各算各的再并排。论文公开数字标为背景参考，不是同条件结果。
- p95 协议：固定客户端地域、并发、预热、超时、重试、样本顺序、API 模式、测量边界；云厂商与自家系统用同一客户端同一时段。
- "规则更新"列改为 policy update mechanism / measured activation latency，脚注写清各自更新了什么（云厂商：标签开关、阈值、词库；我们：策略 DSL）。
- 补充对照（免费）：ChineseHarm-Bench、UnsafeBench 论文里的模型与商用分类器数字并排放；Qwen3Guard、Llama Guard 4 在 Modal 跑一遍（scale-to-zero）。

### 9.4 对外宣称与边界
能说：同模型、同内容、同人审名额、关闭模型升级的条件下，完整 agent 相对固定取证工作流在自动误放、自动误拦、取证调用量、成本、延迟上的差异（分层报告；判官单跳与判官加全证据作为解释性结果）；策略级规则 5 分钟生效不重训；进程崩溃 50 次已提交处置重复 0；判官快判每千条 N 元 p95 M 毫秒；注入翻转率 A%→B%。
不说：比腾讯云准、生产级、替代机审、防注入、任意新规则零训练。

## 附录 A 术语（大白话）
- 判官 / 决策模型：不生成文字、只对封闭问题给概率的小模型（Jev、Laya、Clef）。
- durable 运行时：把 agent 每一步记进本地数据库、进程死了能接着跑的执行引擎（Pi 的 pi-durable）。
- outbox：在同一个事务里保存裁决结果和"待投递的事件"，再由另一个进程投递。投递允许重复，消费端按幂等键去重并保序；这样崩溃不丢，重复也不会造成第二次处置。
- 幂等键：同一件事不管重试几次只生效一次的那个唯一编号。
- 影子回放：新规则先在历史记录上"假跑"一遍，看会改多少结论，不影响线上。
- 灰度：新规则先对 10% 流量生效，看没问题再全量。
- 校准：让模型说的 0.8 真的对应 80% 的正确率。
- contract tests：每条规则配的几个固定样本，改规则必须全过。
- fail-closed：系统出故障时宁可转人工也不自动放行。
