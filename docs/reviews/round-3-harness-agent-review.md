# 第三轮外部审查：harness / agent 工程角度（2026-10-07）

来源：项目负责人用另一工具对 docs/project-doc-v2.md（v2.1）做的审查，原文照录。处理结果见 project-doc-v2.md 附录 D。

## 结论

**这个项目的求职方向、主体架构和 MVP 范围可以定下来。v2.1 还不能原样冻结，但接下来应该做的是消除冲突、明确验收，不是继续增加功能。**

从 Agent / Harness 工程岗位的角度，我的判断是：

**它有潜力成为一项有分量的个人项目，但分量来自"如何约束模型、管理证据、保证处置正确"，不是用了多少判官，也不是接上 Pi 后能恢复。**

这版已经明确了 `review_id`、`app.db` 业务事实源、版本隔离、含图必检，以及收窄后的文本 MVP。这些方向应保留，不再反复推翻。

下面评价的是**设计及其求职展示价值**。文档引用的其他调研报告、代码和实测日志，本轮没有提供，不能当作已经独立验收。

## 一、从找工作看：哪些地方有价值，哪些地方还不够

### 我的岗位匹配判断

| 工作方向 | 当前项目能证明什么 | 不能仅凭这个项目证明什么 |
|---|---|---|
| **Agent 应用工程** | 工具设计、按需查证、规则执行、异常降级、效果与成本取舍 | 真实平台上的业务收益、实际节省多少审核人力 |
| **Harness 集成与可靠性工程** | 执行状态与业务状态衔接、预算控制、恢复后的权限检查、版本一致性 | 从零实现 durable 执行引擎 |
| **通用 Agent 平台／运行时研发** | 有关状态机、接口边界、调度和恢复的工程理解 | 多租户、跨机器调度、通用沙箱、平台规模化能力 |
| **算法／模型训练岗位** | 少量模型选型与校准经验 | 模型训练、算法创新或研究能力；这本来就不是你的目标 |

这是按工作内容做的匹配判断，不是录用概率评分。

**现在最需要防止的偏移，是项目最后变成"一个做得不错的审核后端，里面接了一个 agent"。**

Pi 已经提供任务检查点、会话恢复和工具重跑机制；这些可以合理复用，但面试时必须分清底座能力与自己的贡献。

你的独立贡献应该落在：

> **让模型决定需要查什么，但不让模型决定自己拥有什么权限、采用哪套规则、哪些结果可以提交。**

这句话比"企业级审核 agent，具备六项属性"更能说明项目的技术中心。

### 真正好的地方

**业务给工程机制提供了理由。**申诉解释了为什么需要审次；审核时限解释了为什么需要截止时间；规则变更解释了为什么需要版本隔离；有成本的证据查询解释了为什么需要按需调查。它们不是为了简历关键词硬塞进去的。

**你允许出现不利结果。**文档已经讨论 C 与 B、B+ 接近时如何解释，这比提前认定 agent 必须胜出更可信。不过，这些"零结果解释"还需要修正，下面会说。

**范围终于有了层次。**MVP 只做短文本、ABUSE、一个判官和一个主模型，是可以围绕核心问题交付的范围。图片、微调、完整灰度和云厂商对照后移，应继续保持。

## 二、项目深度建议固定在这三条主线上

**不再新增多 agent、通用记忆系统或更多基础设施。把已有机制做深即可。**

| 主线 | 必须讲清的问题 | 最有说服力的证据 |
|---|---|---|
| **有预算的证据调查** | 为什么查线程而不查历史？什么时候证据已经够了？什么时候继续查也没有意义？ | 与固定取证流程相比，质量、工具调用量、成本和延迟的变化 |
| **不可靠执行下的可靠处置** | 模型超时、进程崩溃、旧结果迟到、申诉改判同时出现时，谁有权提交？ | 故障测试后的数据库终态，而不只是日志里出现"恢复成功" |
| **规则和证据约束下的决策** | 模型能否换规则、伪造证据、借用别的审次的低风险分数？规则更新后旧校准还能不能用？ | 权限拒绝记录、版本绑定检查、规则发布门槛和失败案例 |

这里的 agent 不必拥有复杂的自主规划。**根据中间证据选择下一步工具，并在明确边界内停止，就足以形成有意义的 agent 行为。**但如果所有内容都固定查同样三个工具，再调用一次模型，应称为固定工作流，不必包装成动态调查。Anthropic 对 workflow 与 agent 的区分也是"预定义路径"与"模型动态决定过程和工具使用"。

另外，§6.4 的"证据不够 → 换更强模型"应拆开：**证据缺失时，强模型不能补出事实；有证据但理解存在歧义时，才考虑升级模型。**缺失且无法补齐，就转人工。

## 三、冻结前必须定下来的四组行为契约

### 1. §5.2—§5.4：审次、转人工和有效处置必须分开

`review_id` 的方向正确，但当前状态机仍把 `release` 和 `pass / limit / takedown` 混在同一组处置里。

这会留下一个没有答案的场景：

> 初审已经下架。申诉产生新审次，但新审次超时、转人工。此时"序号最大的已提交裁决"是 release，内容到底还下不下架？

**建议固定为：转人工是审次的流转结果，不是新的最终内容裁决。**

新审次没有形成有效裁决前，不因为 `release` 就撤销旧裁决；待审期间的可见性，由单独的场景策略决定。

同时建议把会话改为**一个审次一个会话**，而不是同一内容的所有审次复用一个会话。重试继续同一会话；申诉、重审新建会话，旧裁决通过受控工具查询。这样规则版本、预算、截止时间和上下文都自然按审次隔离，避免新审次默认继承旧 agent 的判断。

这不是多做一个系统，而是让现在已经引入的 `review_id` 真正贯穿全链路。

### 2. §5.4、§6.4：超时必须撤销提交资格，不能只是停止等待

文档已经写了主动超时和过期结果拒写，这是进步。但还需要说明：**模型一直不返回时，谁触发超时？W 被杀后，谁处理到期审次？**目前列出的 hooks 不能单独回答这两个问题。

建议固定行为：

> 截止时间持久化；由运行控制层检查到期并撤销执行资格，尝试取消模型／工具调用，再转人工。处置提交时重新检查审次状态、截止时间和当前执行租约。

**同一审次重试时，还应区分执行尝试或租约代次。**否则旧调用和新调用都携带同一个 `review_id`，仅检查审次 ID 无法区分谁已经失去提交资格。

Pi 文档明确区分"取消等待"与"取消工作"：取消 `wait` 不会取消任务本身，停止会话需要相应的 abort 路径。因此不能只用超时包装一个等待操作就宣布完成超时控制。

恢复后也必须重新受并发和预算约束，不能只限制新提交的任务。

### 3. §6.2、§6.4、§6.5：权限门必须绑定"本次内容的完整审核依据"

目前放行条件是"最近一次判官调用成功且低于阈值"。**这个条件仍然太弱。**

它没有排除：最近一次判的是另一份内容、另一个规则问题，或者只检查了一个低风险类别，却遗漏其他必须检查的类别。

建议固定：

> agent 只能提交受控的证据 ID 和行动建议；原始内容、适用规则、问题选项、校准配置由服务器绑定。处置层只接受属于当前审次、版本一致、检查完整的判官结果。

**放行和下架都需要检查。**不能只防模型错误放行，却允许它凭空引用一个规则就下架。

还要修正安全表述：`untrusted:true`、JSON 字段分离和证据投影有帮助，**但不是天然的防注入边界**。OWASP 明确指出，文字标签与结构化提示不能代替工具执行端的权限控制。

这里应该分别证明两件事：**模型是否被诱导改变判断；即使模型被诱导，代码是否阻止了越权动作。**两者不能合并成一个"注入已隔离"。

### 4. §6.3、§9.2：版本固定之后，还要明确版本变化的后果

当前已经固定规则、校准和证据快照版本，但仍有三个缺口。

**规则或问题含义改变后，旧校准不能默认继续有效。**"判官 × 规则 × 选项数"还不够明确，应绑定具体模型版本、规则／问题结构版本及适用场景；选项数量相同，不代表概率含义相同。温度缩放也应明确由你的离线校准结果在适配层执行，不能假定 provider 接收 `temperature` 就完成校准；Pi 的 System One 接口可能忽略该参数。

**规则上线门槛不能只有"翻转数不超过上限"。**一个根本没有生效的新规则，翻转数为零，也可能通过。应同时检查：该改变的样本是否改变、不该改变的样本是否退化、成本与转人工量是否超限。

**新规则需要旧快照没有的证据时，影子结果应标"证据不足"。**不能用不完整快照得出可上线结论。证据版本应从一开始进入结果缓存键，而不是等预测不准再补。

V1 不需要支持运行中热换工具代码。保留规则数据切换即可；**固定数据版本不能自动解决新旧工具实现语义不同的问题。**

## 四、评测方案建议这样定，不再扩成大型 benchmark 项目

### 1. 保留四个组，但重定义 A，让它成为真正有力的对照

现在的 B+ 很有价值，但它使用判官，C 还包含 agent 主模型。直接比较两者，不能单独归因于"循环调查"。

建议采用以下定义，**不增加第五组**：

| 组 | 固定定义 | 回答的问题 |
|---|---|---|
| **B：判官单跳** | 内容与基本场景 → 判官 | 不调查的基线 |
| **B+：判官＋完整证据** | 固定取证 → 全部证据输入判官 | 增加证据本身有没有用 |
| **A：固定取证工作流** | 固定取证 → 与 C 相同的主模型一次判断 → 相同的最终判官／权限门 | 不需要动态调查时能做到什么程度 |
| **C：完整 agent** | 按需取证、决定继续或停止 → 相同的最终判官／权限门 | 动态调查是否带来增量价值 |

**主比较是 C 对 A；B、B+ 用于解释收益来源。**

A 和 C 使用相同的主模型、规则、可用工具、证据环境及最终处置检查。固定取证组取得全部证据的调用量和成本也要计入，不能把它当免费输入。

相应地，零结果解释改为：

**C 与 A 质量接近、但取证更少或成本更低，仍然支持按需调查的价值；质量、成本、延迟都没有优势，才说明在这批任务上没有证明动态调查值得。**

这比要求 agent 必须提高准确率更符合工程目标。

### 2. 把三种数据的结论边界分开

你已经冻结了公开数据 ID，但"冻结了原文"不等于"合成上下文后的任务仍有原始人工 gold"。

C1、C2 会因为历史或上下文改变结论；原数据集的单条标签不能直接充当这个新任务的正确答案。

建议固定三种口径：

| 数据 | 用途 | 可以支持的结论 |
|---|---|---|
| **原始公开数据及原始人工标签** | 判官内容识别评测 | 在该数据集标签体系下的识别效果 |
| **加入上下文的构造场景及项目规则标签** | agent 调查评测 | 在明确构造的审核场景中的表现 |
| **注入、缺证、崩溃等挑战用例** | 安全和可靠性验证 | 对这些已定义故障和攻击场景的处理能力 |

保留外部抽审，但不要把少量外部抽审表述成整套合成场景已经获得真实平台验证。

另外，**如果 C1／C5 的 gold 只是"历史次数超过阈值"，应由代码完成，不要拿它证明 agent 理解能力。**真正适合 agent 的部分应包含需要结合证据解释的歧义，而不是简单计数。

### 3. faux provider 与真实模型必须分开计分

§9.2 将注入也放进了"录制响应＋faux provider，不花 token"的 harness 赛道，这一点必须改。

**模拟模型测试**用于验证状态转换、超时、恢复、租约失效、权限拒绝，以及 outbox 最终效果。

**真实模型测试**用于验证判断效果、证据利用、语义注入、拒答和实际调用成本。

Pi 的 faux provider 返回脚本化响应，token 用量也是模拟估计。它适合确定性测试，但不能证明真实模型看到注入后会不会翻转。

安全测试至少覆盖用户内容和工具返回两条不可信输入路径，并同时报告正常内容被误拒／转人工的情况。不能靠"全部转人工"得到漂亮的攻击阻断率。

### 4. 主指标与最终盲测的使用方式也要定

建议主结果围绕**自动误放、自动误拦、自动完成覆盖率、转人工量、完整耗时和成本**展开。宏 F1 和 ECE 保留为解释指标，不承担整个系统的质量结论。

固定人审配额时，超出配额仍未处理的样本必须计为待处理，不能消失在分母里；同时分开报告人工 oracle 介入前后结果。

**最终盲测不用于反复批准候选阈值。**日常回归和阈值门槛使用验证池，最终方案冻结后再跑盲测。文档当前"回流前后在盲测集上比较"的写法，需要明确是最后一次报告实验，而不是日常调参过程。

对于 agent，既要检查轨迹，也要检查最终环境状态。模型说"已下架"，不等于处置真的提交成功；这也是公开 agent 评测方法明确区分 transcript 与 outcome 的原因。

## 五、需要清理的旧内容，以及不应继续加重的范围

### 文档内部还有这些冲突

| 位置 | 当前问题 | 收口方式 |
|---|---|---|
| **§5.1** | 框图仍写 `content_id` 先写者胜、durable 文档→outbox→app.db | 与 §5.3 的 `review_id`、app.db 同事务提交统一。 |
| **§6.4、§7** | `dispose` 仍写处置文档；规则热更新仍写重装扩展 | 统一为业务库事务、规则数据版本切换。`release` 也会改变业务状态，不能不做幂等。 |
| **§10 场景 3** | 演示仍按 `(content_id, policy_version)` 唯一 | 改为同 `review_id` 不重复，不同审次可改判。 |
| **§5.4、§12** | 评论疑似保持可见，却整体宣称 fail-closed | 要么 MVP 待审不公开；要么明确这是"限时暴露策略"，不称为严格 fail-closed。 |
| **§12** | "疑似比例×平均耗时÷并发"不是吞吐公式 | agent 服务能力约为 `并发÷平均服务耗时`；稳定运行要求进入 agent 的速度低于该能力。 |
| **§6.1、§6.7、§8.4** | 正文仅存 content 表、完整工具证据、durable 记录、日志不含正文之间边界不清 | 区分受限原始存储与脱敏观测输出；不能假定摘要天然脱敏，也不能默认持久化会话不含正文。 |

还有两项应明确留作入库／适配验证，而不是现在伪装成已定事实：**Roboflow 等数据源的具体项目、版本和许可；中转站模型别名对应的真实版本与接口行为。**

### 两项建议直接降级为可选

**第一，取消"每个 harness 机制都必须有同条件对照"的总要求。**正确性机制需要明确的不变量和故障验收，不是每项都需要搭另一套系统证明。否则项目会重新变成你不想做的评测基础设施项目。

**第二，Plan B 保留为退路，不作为必须实现的对照组。**`AgentSession＋sink 幂等`能否继续执行、恢复哪些进度，需要另做设计；sink 幂等本身不等于 durable 恢复。也不能因为两版 token 浪费相同，就推导出 durable 只剩"不重复"价值。

多模型横评和 Laya 微调也不应阻塞主线。**保留适配能力，部署组合保持小；先证明审核链路，再决定微调是否值得。**

## 六、什么时候可以进入开发文档

我建议把"完全确定"定义为：

> **产品行为没有互相矛盾的版本；核心机制有明确验收；效果结论有明确实验方法；依赖失败有预定退路。**

| 现在必须冻结 | 进入开发文档后细化 | 必须等实现验证 |
|---|---|---|
| MVP 范围、三条技术主线 | 表结构、接口 schema、错误码 | 判官最终选择 |
| 审次与处置语义、超时和权限契约 | 租约、取消、恢复的具体实现 | 实际吞吐、延迟、成本 |
| 评测组、数据口径、主指标 | 用例目录、CI、部署与配置 | agent 是否优于固定工作流 |
| 对外声明边界、失败退路 | 每项工作的依赖与验收命令 | 模型与通道兼容性 |

开发顺序也应调整为：**机制实现时就配故障测试，W7 汇总报告，而不是 W7 才第一次验证。**

按你明确的阶段顺序，项目文档和开发文档完成后才正式开发，那么 **10 月 22 日仍只是目标日期，不能继续默认拥有完整的两周开发时间**。

### 我的最终意见

**项目可以继续，求职技术主线可以冻结；当前不能原样通过的是行为契约和评测口径，不是项目方向。**

本轮收口重点就是：**审次与转人工分离、超时撤权、证据绑定的处置权限、规则发布语义，以及重新定义后的 A/B/B+/C 评测。**这些写清并清掉旧章节，就具备进入开发文档的条件，无需再扩一轮功能。
