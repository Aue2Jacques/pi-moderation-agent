## 二、优先处理的六组问题

### 1. §5.4、§9.2：放行确认仍有两个不同性质的问题

#### 1.1 快判与提交层对"是否必须确认"意见不一致

目前规定：

**提交层：**所有 `pass_support` 都必须满足 `confirmed`，fastpath 同样执行这套检查。

**快判层：**G 只对疑似边界附近的样本复问；W 内用于放行的答案才明确要求必复问。

于是，一条风险概率为 `0.02`、远离边界的正常内容可能这样走：

```text
G 一次快判 → pass
T2 提交 → 没有 confirmed → 拒绝
```

**【局部条件验证】这个冲突能够复现。**

这不是模型准确率问题，而是正常成功路径被自己的校验挡住。

**建议：MVP 先统一口径，所有准备自动放行的结果都完成规定的确认。**如果未来为了吞吐减少 G 的确认，应把它明确设计成不同的放行策略，并独立验证，不能在 T2 中悄悄绕过检查。

这项选择会增加放行侧调用量，快判成本和延迟需要重新测，不能继续沿用单次调用预算。

#### 1.2 两次 choice 相同，不代表两次都支持放行

当前 `confirmed` 仍主要看 choice 一致，概率采用最新一条。

**【局部反例验证】**假设放行阈值为 `0.10`：

| 调用 | 违规概率 | choice | 策略分段 |
|---|---:|---|---|
| 原调用 | 0.20 | 正常 | 疑似 |
| 确认调用 | 0.02 | 正常 | 放行 |

两次都选"正常"，所以当前条件会认为已确认，并使用第二次低分放行。

**这说明上轮"同证据跨阈值"的问题仍然存在，新增一次确认没有自动解决它。**

建议把确认成功定义成：

> 原调用和确认调用的实际输入、问题、模型及校准版本一致；确认关系有效；两次结果都支持同一个允许动作。用于放行时，两次都必须满足放行条件。

至少把这组 `.20 → .02、choice 不变` 的例子加入 U-12/H-25。不能只测试 `.70 → .02` 这种通常会改变 choice 的情况。

### 2. §2.2：新增复合外键仍没有把裁决身份绑定到同一审次

目前 `ruling` 有两条独立约束：

```text
review_id → review.review_id
(content_id, seq) → review.(content_id, seq)
```

它们分别成立，**不保证指向的是同一行 review**。

**【SQLite 局部实测】**存在：

```text
review-A：内容 A，seq=1
review-B：内容 B，seq=1
```

下面这条裁决仍能插入，而且 `foreign_key_check` 不报错：

```text
ruling：review_id=review-A，content_id=B，seq=1
```

它的 `review_id` 引用了 A 的审次，内容与序号却引用了 B 的审次。

**建议直接改成三列联合身份约束：**

```sql
FOREIGN KEY (review_id, content_id, seq)
REFERENCES review (review_id, content_id, seq)
```

父表增加相应三列的唯一约束；同时，T4 的 `content_id/seq` 应从已经读取的 review 行派生，不接受调用方指定。

我也验证了这个修正：**错误组合被拒绝，正确组合可以插入。**

这里不是说尚未存在的 T4 实现已经写错，而是当前 DDL 还没有提供文档声称的那层数据库保护。

### 3. §7.3、§8.2、§8.4：恢复还缺"提交前后缝隙"，同轮工具的身份映射也没落实

#### 3.1 增加了 `submission_id`，但新增的写入缝隙也要处理

现在顺序是：

```text
创建 conversation
→ 绑定 conversation_id
→ submit
→ 绑定 submission_id
```

至少存在两个需要明确的恢复状态：

| 崩溃位置 | 重启后可能看到的状态 |
|---|---|
| conversation 已绑定，submit 尚未发生 | 会话存在，但没有任何 submission 可恢复 |
| submit 已持久化，submission_id 尚未回写 | durable 已有任务，业务库不知道对应 submission ID |

当前启动流程主要是分类、重新取租约、建立 grant、`resume()`，没有把这两种情况写成明确分支。**`resume()` 不能恢复一个从未提交过的 input。**

建议增加：

> 在审次仍允许机器执行的前提下，按固定首次 requestId 查询或幂等提交，取得原 submission，并补齐绑定；不能因为绑定缺失就创建另一份逻辑审核。

这两处都应有 kill 测试，不能只覆盖"创建会话后尚未绑定"的孤儿会话情况。

#### 3.2 `roundHasTerminal(api.taskId)` 缺少从工具任务到生成轮次的映射

文档说按 generation task 记录本轮工具，但 `beforeTool` 收到的 `api.taskId` 属于当前 **ToolTask**。Pi 为同一轮里的不同工具创建不同 ToolTask，并把它们归属于 generation。

因此，**如果直接用 `api.taskId` 作为本轮 key，不同工具会落到不同组**，看不到同轮已经出现的 dispose。当前文档没有定义这层转换。

应通过工具任务的归属或对应 assistant entry，找到同一轮的稳定标识。

更重要的是：**即使把其他工具 block，也不等于整轮会 terminate。**Pi 要求这一轮所有结果都要求 terminate；被 block 的结果并不会自动满足它。

建议仍然把最终保障放在宿主层：

> 业务审次已终结，宿主负责停止后续执行并完成收尾，而不是等待模型下一轮配合。

"可能多一次模型请求"可以作为观测结果，不能预先当作已经证明的上界。

### 4. §7.5：费用公式有确定的重复计入，未知费用与最终结算也未闭合

#### 4.1 回退公式可能把同一次判官调用加两遍

现在 S7/S11 的回退口径是：

```text
model_call.first_usage
+ judge_call.cost_micro
+ tool_slot.settled/reserved
```

但 judge 工具调用的费用，本来就同时出现在 `judge_call` 和对应 `tool_slot` 中。

**【局部公式验证，数值是假设】**

```text
主模型：100 微元
某次 judge 请求：700 微元
该请求对应 tool_slot：700 微元

公式结果：1500 微元
不同请求的已知费用合计：800 微元
```

"estimated"可以表示不确定，**不能用来合理化已知部分重复计算**。

#### 4.2 同一个 slot 既有已知费用又有未知请求时，会漏掉已知部分

当前公式按 slot 的单个 `status` 选择 settled 或 reserved。若某工具第一次请求已结算，恢复后第二次请求超时，slot 变成 unknown，公式可能只计 reserved，把先前已知费用排除掉。

另外，T12 仍是单纯累加，没有物理请求级的幂等标识。缓存结果恢复、结算重放时，如何避免重复累加，还没有规定。

**建议统一原则：**

> 按物理请求标识记录费用状态；同一请求结算幂等，不同请求可以追加。`tool_slot` 负责逻辑额度和聚合，不再与底层请求账单直接重复求和。

最后，**业务裁决不可覆盖，不等于费用只能写一次。**撤权之后，在飞请求仍可能结束；过早把 `used_micro` 永久冻结，会遗漏后到用量。可以让费用对账字段后续更新，同时保持原裁决不变。

S5/S6 中只要仍包含 unknown 或估算，也不应自动标记为 settled。

### 5. §11.5：部分验收条件仍会把正常状态当故障，离线"只读"检查也不是真只读

#### 5.1 四秒排队不能直接等同于丢失

当前未判完的 intake 必须满足：

```text
有有效租约，或者 updated_at 不早于两个扫描周期之前
```

`SCAN_MS=2000`，意味着一条尚未领取的内容等待五秒，就可能被守恒检查标错。

**【局部条件验证】**这一现象可以复现，即使队列还远低于背压阈值。

这实际上是在引入"四秒接入排队时限"，而不是证明有没有丢失。建议分开：

**守恒检查**确认内容有记录、能找到处理归属；**排队超时检查**使用明确的排队时限；**控制循环健康检查**确认该扫描的任务被按时扫描。

不能靠不断更新 `updated_at`，让"守恒检查"保持绿色。

#### 5.2 不是每个终态审次都有 durable submission

最终一致第 6 条要求"每个终态审次的 durable submission 为 done/unanswered"。但快判直接完成的审次没有 durable 会话；尚未进入 W 就被转人工、随后人工完成的审次，也可能没有 submission。

应按路径判断：**实际进入 durable 的审次才检查其收尾；未进入的路径标为不适用，而不是失败。**

#### 5.3 `openNodeSqliteStorage` 没有文档所说的只读打开语义

Pi 1.0.4 的这个函数会创建普通数据库连接、设置 WAL 等参数，其公开选项没有 read-only 开关。**不调用 resume，并不意味着数据库连接是只读的。**

因此，W 已死时的检查应明确为**持有 `w.lock` 期间的独占离线检查**，锁要一直持有到关闭存储；不能只试一下锁是否可取得，然后释放它再检查。当前"只读打开"的表述需要改。

### 6. 还有两处新的跨模块边界：策略版本与实验快照

#### 6.1 `scenes.yaml` 已成为安全策略，却没有明确进入版本固定

现在 `scenes.yaml` 控制必查类别、动作白名单、图片检查阈值、可见性和截止等行为。但 review 只固定 rules/calib/evidence/prices 版本；规则版本又定义为 `rules/` 的 tree SHA。

**由此推导出的风险是：**规则文件没有变化，只改 `config/scenes.yaml`，同一 rules_ver 下的权限门就可能改变，旧审次恢复后也可能使用新配置。

建议把 rules 与 scenes 的相关内容纳入**同一个不可变策略包版本**，审次和发布门槛都绑定它。没有必要再建一个配置服务。

这项不是要求你支持更多热更新，而是保证已经承诺的版本隔离覆盖真正决定行为的配置。

#### 6.2 各组独立数据库，不等于各组看到相同历史

B+ 的快照现在可以取 C 组运行时产生的 snapshot_seq；A/C 自己又在运行过程中创建审次、提交裁决。

一个可能的执行顺序是：

```text
A：先完成内容 1，再创建内容 2 的审次 → 能查到内容 1 的新裁决
C：先创建内容 2 的审次，再完成内容 1 → 查不到该裁决
```

两个数据库来自同一基线，内容也相同，但证据环境已经不同。此时差异就不再只来自动态取证。

**主比较建议采用实验前统一冻结的案例清单：**每条内容固定证据边界，A/B/B+/C 都读取它，不从某个实验组运行后的数据库反向定义其他组的环境。

如果后续专门研究"连续审核如何影响后续历史"，可以另做系统级实验；不要混入当前声称控制了证据环境的主比较。

## 三、几处可以顺手修掉的小问题

| 位置 | 问题 | 处理方式 |
|---|---|---|
| **T3′、T5** | 仍只比较 owner/attempt，不能排除租约已到期、但控制循环尚未处理的窗口 | 明确过期租约能否续租；按现有"过期失去资格"的契约，应检查状态、有效期和撤销标记，重新接管走新代次。局部 SQL 已验证旧条件能给过期租约续期。 |
| **D-10** | 重复 event_id 应返回原结果，但测试仍要求重放 release 得到 stale_notification | 区分"重复事件"与"第一次送达但已过时的事件"；前者返回原结果，后者才产生过时通知结果。 |
| **§7.1、§8.1** | `20 秒 × 2 = 40 秒`漏掉重试等待，不能直接作为生成墙钟上界 | 把等待和剩余 deadline 纳入计算；Pi 的重试实现确实计算了下一次重试时间。 |
| **§5.4 多选题** | 低违规概率不必然等于确认正常，例如题目包含 unknown 选项时 | 明确哪些 choice 支持放行，并增加"两次都选 unknown，但违规概率很低"的拒绝用例。 |
