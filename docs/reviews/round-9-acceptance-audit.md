## 结论

**你的担心有依据。现在确实存在"主要流程跑通了，就把整个阶段标成通过"的情况。**

但也不能说"很多东西都是假的"：**业务事务、权限检查、Pi 工具执行、部分崩溃恢复和 HTTP 工作台，都已经有真实实现。问题是，组件实现、冒烟测试、完整验收这三件事，被混在了一起。**

更准确的项目状态应当是：

> **已有实质工程实现的文本审核原型，完成了部分故障验证和低速端到端联调；尚未完成开发文档承诺的完整验收，也没有证明审核效果。**

本轮固定在提交 **`91ab0d0`**。我检查了实际源码、测试、CI 日志和阶段记录，还直接运行了几个与仓库字节一致的原始函数。**没有连接你的开发机，没有重跑付费模型或那次 500 条回放。**

## 一、不是"开发得快"本身有问题，而是完成标准被放宽了

当前 README 写"阶段 2 已实现""阶段 3 已跑通""阶段 4 已通过"；但开发文档同时写着：

**阶段 2 仍有未补项：**D 点子进程崩溃、崩溃后自动对账、工具恢复重放计数。

**阶段 3 校准没有完成：**原定验收包含校准文件和效果检查，现在改成"工具就绪，真实拟合后移"。

**阶段 4 计划中的图片工具没有接入：**代码里没有 `get_image`，但该阶段已经标为通过。

这就是你感觉"不踏实"的具体来源：

> **不是没有做，而是完成了某个阶段里的部分工作，随后沿用了整个阶段的完成标签。**

正常后移的功能不必现在全部补齐，但必须明确标注"未做"，并保证未完成能力不会被主流程当成已经完成。

## 三、最能说明"看起来跑通，实际没做完整"的五处

### 1. 校准函数写了，但真实审核路径绕过了校准

`packages/gateway/src/main.ts` 默认使用 `calibVer: env("CALIB_VER", "calib@identity")`；快判路径和 agent 内复判写入答案时，都是 `rawProbs: a.probs, calibratedProbs: a.probs`。**没有经过真实拟合的原始概率，被直接写进"已校准概率"字段，然后参与自动处置。** 而开发文档规定：校准文件缺失，应当得到 `calibrated: null`，不进入有效答案，只能疑似处理。

**应补的验收：**删除或换错校准文件，系统不能照常自动放行；加载有效校准文件后，实际送进权限门的概率必须能追溯到该文件。

### 2. 图片检查目前可能只是"问了图片问题"，并没有发送图片

快判看到 `image_refs` 非空时添加 `image_check` 问题；但调用判官时只传 contentId、text、scene、evidence、questions；`pi-judge.ts` 组装的请求里没有图片。权限门根据 `image_check` 的答案决定该项是否通过；Worker 工具列表没有 `get_image`。

> **模型没有看图，却可能回答了一个叫 image_check 的问题；系统随后把这个答案当成图片已经检查。**

**当前最合适的处理：文本 MVP 遇到图片明确转人工或拒绝自动处置。**

### 3. 成本收尾有一段明确的无效计算，仪表盘口径也不完整

`worker.ts` 中 `(r.used_micro ?? 0) + 0 * t.settled`：工具费用算出来了，却乘以 0。宿主触发转人工时先写 `usedMicro: 0, costStatus: "estimated"`。仪表盘 `release_pct` 只统计 G 的 judge_down、backpressure、preprocess_error；每千条成本从 `used_micro IS NOT NULL` 的审次取平均，不是完整内容流的全部费用。

**应补的验收：**正常裁决、主动释放、预算释放、超时撤权、崩溃恢复这几条路径，分别核对调用记录与最终费用；仪表盘的转人工数必须与业务队列结果一致。

### 4. CI 的规则验收入口还是占位脚本

`scripts/contract.mjs` 只有 `console.log("contract: no rules yet")`；夹具拉取脚本只有 `echo "fetch-fixtures: no refs yet"`。

> 故意让一条必需规则测试失败，CI 必须变红；故意移除一个必需夹具，CI 也必须变红。

### 5. 500 条回放是有效联调，但不是审核效果证明

回放脚本写入 `rp:abuse:123` 这类 ID；agent 的模型上下文包含由这些内容 ID 派生的 `review_id`；线程工具还会返回邻居内容 ID。**生成类别因此进入了 agent 能看到的信息。** 33 条进入 agent：8 自动下架、25 转人工、其中 10 超时；转人工率约 75.8%，超时约 30.3%。截止从 60 秒改成 120 秒不能单独算修复：应先区分排队、模型耗时、重复取证和终结失败各占多少。

## 四、测试是真实的，但有些只证明了比名称更窄的事情

1. **版本测试**（H-12）证明了"版本号存下来了"，没有证明"旧审次能按旧版本继续"。拒绝混用版本，不等于已经实现跨版本恢复。
2. **注入测试**（H-16）证明了权限门，不是实际模型抗注入能力。应准确命名为"越权动作被代码拦截"。
3. **"对账零违例"不是"全部任务完成"**：数据库中仍有一个未完成、尚未过期的 queued 审次，`instant()` 和 `final()` 都返回零违例。`scripts/reconcile.ts` 不执行 W `/sessions` 的 durable 收尾检查，也不因违例以非零退出码结束。
4. **权限函数边界**：相同证据已有一对低风险确认结果 → 随后又出现同 choice、但概率为 0.40 的疑似结果 → `allowedActions` 仍然包含 pass。

## 五、现在最应该改的不是开发速度，而是验收方式

| 优先级 | 要完成的事 | 真正通过的证据 |
|---|---|---|
| **先恢复边界** | 未校准模式显式化；图片未接入前不得自动放行；修正费用无效收尾 | 删除校准配置、输入含图内容、触发超时释放，都得到规定行为 |
| **接通验收入口** | CI 真正调用规则测试与夹具检查；对账有完成检查和失败退出码 | 故意破坏规则或必需数据，验收必定失败 |
| **补关键运行分支** | D 点子进程恢复、工具请求重放计数、完整收尾、旧策略审次恢复 | 在真实 G/W 入口下触发，不只直接调用辅助函数 |
| **再测审核效果** | 使用不泄漏类别的 ID、冻结标注样本、明确统计分母；随后做 A/C 对照 | 能分别说明流程完成、审核正确和动态取证收益 |

进度应拆成四种状态：**代码已实现、入口已接通、故障验收通过、效果评测完成。**

## 最终评价

> **真实实现已经不少；真正保证质量的接线、异常路径、数据口径和验收门槛，还没有跟上完成声明。**

我对"可以继续写 core、做最小验证"的判断不变；**但不认可当前已经完成阶段 1—4 的完整验收。下一步应补验收，不应继续用一次 500 条联调代表整阶段完成。**
