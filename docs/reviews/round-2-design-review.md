# 第二轮外部审查：项目文档 v2 设计审查（2026-10-07）

来源：项目负责人用另一工具对 docs/project-doc-v2.md（v2.0）做的设计审查，原文照录。处理结果见 project-doc-v2.md 附录 C。

## 结论

**有条件可行，值得继续。v2 比原来的清单成熟很多，但还不能直接冻结成开发规格。**

现在主要不是"这个方向适不适合做 harness"，而是两件事：**几个关键机制单独成立，连起来还存在冲突；MVP 的范围和周计划没有对齐。**

按一人主要精力投入判断【工程估计】：**约两周做一个收窄的文本 MVP 有机会；8 周做出有说服力的工程原型合理；原样完成文档里所有功能、微调和三条评测赛道，不宜承诺。**

以下按 **v2 章节号**评价。文档中的【实测】我没有复跑，因此这是设计审查，不是代码或性能验收。

## 一、这次真正改好的地方

| 位置 | 我的评价 |
|---|---|
| **§4、§5.3：恢复语义** | 把"执行至少一次""已提交处置去重""进程崩溃而非主机断电"分开了。这比笼统说"零重复零丢失"可信得多。 |
| **§5.1：两个进程** | G 留着展示积压，W 被杀后恢复，架构和演示互相服务。对个人项目来说，比先堆多个服务更合理。 |
| **§9.2：增加 B+ 对照** | "判官＋全部证据一次性输入"是很有价值的对照，能区分收益来自证据增加，还是 agent 的调查过程。比只比较"有 agent／没 agent"严谨。 |
| **§6.6、§8.4：标注边界** | 明说是模拟审核员，并增加独立人工抽审，解决了上一版最容易被质疑的真实性问题之一。没有外部审计时也不掩饰，这点应保留。 |

底座选择也有公开依据：当前官方文档确实提供 Pi 的 classifier 注册、durable 恢复，以及 Clef-flash 图片输入。但这只能证明接口方向有依据，**不等于你锁定的版本和中转站组合已经验证成功**。

## 二、优先修改的六处

### 1. §5.3、§6.4、§6.6：幂等设计可能挡住合法的申诉改判

目前同时出现了"`content_id` 先写者胜"和 `UNIQUE(content_id, policy_version)`，但系统又允许人审改判、申诉重审。

举例：同一内容按同一版规则，初审下架，申诉后放行。**这是两次合法审核，不是重复执行。**按目前描述，第二次可能被唯一约束挡住。

建议明确：

**用 `review_id` 标识"一次审核"。重试复用它，申诉和重审新建它；同一次处置去重，不同审次允许追加新裁决。旧事件迟到时，不能覆盖较新的有效裁决。**

另外，`session.sqlite` 与 `app.db` 谁是最终处置事实源，还需要写死。现在"durable 文档→outbox→app.db"和"决策＋处置＋outbox 同事务"的描述之间，事务边界不够清楚。

我的建议是：**`app.db` 作为唯一业务处置事实源，处置、业务终态和 outbox 在其中同事务提交；durable 保存执行进度，重试时查询已提交结果。**Outbox 本身仍可能重复投递，必须依靠消费端幂等和顺序控制。

**这是目前最值得先解决的问题。**

### 2. §6.3、§7：热更新不等于规则版本隔离

你写了 G 热加载、W 重装同名扩展，但没有明确：**正在审核中的内容，到底继续执行旧规则，还是中途切到新规则？**

这不是纯理论问题。当前 Pi 官方 README 明确说明，工具和 hooks 会在任务执行阶段解析配置，扩展变化可能影响模型已经发出的工具调用。

因此需要增加一条契约：

> 每个审次固定规则、校准配置和证据快照版本；灰度决定新审次用哪个版本，不能让同一次审核前后混用。

**规则更新优先作为数据版本切换，不要默认通过重装扩展实现。**模型升级可以保留，但必须记录每次调用实际使用的模型。

### 3. §6.2：当前视觉级联有直接漏审路径

文档写的是：文本不确定，或者带图且文本极短，才送视觉判官。

这会留下一个很直接的反例：

> 一段正常长文＋一张违规图片。文本判官很确信正常，于是整条内容跳过图审。

应改为：**含图内容要被自动放行，必须完成必要的图片检查；更昂贵的视觉复核才按疑似触发。**已经确定要拦截的内容，可以按策略提前结束，不必浪费后续调用。

这不是调阈值能解决的问题，是路由逻辑问题。

### 4. §5.4、§6.4、§12：容量、背压和 fail-closed 还没形成闭环

文档目标是快判 100 条/秒、agent 约 20 并发，但这些数字还没有通过分流比例和平均耗时关联起来。

举一个**假设计算，不是实测**：

`100 条/秒 × 3% 进入 agent × 平均 10 秒 = 30 个在途任务`

这已经超过 20 个并发。这里用的是假设的**平均耗时**，不是把 p95 当平均值。

因此必须分开报告：**接入速度、快判完成速度、完整审核完成速度**。不能因为回放器成功写入 100 条/秒，就认为系统能稳定完成这个吞吐。

背压部分还有一个空缺：agent 队列超过 H 后改送人审，那么 agent 队列可能不再涨到 2H，反而是人审队列持续增长。应按**总未完成量和各队列容量**决定暂停，而不是只盯 agent 队列。

同时补清楚：转人审期间内容是否暂不可见；模型一直不返回时如何主动超时；超时后迟到的结果如何禁止处置。**"最后会 release"还不等于已经 fail-closed。**目前 hooks 描述尚不足以回答这些问题。

### 5. §6.2、§6.6、§9.2：评测进步很大，但仍有几处结论写得过满

**校准门槛不能只看数量。**"样本 ≥200 用 isotonic"和"正式支持数 30"没有给出适用依据。30 条可以作为"生成候选阈值"的流程门槛，不能直接视为安全上线的统计保证。

scikit-learn 官方文档明确提醒 isotonic 在小样本上容易过拟合，给出的经验参考是约千条以上；这也不是新的硬门槛，而是说明你不能机械地在 200 条时切换。

**"零样本≈微调"不能直接推出"可以替代重训"。**它只能支持当前规则和测试分布下未观察到明显差距；要说"不掉能力"，需要预先定义可接受差距，并看区间，而不是只看结果接近。

**"50 次 kill ×20 条在途"不能自动当成 1,000 次独立试验。**同一次崩溃里的任务共享故障条件。零重复可以如实报告，但故障率区间必须说明统计单位和独立性假设。

此外，冻结样本 ID 之后，还要防同线程、同账号、近重复样本跨集合，以及"未来人审结论"进入 agent 可查历史。你已经做了合成捷径审计，但这两类泄漏需要单独检查。

### 6. §11.1、§11.2：MVP 与周计划直接冲突

§11.1 的 MVP 包含 Clef-flash、规则影子切换和最简人审；但周计划把视觉和人审放在 W4，把完整规则治理放在 W7。

而且 **2026 年 10 月 8 日到 10 月 22 日只有 14 天间隔**，不是完整三周开发期。

我的判断是：**你的排期仍然让"选模型、做微调"占了过早的位置，而核心审核链路还没有验收。**对这个求职目标，先微调 Laya 的价值，不如先证明一次完整审核能够恢复、正确处置、拒绝越权。

10 月 22 日版本建议只保留：**短文本、一个先做透的类别、一个判官、一个 agent、必要证据工具、审次与处置账本、恢复、基本权限门和最简指标。**保留规则版本固定与切换；图片、微调、完整灰度、阈值回流、多模型横评后移。这是调整交付顺序，不是否定最终范围。

## 三、预算和宣传怎么评价

**预算不是当前最大风险，但它只能支撑分批开发和实验，不能默认支撑持续高流量运行。**

Cloudflare 当前定价确实支持每天 10,000 neurons，按 Clef-flash 的价格换算约为 **122 万输入 token【按官方单价计算】**；这不是固定图片数量或吞吐保证。

Modal T4 当前约 **0.59 美元/GPU 小时**，20 美元约对应 **34 GPU 小时【抵扣前计算，不含 CPU、内存】**。加载模型和缩容前保活也计费。因此"小批实验可能够"，但不能仅凭 scale-to-zero 就把费用写成"免费"。

还有两处文案应收紧：

| 位置 | 修改意见 |
|---|---|
| **§0：行业差异化** | "业界都把工具当附件""开源项目要么分类器、要么没数字"没有被这份文档证明。改为陈述你实际实现的机制，不需要靠贬低整个行业证明价值。 |
| **§9.3：云厂商对照** | UNMAPPED 不硬凑是对的，但必须报告排除比例，并让横向比较使用共同可比样本，不能各自在不同子集上算分再并排。论文公开数字应标为背景参考，而不是同条件结果。 |

## 最终评价

**我支持这个项目继续做。它已经具备展示 harness 能力的结构，不是简单套一个模型接口。**但真正能增加说服力的，不是再增加判官名单，而是把"重试、改判、热更新、超时"同时发生时的正确性做扎实。

**下一步只解决一个难点：审次与处置语义。**先跑通"初审下架 → 申诉放行 → 重放旧事件仍保持放行"，再在提交边界插入 kill。这个测试能同时暴露当前幂等键、两库职责和事件顺序的问题，比先做大规模判官横评更值得。
