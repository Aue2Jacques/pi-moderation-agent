# 第十一轮外部审查：方向与优先级（基于 bbe6340）

来源：外部审查员，2026-10-07，用户转贴。原文要点照录（审查员沙箱里的验证包未入库）。事实性说法逐条核对全部属实，见 `docs/dev-plan-2026-10-07.md` 附录 A。

---

## 结论

**目前确实有方向偏移，但不是项目选错了，也不是应该换掉 Pi。偏移主要在开发优先级：已经投入很多精力证明"系统不会乱写、流程能够结束"，却还没有证明"agent 能把一类疑似内容真正查清楚"。** 同时，开发开始围绕 Jev 的分数波动、确认调用和阈值展开；这些需要研究，但不应该变成项目主线。**建议暂停扩展功能，把主线收回到：有预算的证据调查，如何得到正确、可提交的审核结论。**保留现有事务、恢复、版本和权限机制，修掉明确缺口；不要推倒重写。

## 一、现状

校准入口（strict 默认、identity 显式）、图片边界（含图转人工）、规则版本（按审次加载已存策略包）、CI 规则测试（正式入口接通）、恢复测试（J、D 点）、完成声明（四态）——上轮问题已有实质修复。CI：65 unit、39 harness 通过；契约 7 条过 6 条，因 `ABUSE-001/c5` 变红。问题已从"完成标签夸大"转为：**工程机制逐渐扎实，但业务决策语义、agent 的工作方式和效果验证，还没有成为真正的中心。**

## 二、方向偏在哪里

1. **更像"模型不断尝试满足提交条件"，而不是"审核员有目的地调查"。** 初始上下文没有交代为什么进入疑似、哪条规则卡住、缺什么证据、哪些证据可取得、何时继续调查已无意义；这些往往在 `dispose` 被拒后才从错误详情返回。13 条 evidence_gap 中 12 次提交被拒后才释放——是定位线索，说明需要检查 agent 是在补证据还是在试探提交协议。**权限门必须保留，但不应成为 agent 获知审核状态的主要接口。**
2. **"安全不变量"与"效果策略"被混为一谈。** 不能提交别的审次、过期租约不能处置、规则版本不能混用、裁决不能重复执行——由代码保障。是否每次放行都双确认、同调用还是分开调用、取平均还是其他聚合、阈值在哪——是需要实验验证的策略。前几轮审查也过于集中在"再加一道约束"，确认机制被升级为全局硬要求却没有先证明增量收益，应重新作为可验证策略。
3. **不应因"大厂有"就补一整套审核产业链。** 小分类器兜底、蒸馏回路、案例检索不是当前求职短板；行业报告仍保留已被更正的"Jev 基本确定"结论。暂不新增小模型级联、蒸馏导出、多判官、案例知识库。先回答：**对于明确需要上下文的疑似内容，agent 能否比固定取证工作流少查一些证据，或更准确地完成裁决？**

## 三、最影响业务成立的四个问题

1. **规则问题、例外与最终裁决的语义未统一。** 例外成立只能让 blockSupport 为 false，不能让 passSupport 成立；"规则高分 + 例外确认引用举报 + 其他齐全"结果是既不能下架也不能放行。建议明确组合语义：事实判断 → 例外核验 → 净违规结论 → 处置，用一张小型决策真值表。另：两条规则分别支持下架与限流时 `allowedActions` 同时包含两者，模型可挑较轻处置；应由策略确定冲突合并规则。
2. **不同原因的"疑似"进了同一条 agent 路径。** 缺上下文（agent 可能解决）／缺校准、通道或策略包（agent 不能解决，应降级或直接转人工）／证据完整但在争议区（有限复核，没有新信息就停）。黑名单、频控触发后创建审次时没有保留"为何转入"。
3. **判官稳定性实验在承担它不能承担的结论。** 同一输入 50 次中 13 次达阈值，不是 50 条违规内容上的召回率。缺的是不同内容的已知标签，以及阈值变化对误放、误拦、覆盖率、转人工量的共同影响。校准使概率与频率一致，不是把分数推过阈值。建议冻结题面，在同一份固定开发集上比较措辞、打乱、聚合与阈值，而不是每修一处重录几个例子。调用两次不等于独立证据。
4. **防注入测试与内容审核标签混在一起。** c5 是指令式文本，不是辱骂；正常分类为 pass 不代表被注入攻破。拆成：按业务规则 gold 判断；验证版本、证据归属、工具权限、提交约束不能被改变；有／无注入的配对测试看误放与误拒。若要把"操纵审核系统"作为独立规则，应明确增加，不能塞进 ABUSE；不建议加关键词补丁让 CI 变绿。

## 四、必须修的代码问题

1. 成本修复仍会遗漏同一 generation task 的后续请求（`first_usage` + `INSERT OR IGNORE`）；应把逻辑任务去重与物理请求计费分开，加"失败后成功"的独立费用验收；部分测试用同一个 `spentFromLedger()` 同时算实际值和期望值。
2. 明确要求检查 W 时，W 不可达仍可能返回成功。
3. 重启恢复没有复用准入上限（`start()` 对所有可接管会话发 active grant）。
4. 校准桶键（judge × rules_ver × scene × n_options）没有问题标识，同场景同选项数的文件会被 `Map.set()` 静默覆盖；拟合前要明确按问题校准还是共享校准器，并拒绝重复桶。
5. 证据工具与输入指纹不准：账号历史先取 5 条再计数，合成事件里的 `prior_ruling` 不进计数；`runJudge()` 输入指纹只算 content-bearing 证据，却把 rule/judge 的 `model_view` 也发给判官。

## 五、接下来只推进一条主线

保留 Pi、G/W、审次账本、租约、outbox、受控工具和测试；暂缓新增判官、训练、图片、完整灰度、后台美化、云厂商横评。

| 顺序 | 交付 | 通过条件 |
|---|---|---|
| 1 | 统一审核语义与疑似路由；修正注入测试归属 | 引用举报得到规则规定的结果；缺校准不空耗 agent；多规则不任由模型挑轻处置 |
| 2 | 小型、有标签的业务案例池（60–100 个起步）；ID 不泄漏类别；原始标签与上下文任务标签分开；模型标签标明来源 | 能判断每次审核是正确、错误、合理转人工，还是系统无法完成 |
| 3 | 简化 agent 审核接口：初始任务带疑似原因与待核验项；judge 返回可行结论与缺失项；确认、缓存、去重由运行层管理 | 不靠反复 dispose 报错发现规则；同证据不重复调查；缺证时知道停止 |
| 4 | 最小 A/C 主比较：同模型、规则、证据环境、预算、截止 | 质量、自动完成覆盖率、转人工量、工具调用数、成本、时延的对照；允许出现不利结果 |

## 六、最终判断

不换项目，不继续围绕 Jev 的几个分数调整整套系统。要讲清楚的是：**一个疑似任务为什么值得交给 agent；agent 查到了什么新事实；这些事实怎样依规则改变裁决；这个过程相对固定工作流是否值得付出成本。**下一批提交的重点是"裁决语义＋疑似原因＋一组可验证的上下文案例"，不是降低 0.90 阈值、增加确认次数，或接入另一个守卫模型。
