这版已经有真正的开发规格，而不只是功能清单。

| 部分 | 判断 |
|---|---|
| **业务逻辑集中在 core** | G、W、人工提交共用业务写入函数，能避免多个入口各写一套校验。 |

## 二、六个必须先修的问题

以下编号均针对 **开发文档 `dev-doc-v1.md`**。

### P0-1｜§5：放行检查验证了"证据齐全"，却没有验证"证据支持放行"

目前放行条件是：

```text
covered(evidenceIds) 覆盖 required
并且 noOpenGap(evidenceIds)
```

这里没有明确要求：判官调用成功、校准有效、风险低于放行阈值，以及不存在仍然有效的拦截依据。下架条件中的 `exceptionsChecked` 也只描述了"每个例外都有核验证据"，没有明确**核验结果是否允许下架**。

**【已验证反例】**给出一条"ABUSE 检查成功、风险概率 0.99"的完整证据，按当前放行伪代码，结果仍然是 `true`。

这意味着，模型不需要伪造证据，只要拿着完整的高风险证据调用 `dispose(pass)`，当前条件就没有明确阻止它。

**建议固定实现：**

`core` 根据审次绑定的规则、可信判官结果和必要证据，计算：

```text
allowedActions = 当前审核依据实际允许的动作集合
```

模型提出的动作必须属于这个集合。证据 ID 只是引用，不是授权本身。

同时，`judge_call` 应能核对**本次输入内容、证据快照、判定问题和模型版本**。目前表里没有 `evidence_ver` 或输入指纹，仅凭同一个 `review_id` 和规则版本，不能证明两次调用使用了相同审核依据。

**验收必须同时包含：**高风险证据不能放行；成立的豁免不能被下架；正常低风险证据能够放行。不能用"全部转人工"通过测试。

### P0-2｜§7.3、§8.1、§8.3：恢复顺序和租约衔接存在冲突

这里有三个具体问题。

**第一，先恢复，再准备恢复所需状态。**
§7.3 第一步调用 `harness.resume()`，第三步却要求"在续跑之前"重建租约。§8.1 的示例也在打开后直接 `resume()`。

Pi 官方接口说明还明确指出：不仅 `resume()`，`submit()`、`abort()`、等待任务等操作也会启动调度。因此，不能认为"还没手动 resume，所以提前 abort 一下是安全的"。

**第二，租约暂时拿不到，不等于任务已经被撤权。**
进程刚被杀就重启，旧租约可能还没到期。按 T3 的条件，新进程暂时拿不到租约；但 §7.3 把 T3 失败统一处理成 abort，会把一个本应等待接管的任务提前终止。

**第三，C 崩溃点的业务已经完成，却可能无法补齐 durable 收尾。**
T4 已提交、memo 未提交时，`review.state` 已是 `disposed`。恢复代码主要重建 `investigating` 的租约映射，但工具重跑又依赖这张映射。这样 H-03 所要求的"读回裁决、补 memo"，没有一条完整的执行路径。

**建议固定启动顺序：**

```text
确保只有一个 W
→ 打开存储，暂不触发调度
→ 对账并分类审次
→ 建立恢复映射、执行资格和并发限制
→ 再允许调度
```

分类至少区分：已裁决、已转人工、租约尚未到期、允许重新接管。

其中，**读取已提交裁决并补收尾，不是再次申请处置权限**，应有独立的恢复路径。

还有一个必须防住的风险：不要让旧调用在返回时查询"当前最新 attempt"，从而自动获得新租约。执行资格应绑定到具体执行调用；真正的恢复重放可以重新授权，旧调用的迟到结果不能被换上新代次。

**这一项需要最小 Pi 原型验证，不能只靠文档推导通过。**

### P0-3｜§4 T2/T2′/T9、§6.1：唯一审次序号不等于请求幂等

T9 写的是：

> 新序号取 `max(seq)+1`，依靠 `UNIQUE(content_id, seq)`，并发申诉只会有一个赢。

**这个结论不成立。**在 `BEGIN IMMEDIATE` 下，两次请求可以先后成功：第一次创建 seq=2，第二次随后读取最新值，再创建 seq=3。

**【已验证反例】**我按这个条件执行两个并发请求，得到的序号就是 **2 和 3**，两个都成功。

真正需要解决的是：

> 同一次申诉请求提交成功，但响应丢了，客户端重试，是否仍然返回原来的审次？

**建议增加稳定的触发请求标识**，例如 `trigger_request_id`，并明确：

```text
同一请求标识＋相同请求内容 → 返回原审次
同一请求标识＋不同请求内容 → 拒绝冲突
新的申诉请求标识 → 分配新序号
```

初审同样需要稳定标识，不能因为 G 重试时路由结果变化，就从 `fast` 变成另一个新的初审。

此外，T2/T2′ 应明确把 **intake 完成标记与审次创建／裁决提交**衔接起来。目前事务清单没有包含 intake 的完成写入，G 在提交后崩溃时如何识别已经处理过的接入任务，还没写完整。

**验收：**在"业务已提交、客户端或队列尚未收到确认"的边界重复请求，仍然只有同一个初审或申诉审次。

### P0-4｜§2.2、§4 T10：release 事件可能挡住同审次的人工裁决

outbox 同时包含 `release` 和 `ruling`，二者使用相同的审次序号；T10 则统一按：

```text
seq > 已应用最大 seq
```

判断是否应用。

**【已验证反例】**

```text
r1 release，seq=1 → 应用
随后人工提交 r1 ruling，seq=1 → 不是更大的序号，被忽略
```

业务库可能已经显示"人工放行"，模拟下游却没应用放行。

**建议明确分开：**

| 事件 | 消费规则 |
|---|---|
| `release` | 人审流转通知，按事件 ID 去重，不推进内容裁决序号 |
| `ruling` | 内容处置，按事件 ID 去重，并与已应用的裁决序号比较 |

模拟消费端还应有**实际处置状态**，不能只记录一个 `applied=1` 就当作下游动作完成。消费记录与模拟处置状态要同事务写入。

人审提交成功后，`human_queue` 的记录也要在同事务删除或关闭。目前 S9 的写入清单没有这一步。

**验收：**release → 人工裁决 → 重放 release → 重放旧裁决，下游最终状态始终与最新有效裁决一致。

---

### P0-5｜§7.4、§8.4：预算计数不能在整轮工具结束后才更新

文档依靠 `afterTools` 一次增加整轮工具数量，同时认为 `sequential` 能让预算计数确定。

但顺序执行不等于每个工具执行前都会更新计数。

**【已验证反例】**已经使用 11 次，上限 12 次，模型一轮发出 3 个工具调用。若这 3 次执行前都看到旧值 11，最后一次性加 3，就会执行到 **14 次**。

**建议固定为：**

每次工具调用执行前，按稳定调用 ID **原子占用一次额度**；调用恢复重放时，不重复占用同一个逻辑调用的额度。费用也应有可对账的调用记录，而不是简单在回调里累加。

费用上限还要明确是硬预算还是软预算。当前方案是调用结束后才计费，不能保证单次请求不会超过剩余额度。更稳妥的方案是**调用前保守预留，结束后结算；超时但无法确认计费的调用，单独标为未知或估计**。

另一个相关问题是 `onYield` 的"最多继续一次"：Pi 的 hook memo 属于所在任务，不能直接当作整个审次的全局计数。应把该限制绑定到审次或整个 run，否则新 generation task 可能重新获得一次继续机会。

**验收：**一轮多个工具、工具重放、计费回调重放、模型连续不提交结论，都不能绕过对应限制。

### P0-6｜§8.3、§10：证据必须既能支持语义判断，又确实来自固定快照

这里有两处需要一起修改。

**模型可用的证据不足。**
`get_thread_context` 的投影写成"只含 content_sha、长度、类别线索"，`judge` 又使用证据投影复判。哈希和长度不能提供评论的上下文语义；"类别线索"具体是什么、由谁生成、费用算在哪里，也没有定义。

**快照版本目前更像标签。**
规则写了 `evidence_ver`，但工具仍描述为读取 content 表、查询相似内容的当前 `effective_action`。没有说明这些查询如何回到审次固定的历史状态。仅记录一个版本字符串，并不会让实时查询自动变成快照查询。

**建议 MVP 采用一个明确且简单的实现：**

每个审次绑定不可变的证据清单和快照；工具只能从这份快照中按需读取。输出分成两种：

| 接收方 | 输出 |
|---|---|
| **模型／判官** | 完成判断所必需的受控原文片段、结构化事实和来源引用 |
| **日志／仪表盘／普通 API** | 固定白名单字段，不包含自由文本摘要或原文 |

开发者不查看样本，**不等于模型也不能获得必要上下文**。这两个边界必须分开。

尤其是 §6.1 的普通详情接口仍返回 evidence 投影，而投影中包含 `summary`。只删除 `text/body/reason` 字段，不能保证摘要不会复述原文。

**验收：**创建审次后修改在线历史，旧审次的工具结果仍保持不变；模型能读到必要语义，普通接口和日志看不到这些文本。

## 三、还需要补齐的实现细节

这些不要求换架构，但应该在对应模块开始前写清。

| 位置 | 问题 | 建议落地方式 |
|---|---|---|
| **§2.2、§3.3：待审初态** | `content_state` 要求有效动作和序号非空，但首个待审内容还没有裁决。仅更新 visibility 会找不到行。 | 明确"尚无裁决"的表示，例如动作为空、序号为 0、可见性 hidden；不要伪造一条 pass 裁决。 |
| **§5：拒绝审计** | "失败即回滚"与"每次拒绝写 audit"没有说明事务关系。 | 业务回滚后提交独立拒绝审计，或提交一个不含业务修改的审计分支。审计不能跟着回滚消失。 |
| **§5 与 H-06：幂等返回** | 第 2 步直接返回已有裁决，H-06 却要求迟到提交返回 `E_LEASE_LOST`。 | 区分恢复读取与新提交，或调整测试断言；核心不变量是不能新增或覆盖裁决。 |
| **§9.1：logprob 解析** | 未定义选项 token 缺失、多 token、前导空格、概率质量不完整时的行为。 | 写成适配器契约；不能把未返回的选项直接当概率 0，再归一化出虚假的高置信度。 |
| **§2.2、§13：费用单位** | 数据库预算以美元计，项目成本目标存在人民币口径。 | 单价、预算、展示分别标单位，换算进入固定版本的价格配置。 |
| **§15：数据库锁验证** | "两进程不报 SQLITE_BUSY"不能作为普遍保证。 | 测试主动持锁、超时、有限重试、背压及心跳延迟；事务内不等待模型或网络。 |

前面三项中，待审初态和拒绝审计已经通过最小 SQLite 验证复现：前者会遇到 `NOT NULL` 约束，后者在同事务回滚后审计行数为 0。相关设计分别来自 DDL、事务和校验章节。

数据库选型本身不用改。需要注意的是：SQLite 同时只能有一个写事务，而 Node 的 `DatabaseSync` 是同步接口；较长的锁等待也会阻塞所在进程的事件循环。**因此要验证的是"发生竞争后仍正确、可恢复"，不是假定竞争永远不发生。**

## 四、规则治理和评测还差最后一层"执行准确性"

### 1. 新规则不一定能复用旧判官分数

§10 的影子回放写成"用新规则在已有 judge_call 与 evidence 上重算三态"。这只对一部分变化成立。

**应明确区分：**

| 变更 | 是否可以直接复用旧分数 |
|---|---|
| 只改阈值、路由或确定性动作映射 | 在模型问题和输入均未变化时可以 |
| 改规则含义、例外、判定问题或模型输入 | 必须基于固定证据重新调用判官 |

否则演示里虽然显示"规则已切换"，模型实际回答的仍是旧问题。

发布门槛也不能只要求"最近一次 gate 通过"。通过记录必须绑定**准备发布的规则、校准和模型配置**，避免 A 版本通过测试，却给 B 版本放行。

### 2. 录制响应的 contract tests 不能证明语义规则生效

§12.4 用录制判官响应运行规则测试，这适合检查策略代码，但不能证明改过的规则文字会被真实判官正确理解。

保留两层即可，不需要增加大型平台：

**日常 CI** 使用录制响应验证结构、路由、阈值和权限；**规则发布前** 使用真实判官验证变化的语义及必要回归。

### 3. A/C 还需要对齐执行限制

§11.3 中，A 只明确复用提交校验的第 7—11 步，C 则运行完整准入、截止和预算控制。这样可能让 A 实际不受相同限制。

建议 A 仍然走相同的机器审次生命周期和预算、截止检查，只是取证顺序固定。**主比较应主要改变"固定取证还是动态取证"，不能顺便改变提交权限和资源限制。**

另外，六个主指标还需要写出分母。例如，以下两项不能都叫"漏放率"：

```text
被自动放行的违规样本 / 全部违规样本
被自动放行的违规样本 / 全部自动放行样本
```

建议保留清楚命名的两种口径，转人工和未完成样本另外列出，不能悄悄从质量统计中消失。

### 4. 环境隔离要包含快照和 session.sqlite

目前只明确复制 app.db。若基线数据库仍处于 WAL 活跃状态，直接 `cp app.base.db` 可能漏掉尚在 WAL 中的提交；应使用一致性备份，或在确认停止写入并完成处理后生成基线。SQLite 官方也将在线备份 API 用于这类一致性复制。

每个实验运行还应指定独立的 `SESSION_DB`、输出目录和缓存命名空间，不只独立 `APP_DB`。

## 五、现有测试清单还不能证明"零丢失"

§11.5 主要检查：

```text
同 review_id 的 ruling ≤ 1
同 event_id 的 applied ≤ 1
```

这些是"不重复"的必要检查，但 **0 也满足 ≤1**，所以仅靠这些条件，不能证明任务没有丢失。

建议补一条总量守恒检查：

> 每个已经确认接收的唯一请求，都必须能归入已裁决、待人审、明确等待／重试中的某一类，不能无记录消失；故障解除后，应完成的测试任务必须最终完成。

同时验证三层状态：**业务裁决、durable 收尾、模拟下游实际状态**。只检查 `content_state` 不够。

当前最值得补进测试目录的是以下六条，不需要再铺一大批泛化用例：

| 用例 | 要证明什么 |
|---|---|
| 完整高风险证据下请求 pass | 权限门检查结论，不只是证据数量 |
| 重复申诉请求 | 同一业务请求不会创建两个审次 |
| release 后同审次人工裁决 | 通知事件不会挡住内容处置 |
| 旧租约未到期时立即重启 | 暂时不能接管不等于任务应被取消 |
| T4 已提交、memo 未提交时恢复 | 已完成业务可以正确补收尾 |
| 同轮多工具及回调重放 | 预算不能超发，也不能重复记账 |

## 六、CI 和排期需要做实，不宜继续写成"看起来能跑"

### CI 示例目前有确定错误

§12.6 这行：

```yaml
- uses: actions/setup-node@v4 { node-version: 22.23.3, cache: pnpm }
```

**【已验证】无法通过 YAML 解析。**参数需要放在独立的 `with:` 下；Python job 还缺少运行环境和 checkout 步骤。

CI 还要具备不依赖私有数据和密钥的测试夹具。仓库只存数据集行号，不能自动保证另一台机器能运行 contract tests。

此外，"连续 20 个中文字符扫描"只能是提示风险的启发式规则，不能称为正文不泄漏的机械保证：它既可能拦住正常规则和提示词，也会漏掉短文本及其他语言。真正的边界应来自输出白名单、测试夹具管理和访问控制。

### 14 天表需要按依赖关系调整

当前 D5 做恢复验收，D9 才完成动作证据校验，D12 才补合成数据。按这个顺序，早期恢复测试很可能只证明简化实现能跑通，之后仍须在完整校验下重跑。

建议不再重新猜一套精确日程，先把开工顺序固定成：

```text
接口与类型编译、无害测试夹具
→ 审次创建、提交校验、消费端语义
→ 最小 Pi 恢复与租约验证
→ 一个真实判官和一个真实主模型
→ 数据回放与最简界面
→ 故障、效果及演示验收
```

图片、多模型横评、完整灰度仍按原计划后移。**不能为了赶演示，把尚未成立的恢复或权限检查包装成已经完成。**
