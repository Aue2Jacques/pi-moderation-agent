## 二、从 Agent / Harness 找工作的角度，项目现在处在什么位置

### 1. Harness 方向：设计深度已经足够，接下来缺的是实现证据

你现在的三条主线——有预算的证据调查、不可靠执行下的可靠处置、规则与证据约束下的决策——已经形成了一个明确的技术中心，并且区分了 Pi 提供什么、自己负责什么。

我的评价是：**这比再增加多 agent、通用记忆或一批 provider，更值得投入。**

尤其是"超时后撤销提交资格""旧执行结果不能覆盖新裁决""模型不能自行挑选有利规则"，都能支撑具体的工程讨论。它们不只是数据库功能，也不只是提示词功能，而是模型执行与业务系统之间的约束。

但求职时应定位为：

> **基于 Pi 构建的、面向内容审核场景的 Agent Harness 工程原型。**

不能把它说成"从零实现 durable runtime"，也不宜说成"通用 Agent 平台"。你的方案主动复用了底座，并且没有承诺跨机器调度、多租户或通用沙箱；这是合理取舍，不是缺陷。

### 2. Agent 方向：已经有证明价值的方法，但价值本身还没有得到证明

**现在不能提前认定动态调查一定胜过固定工作流。**

好在你已经允许这样的结果：C 与 A 质量接近，但取证更少、成本更低，也算有价值；如果质量、成本和延迟都没有优势，就如实报告。这是合适的工程判断标准。

这里真正需要实现出来的，不是"一条内容调用了很多工具"，而是：

> 不同内容触发不同的调查路径；该补证据时补，该停止时停止，缺证时不编造事实。

这也符合公开 agent 工程方法对动态工具使用和固定工作流的区分：复杂度应由实际收益支撑，而不是由框架或调用次数支撑。

### 3. 最大风险仍然是完成度，而不是深度不够

MVP 已经收窄到短文本、ABUSE、一个判官、一个主模型和必要的可靠性机制。这个范围应该保持。

不过 W7 仍集合了压测、完整灰度、发布门槛、反馈回流和完整演示；W8 又包含云厂商对照、文章、报告和评测卡。**我的工程判断是：后半程仍偏满，不能把"已排进周计划"当作"已经有完成保障"。**

因此，不再给项目加深度。优先把已有深度变成可运行代码、可复现测试和可解释结果。

## 三、冻结前必须补清楚的两处契约

### 1. §5.2—§5.4、§6.6：机器超时以后，人工怎样合法提交？

当前文档同时规定：

- 人审在**同一个审次**上形成裁决。
- 提交裁决必须满足：未过截止、仍持有当前执行租约、判官检查完整。
- 机器超时后撤销租约，并将审次 release 到人审。

**人工提交的独立条件还没有写出来。**按照通用提交条件直接实现，机器超时后，人工也可能因为"已过截止、没有机器租约"被挡住；人工纠错也不能被要求必须服从被纠正的机器判断。

建议固定为：

> **机器审核截止时间只终止自动审核权限，不终止人工裁决资格。转人工后，旧机器执行代次永久失效；人工通过独立授权路径，在待人审状态下提交裁决，不继承旧机器租约和机器截止条件。已提交裁决需要纠正时，新建审次，不覆盖旧记录。**

另外，**转人工不能依赖 `abort` 成功返回。**建议先在业务库原子完成撤权和转人工状态变更，再尽力通知 W 停止执行。W 已经死亡或不响应，不能阻止人工接管。

对应的验收只需明确这一条：

> **机器超时 → 转人工 → 人工放行成功 → 旧机器结果迟到 → 拒绝旧结果，保留人工裁决。**

这不是新增功能，而是让已经承诺的人在环流程闭合。

### 2. §5.3、§6.2、§6.4：放行和提前拦截，不能使用完全相同的证据完整性要求

§6.2 允许"文本已经明确拦截时提前结束"，但 §5.3、§6.4 又统一要求裁决前"必查类别全部覆盖"。两者在含图、多类别场景下可能产生不同实现。

这里也需要修正我上一轮建议的精度：

**放行和下架都必须过权限门，不等于两者需要完全相同的检查覆盖条件。**

建议固定成动作相关的条件：

| 动作 | 所需依据 |
|---|---|
| **自动放行** | 完成所有适用的必查类别与模态，没有未解决的必要证据缺口 |
| **自动下架／限流** | 满足支持该动作的规则证据，并完成相关例外核验；不能跳过仍可能改变该裁决的必要证据 |
| **转人工** | 无法满足相应动作的条件，或达到预算、截止等边界 |

所有动作共同检查审次身份、执行权限、版本一致性和证据归属。这样既保留合法的提前结束，也不让 G 快判与 W 慢审形成两套隐含标准。

## 五、评测框架可以定，但开发文档必须落实三个执行细节

### 同一批疑似内容，不能各组自己挑

开发文档应规定：**先冻结同一个入口判官与路由规则，得到共同的疑似样本 ID，再让 A/B/B+/C 处理这批样本。**不能每组根据自己的结果挑一批疑似，再横向比较。

同时，疑似集结果只能说明第二层的价值。系统级报告还要包含快判直接放行、直接拦截的结果，因为这些路径上的错误不会被后面的 agent 自动纠正。

### A/C 主比较不能偷偷混入模型升级的收益

文档既要求 A/C 同主模型，又保留 C 的 `escalate_model` 工具。

**建议主比较关闭升级，固定主模型和总预算上限，报告各自实际消耗。**模型升级作为后续单独说明的实验，不混入"动态调查比固定取证好"的主结论。

这并不要求 A/C 消耗完全相同的 token；节省调用本身就是要测的收益。

### 各组必须从相同、互不污染的环境起跑

你已经规定跨集合的账号、线程、近重复和未来标签隔离，这是对的。接下来还需要在执行协议里规定：**A 组写入的裁决、历史记录和缓存，不能变成 C 组随后可查的额外证据。**

可以用独立数据库副本或只读证据快照解决，不需要新平台。
