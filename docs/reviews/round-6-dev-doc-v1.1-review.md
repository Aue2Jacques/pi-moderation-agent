## 结论

**v1.1 已经可以作为"最小技术验证"的基线，但还不能当作已经完全正确的开发规格，直接进入完整 MVP。**

这次不需要推翻项目、换底座，也不需要再增加功能。**应该结束大范围方案讨论，转为修正几个明确的实现契约，再用代码关闭反例。**

我另外做了 **9 个局部逻辑／SQLite 验证**，包含正向验证和反例。它们用于检查文档条件，没有运行完整 Pi 集成、开发机或真实模型。

## 二、仍需要关闭的六组问题

下面均按 **开发文档 v1.1 章节号**说明。"需要关闭"是指必须进入对应阶段的验收条件，不是要求在写第一行代码之前解决所有运行结果。

### 1. §7.3、§8.3、§8.4：恢复流程仍然存在互相矛盾的路径

目前关于尚未取得租约的审次，有三种描述：

**§6.3** 说放入 `pendingTakeover`，等待，不 abort；**§7.3 第 7 步**说恢复工具遇到未授权状态后 abort，接管后重新 submit；**H-20** 又要求"不被 abort"。更直接的是，§8.4 的 `afterTool` 在没有 grant 时直接返回，并没有执行 §7.3 所说的 abort。

**开发者照着不同章节实现，会得到不同的恢复语义。**

而且，只控制工具还不够。恢复的可能是一个已经进入模型请求阶段的 generation task，不一定先经过工具调用。当前代码没有证明：`pendingTakeover`、`revoked` 和 `finalize` 会话不会先发出一次模型请求。

这次核对 Pi 源码后，还确认了一个重要边界：

> **工具在 intent 后恢复时，直接重跑执行体，不会重新执行 `beforeTool`。**

因此，当前 `beforeTool` 中的租约、截止和预算检查，不能自动覆盖所有恢复路径。工具执行体或调用下游前的统一适配层，仍需检查执行资格。

**建议收口：**

MVP 先采用简单的启动屏障：完成恢复分类、租约处理和准入安排后，再允许相关任务产生外部调用。不要一边放开全部恢复任务，一边期待工具报错来阻止它们继续运行。

同时把不同模式写成唯一行为表：

| 模式 | 允许做什么 |
|---|---|
| `active` | 在重新检查资格后调用模型、工具和提交 |
| `pendingTakeover` | 等待接管，不产生新的外部调用，不向模型追加误导性的业务失败结果 |
| `finalize` | 读取已提交业务结果并完成收尾，不再调查 |
| `revoked` | 停止执行，不重新提交业务动作 |

这里还应区分 **正常恢复重放** 与 **主动中断后重新开始一个 input**。后者可以设计，但不能混在前者中，然后都称为"从原断点继续"。

**验收重点：**立即重启、租约尚未到期、生成请求待恢复、工具 intent 待恢复，以及 `finalize` 收尾，分别验证"有没有越权外部调用"和"最终能否完成"。

### 2. §7.5、§8.4、§11.5：`memo` 的两种用法有确定错误

#### 计数器用法错误

当前记账代码是：

```ts
const n = (await api.memo<number>("n", ctx)) ?? 0;
await api.memo("n", n + 1, ctx);
recordModelCall(`${conversationId}#${taskId}#${n}`, ...);
```

但 Pi 的 `memo(name, candidate)` 是**该名称尚不存在时才写入，之后返回首次写入的值**，不是可更新变量。实际类型定义明确写了这个语义。

**【局部逻辑验证】**按这个语义执行文档代码，连续生成的记账后缀是：

```text
0、1、1、1……
```

这既可能让同一响应的处理重放多记一次，也可能让后续响应因为 ID 冲突而漏记。不能通过 H-22 所要求的"不重复记账"。

**修改方向：**在实际模型请求发出前，持久化分配稳定的请求标识；同一响应处理重放复用该标识，真正重新发出的请求使用新的物理请求标识。不要用 hook 被调用了几次来推导请求身份。

#### 终态检查用法错误

§11.5 要求：

> durable 的 dispose/release memo 存在，当且仅当审次为终态或 human_queue。

但 Pi 的任务进入 `completing`／`terminal` 后，当前任务记录不再包含 memos；最终保留的是任务结果回执。

所以，**正常完成的任务也可能被这条对账规则误判为未收尾**。此外，G 快判直接完成、G 超时转人工等路径，本来就不一定执行 durable 的 dispose/release 工具。

**修改方向：**业务完成看 app.db；durable 完成看任务终态、结果条目和 submission 状态。memo 只作为尚未完成任务的恢复辅助，不承担永久收尾凭证的角色。

这两项属于明确的接口语义错误，应直接改，不需要继续论证。

### 3. §5.4：旧的疑似结果可能永久阻止 agent 后续放行

新的 `allowedActions` 已经堵住上一版"高风险证据也能放行"的简单漏洞。

但现在有两个同时存在的条件：

```text
每条规则取最新一次可信调用
同时，任何可信调用都不能落在疑似区间
```

后一条没有限定只看当前有效结果，按字面会检查全部历史可信调用。

**【局部逻辑验证】**假设规则放行阈值为 0.10：

```text
初判：0.70，疑似
补充上下文后复判：0.02，支持放行
```

最新结果满足放行，但旧的 0.70 仍在历史中，整个集合仍为空。只保留 0.02 时，放行才被允许。

**这会直接削弱 agent 的业务作用：补证据可以改变模型判断，却无法改变系统的放行资格。**

需要定义的不是"删掉旧分数"，而是：

> **哪一个判官结果是当前裁决依据，哪些只是历史记录，什么条件下新结果可以替代旧结果。**

建议按规则／问题和证据版本建立有效结果关系。补齐必要证据后的复判，可以按明确规则替代此前的缺证判断；相同证据反复调用产生分歧，则不能简单取最后一次低分。

验收应增加一对对称用例：**补证据后允许合理放行；同证据反复抽样不能靠碰到一次低分放行。**

### 4. §4 T11—T13、§7.5：工具次数限制与总费用预算还没有统一

增加 `tool_slot` 是正确方向，但现在至少有三处需要写实。

**第一，终结工具豁免没有落实到 T11 条件。**
正文说 `dispose/release` 不计次数，示例却仍统一调用 T11，而 T11 按非 blocked 行数计数。零费用不等于不计次数。

**【局部 SQLite 验证】**已经占用 12 次额度，再插入 release 的 slot，字面计数会变成 13。必须在 T11 中明确豁免，或使用显式的 `counts_toward_limit` 字段。

**第二，逻辑调用去重不等于实际费用去重。**
同一个工具恢复重放，工具次数不应重复计算；但它重新向外部模型发出请求，可能再次产生费用。现有一个 `tool_slot`、一次 settlement 的表达，不能完整表示这两件事。

应分清：

```text
逻辑工具调用次数
实际模型请求及重试次数
已知费用、估计费用和未确认费用
```

**第三，当前不能把总费用称为硬预算。**
文档明确承认主模型调用结束后才记账，但同时把预算汇总描述成硬预算，并宣称最多多花一次模型调用。这个上界没有覆盖恢复重发、下游自动重试和其他在途请求。

MVP 可以选择**工具次数硬限制、费用软限制**，但要如实命名，固定输出长度和重试上限，记录实际超出量。没有必要为了一个个人项目，提前承诺无法严格证明的绝对费用上限。

另外，内部逐调用费用用"整数分"偏粗：若调用费用小于一分，必须说明取整方式。建议内部用更细的整数单位累计，展示时再转元／分，避免成本对比被舍入规则主导。

### 5. §8.5：as-of 可以保留，但仅过滤时间戳还不等于不可变快照

**不要求你回到"每审次复制整份数据"的方案。**as-of 查询本身是可以采用的，只是目前保证条件不够。

当前查询依据是：

```text
created_at ≤ review.created_at
```

时间精度为毫秒。

**【局部 SQLite 验证】**审次创建后，又提交一条相同毫秒时间戳的裁决。旧审次重新查询时，这条后来提交的数据仍满足 `≤`，结果发生变化。

迟到入库、但业务时间较早的历史事件，也需要同样区分：**事件何时发生，与系统何时已经知道它，不是一回事。**

最小补充是让审次固定一个**可见入库／提交序号边界**；业务时间继续用于"近七天"等业务过滤。这样不用复制全部数据，也能阻止后来提交的数据进入旧审次。

还有一个需要明确的查询规则：

> 历史有效裁决，应取"在该边界内已经提交的最高审次序号"，而不是仅取完成时间最新的一条。

否则旧审次晚于新审次完成时，历史查询可能重新返回旧裁决。当前"最后一条 ruling"的表述不足以排除这种实现。

H-21 应覆盖**相同毫秒、迟到入库和审次乱序完成**，不只测试新增一条时间更晚的记录。

### 6. §4 T10、§11.5：下游的人审状态还会被晚到事件重新打开

T10 已经正确地让 `release` 不再推进裁决序号。

但现在规定的是：

```text
release → human_pending = 1
ruling → 更新 applied_action / applied_seq
```

没有写人工裁决后如何关闭下游的人审标记，也没有规定**第一次送达但已经过时的 release**如何处理。

**【局部逻辑验证】**按这些字段更新规则：

```text
release → 人工裁决
```

下游最终是 `pass`，但 `human_pending` 仍为 1。

即使补上"ruling 时置 0"，还有另一个问题：

```text
人工裁决先送达
此前的 release 第一次送达
```

它不是重复 event_id，仍会重新置 1。

**应按审次管理人审生命周期，而不是让任意 release 修改一个内容级布尔值。**某审次已形成裁决后，该审次晚到的 release 只能记为过时通知；多个审次的人审状态也不能互相覆盖。

对账还要区分**即时安全约束**和**队列排空后的最终一致**：

在 D 崩溃点，下游已经应用事件，dispatcher 还没写 ack，这是合法的暂时状态。不能此时要求：

```text
downstream.applied_seq == 已 acked 事件的最大 seq
```

最终一致可以在恢复、重投和确认完成后检查；过程中检查不重复、不倒退、事件可追踪即可。

## 三、评测框架可以保留，执行协议还需补四处

A/C 使用同一生命周期、预算、截止和权限检查；独立 app.db、session.sqlite 和缓存空间；指标分母单独列明——这些都已经明显改善，可以保留。

| 位置 | 尚未闭合的问题 | 修改要求 |
|---|---|---|
| **§9.1、U-10** | 解析器允许"匹配至少两个选项"就输出概率，但 U-10 又要求缺选项时 abstain | MVP 建议固定为：配置的选项未完整匹配，则 abstain；不要一边缺选项，一边按完整分类问题校准 |
| **§11.5 守恒** | 只从 `intake.status='judged'` 开始检查，无法发现一直卡在 received、从未生成审次的已接收内容 | 从所有已确认接收的内容／请求开始核对，明确每条的当前归属和最终去向 |
| **§11.4 延迟** | 自动完成样本的 p95 容易掩盖大量超时转人工 | 自动裁决时延、自动阶段终止时延、转人工率并列；超时样本不能只在延迟统计中消失 |
| **§12.4 夹具** | 拉取失败时 skip，并不自动保证门槛不能变绿 | 输出计划数、执行数、通过数、跳过数；必需夹具缺失时，对应验收不得通过 |

这些不是要求增加新的 benchmark，而是确保已有实验能回答你声称要回答的问题。

另有一个实际接口细节：`/restricted` 写的是 `X-Reviewer` 加 `X-Confirm`。确认标记不等于身份认证，应明确复用已有人工 token 的校验，而不是仅凭两个可填写的请求头开放原文。

## 四、开发文档目前还不够独立可用

v1.1 大量使用"同 v1.0"，但当前仓库里没有独立保存的完整 v1.0 文档，开发者需要自行追溯 Git 历史才能找到接口、示例和测试的完整定义。

**这比继续扩充附录更值得修。**选择一种方式即可：把仍然有效的内容并回 v1.1，或者显式链接到固定提交下的 v1.0，并精确说明继承范围。不能让"最新开发规格"依赖读者猜测哪些旧句仍然有效。

分阶段排期比原来的精确日程更合理，但阶段依赖还要对齐：阶段 2 要验证人工接管、恢复对账和下游一致，就需要最小控制循环与消费端测试驱动，不能直到阶段 4 才第一次出现这些部件。完整 HTTP 和界面仍然可以后移。

此外，hooks 中的 `api` 是 `HookApi`，公开类型并不包含工具执行 API 的 `conversation()` 方法。文档里的 `releaseAndAbort` 不应直接照搬工具中的句柄用法；建议由宿主控制循环执行取消，不在当前 hook 内等待自己的会话达到 idle。后者的实际取消行为需要在 Pi 验证中确认，不能只靠伪代码通过。

## 五、我的开工判断

| 阶段 | 本轮意见 |
|---|---|
| **项目方向、业务范围、三条技术主线** | **通过，不再扩范围** |
| **阶段 0：工程骨架、类型、夹具、CI** | **可以开始** |
| **阶段 1：core 语义实现** | 以本轮反例作为必须通过的测试，同时修正文档中的有效判官结果、预算和下游生命周期 |
| **阶段 2：Pi 最小验证** | 必须验证恢复授权、memo 正确用法、终态收尾；没有通过就不进入完整链路 |
| **阶段 3 以后：真实模型和 MVP** | 前述机制验收通过后再进入，不用演示成功替代正确性验证 |

**我不建议你再进行一轮全项目大改写，也不建议现在宣布"所有问题已经解决"。**

这版已经具备进入**有停止条件的验证开发**的基础。下一步的产出应当是一个小而完整的验证提交：固定判官响应、无害夹具、真实 SQLite、Pi 1.0.4，以及能够稳定复现和关闭上述反例的测试。动态 agent 的质量优势、实际费用和吞吐，继续留给后续真实实验。

从找工作的角度，**能解释并证明这些边界为什么正确，比继续写一份更长的"企业级方案"更有说服力。**
