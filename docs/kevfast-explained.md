# Kev 推理提速是怎么做的（kevfast 说明，2026-10-09）

> 面向复盘和面试准备：用大白话讲清楚每一步做了什么、为什么有效、实测多少、踩了哪些坑。数字都是单张 RTX 5060 Ti（16GB）上的单次实测，仅供参考。完整数据和复现命令见 [reports/2026-10-09-kev-inference-speed.md](../reports/2026-10-09-kev-inference-speed.md)，代码在 [python/kevfast/](../python/kevfast/)。

## 1. 一句话

开源判官 Kev-4B 原生推理每秒约 10 条评论。我们做了两类优化，同一张卡做到每秒约 60 条（对外 HTTP 服务约 50 条），单条约 40 毫秒：
- 一类是让每条评论要算的 token 少下来，从约 535 个降到约 67 个。
- 另一类是让显卡算得更快：FP8、去掉补齐、CUDA graphs。

辱骂、营销两题的区分度（AUROC）基本不变。

## 2. 先搞懂 Kev 原来怎么算

Kev 不生成文字，是一个"打分头"：输入一段"状态"和若干道选择题，一次前向计算就给出每道题每个选项的概率。它的输入格式是：

```
[状态：这条评论]  [题 1：规则全文 + 选项说明 + 决定位]  [题 2：……]  ……
```

- 题和题之间互相看不见：每道题是一个"分支"，只看状态和自己。
- 底座是 Qwen3.5-4B，混合结构：24 层线性注意力（Gated DeltaNet）+ 8 层普通注意力。

我们的快判每条评论问 3 道题（辱骂、营销、注入检查），每题再打乱选项"复问"一次，一共 6 个分支。

**测出来的问题**：
- 每条请求约 535 个 token，其中评论本身平均只有 26 个，其余都是规则原文和选项说明。
- 规则放在评论后面，每条评论都要把所有规则重算一遍。
- Kev 自带的缓存只在"同一条评论"再次出现时有用。
- 并发从 16 加到 64，吞吐几乎不变：显卡已经满负荷，多出来的请求只是在排队。

结论：瓶颈是每条要算的 token 太多，不是调度。

## 3. 每一步优化

按实测阶梯（`python -m kevfast.bench`，512 条测试文本，一批 32 条）顺序列出。每一步都是 kevfast 里的一个开关，可以单独打开或关闭。

| 步骤 | 开关 | 做了什么 | 为什么有效 | 每秒条数 |
|---|---|---|---|---|
| 起点 | — | Kev 原生格式，我们的引擎去掉补齐后 | — | 9.8 |
| ① 规则前置缓存 | `layout=rules_first` | 状态改成"规则块在前、评论在后"。规则块对每条评论都一样，算一次存起来（KV 和线性注意力的状态），每条评论接着它算 | 规则不再每条重算 | 18.9 |
| ② 短问题 | `questions=short` | 规则原文只放在缓存里，每道题只剩"规则名 + 选项名"（约 15 个 token） | 6 个分支每个从约 70 个 token 降到约 15 个 | 29.5 |
| ③ 去复问 | `confirm=off` | 不再打乱选项问第二遍 | 分支数减半 | 45.7 |
| ④ FP8 | `fp8=on/auto` | 矩阵乘法用 FP8（权重按行、激活按 token 动态缩放，`torch._scaled_mm`） | 这张卡 FP8 矩阵乘法 103 TFLOPS，bf16 是 51 | 60.5 |
| ⑤ 小批量单次计算 | `branch_mode=auto` | ≤ 8 条的小批量把"评论 + 题"拼成一行一次算完，不分两步 | 少一半算子启动 | 吞吐不变，单条 173 → 99 ms |
| ⑥ CUDA graphs | `cuda_graphs=on` | 小批量按长度分档，每档录制一次计算图，之后直接重放 | 去掉每个算子的启动开销（一次计算约 600 次调用） | 单条 → 37 ms |

其他做了、但不单列成一行的：

| 优化 | 效果 |
|---|---|
| 拼接不补齐 | 长短不一的评论首尾拼接成一条序列（fla 的 varlen 算子，每段带自己的初始状态），不再补齐到一样长。补齐浪费原来约 27% |
| 分词缓存 | 每条评论只分一次词，题目按题目缓存。CPU 开销每批约 45 ms，去掉后 55 → 59.6 条/秒 |
| 传 CPU 端的段长度给 fla | 避免每层同步一次 |
| 显存不足时拆半重算、默认批量上限、GIL 切换间隔 | 服务稳定性：并发 256 下 0 报错 |

## 4. 怎么保证没算错

1. **和 Kev 自己的计算逐题比**（`python -m kevfast.check_parity`）：同一个模型、同一批文本，kevfast 和 Kev 原生实现给出的概率对比。各种开关组合下，最大差异都在 0.01–0.025，平均约 0.0005，首选答案基本不变，属于 bf16 精度的正常差异。
   - 实现上，分支之间严格隔离：每个分支只读自己祖先的 key/value，线性注意力层从父段的最终状态接着算。
2. **FP8 的漂移**单独测：平均 |dp| 0.002，576 道题首选变 2 道。
3. **端到端**：kevfast 当作 Kev 服务的直接替代，跑完整评测流程（拟合校准、两个视图、分流、区分度）。AUROC 和分流与原服务一致：辱骂 0.9641 对 0.9644，违规被自动放行 1.8% 对 2.0%。
4. **训练格式对齐**：新格式要按同样格式训练才能用。我们核对过 300 条训练记录，Kev 训练时的编码和 kevfast 服务时的输入逐 token 完全一致（`python -m kevfast.check_tokens`）。

## 5. 新格式训练后的准确率（v2s）

用和 v1 完全相同的标签，只改格式，训练一版 v2s（约 2.7 小时）。测试集 3,002 条：

| | 辱骂 | 营销 | 注入检查 | 违规被自动放行 | 正常被误处置 | 单次请求 p50（并发 16，含复问） |
|---|---|---|---|---|---|---|
| v1（原格式） | 0.964 | 0.999 | 0.996 | 2.0% | 0.3% | 1,663 ms |
| v2s（新格式） | 0.962 | 0.999 | 0.972 | 1.5% | 0.5% | 783 ms |

前三列是 AUROC。

- 注入检查变弱的原因：这道题从没训练过。原格式里题目带着完整的规则说明，不训练也能答；新格式只给短问题，没训练就答不好。训练集里有 154 条注入样本还没有标签，补标签再训，是推测能补回来的办法。
- FP8 与 bf16 的准确率差异在误差范围内。
- **去复问的代价**：策略里有一个"放行必须经过同次复问确认"的开关（`confirm_pass`，默认开）。去复问后快判一条都不放行，所以必须同时关掉这个开关。按测算，关掉后：

| | 现行（有复问） | 去复问 + 关双确认 |
|---|---|---|
| 违规被自动放行 | 1.5% | 2.1% |
| 正常自动放行 | 66.8% | 71.4% |

这一项待负责人定。

## 6. 试过但没用的

| 尝试 | 结果 |
|---|---|
| 大批量也录 CUDA graph（要先补齐成固定形状） | 一批 32 条只快约 2%，补齐反而慢 57%。批量时显卡在满负荷计算，启动开销可以忽略。保留为开关 `dense`，默认关 |
| 线性注意力换逐 token 递推算子（短序列不用按 64 token 一块算） | 快不了（58.8 对 59.4），保留为开关 `deltanet_kernel` |
| 注意力用 log-sum-exp 合并代替融合 SDPA | 更慢（55.7 对 59.4），不用 |
| 换 vLLM / SGLang | 没换。有报告称 vLLM 里 Qwen3.5-4B 的前缀缓存块是 528 token，短于它的前缀命中率为 0，而我们的规则前缀只有 294 token；Kev 的打分头也要自己移植 |
| vLLM 用的 FlashInfer Blackwell 线性注意力算子 | 只支持数据中心卡（SM100）+ CUDA 13，这张卡是 SM120，用不了 |

## 7. 上限在哪、还能往哪走

- 这张卡上，每秒约 60 条时，批量再大也不会更快，按 token 计约每秒 4,000–5,000（计入补齐）。
- 矩阵乘法约占一半时间，已接近 FP8 能力。整体算力利用率约 FP8 峰值的 37%。剩下的时间在线性注意力、归一化、量化等小算子和数据搬运上。
- 下一步可选（都还没做）：

| 方向 | 估计效果 | 代价 |
|---|---|---|
| 规则名和选项各压成 1 个 token，每条约 67 → 40 个 token | 估计再快约 1.5 倍 | 要重新训练 |
| 融合小算子 | 收益不确定 | 工作量大 |
| 更好的卡（4090 / A100 等） | — | — |
| 多卡各自独立服务，吞吐按卡数叠加 | — | — |

## 8. 踩过的坑（都已处理，记在开发计划问题 13–15）

1. **显存不足**：
   - 一次塞太多题目分支（约 14k token）会爆显存，于是加了每次计算的 token 预算。
   - FP8 "auto" 同时留两份权重，加上计算图在 16GB 上放不下，于是最快配置用 FP8 "on"。
   - 高并发下服务端显存不足：改为自动拆半重算，并降低默认批量。
2. **共享前缀被每个分支复制一份**：注意力里每个分支单独取一遍规则前缀的 key，显存暴涨。改成前缀只取一次（批量小时随段取出走融合 SDPA，批量大时用 log-sum-exp 精确合并）。
3. **服务返回 422**：服务文件用了 `from __future__ import annotations`，FastAPI 认不出局部导入的请求类型，3,002 条全部 422。去掉后正常。
4. **去复问时评测全失败**：服务端去掉复问，客户端仍发复问题。pi-ai 客户端因缺答案判失败，服务端却都返回了 200。现在两边都加了明确的开关和报错（`JEV_IN_CALL_CONFIRM=0`；服务端收到复问时返回 400）。
5. **图被反复重录**：小批量的图按（行数 × 长度档）录制，组合太多超过上限就会反复重录。行数也分档后解决。

## 9. 面试时可能被问到的

| 问题 | 回答要点 |
|---|---|
| 为什么不直接用 vLLM？ | 我们的判官不是生成模型，是带自定义打分头的分类器；另外前缀缓存块大小对我们的短前缀不友好（见第 6 节）。在自己的引擎上做，每项优化都能单独开关、逐项对比准确率 |
| 怎么证明优化没有改变结果？ | 第 4 节：逐题和原实现比概率、FP8 单独测漂移、完整评测流程端到端对比、训练与服务逐 token 对齐 |
| 速度提升主要来自哪？ | 大头是"少算 token"：①②③ 从 9.8 到 45.7。计算层面（FP8、分词缓存等）从 45.7 到约 60。CUDA graphs 主要降单条延迟 |
| 混合结构（线性注意力）给前缀缓存带来什么难点？ | 线性注意力层的缓存是一个固定大小的递推状态，不能像 KV 那样按位置截取。所以缓存的是"规则块结束时"的状态，子段从这个状态接着算；拼接多段时要给每段传自己的初始状态（fla varlen） |
| 代价是什么？ | 新格式要重新训练；没训练过的题（注入检查）会变弱；去复问要同时改策略（双确认），漏放略升 |

## 10. 怎么跑

```bash
# 算力服务器，kev 的环境，PYTHONPATH 指向仓库的 python/
python -m kevfast.check_parity <模型目录> <题目 json> <文本 jsonl> 96 --fp8   # 和 Kev 逐题比
python -m kevfast.bench <模型目录> <题目 json> <文本 jsonl> 512               # 提速阶梯
KF_LAYOUT=rules_first KF_QUESTIONS=short KF_CONFIRM=off KF_FP8=on \
  python -m kevfast.serve --run /hy-tmp/train/runs/kev4b-v2s --port 8010      # 最快配置的服务
python -m kevfast.loadtest 8010 <题目 json> <文本 jsonl> 64                    # HTTP 压测
```
